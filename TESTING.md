## Обязательное правило миграции репозитория — 28.10.2026

По прямому решению владельца проект переезжает в другой GitHub-репозиторий.
В старый репозиторий больше не пушить, в том числе ветки и теги.
Перед следующим коммитом и любым push сначала получить от владельца точный
адрес нового репозитория и подключить рабочую копию к нему. До этого
сохранять все Changes локально; не выполнять коммит, push или создание PR.
Проверить fetch/push URL всех remotes, upstream текущей ветки и настройки
push по умолчанию: отправка не должна направляться в старый репозиторий.
Не использовать push --all/--mirror для переноса без отдельного согласования.
Сохранить историю Git и незакоммиченные изменения; не делать reset/clean
или замену рабочего дерева ради подключения нового remote.
После подключения нового репозитория действует последнее решение о проверках
в начале этого документа; коммит/пуш требуют отдельной команды.
Подключение выполнено 28.10.2026: origin fetch/push — https://github.com/lava-reborn/server.git; текущая ветка release/new-mechanics-and-updates-2026-10-27 от нового origin/main.

## Прежнее правило полного локального прогона (для текущего этапа отменено)

По решению владельца от 27.10.2026 перед каждым пушем сначала выполняется
полный локальный прогон из PowerShell на текущих исходниках, включая Changes
и новые тестовые файлы. Адресный список, `--affected` или один SQLite-набор
не заменяют полный прогон. После изменения кода результат предыдущего
прогона требуется актуализировать. Пуш выполняется только по отдельной
команде владельца; скрипт не коммитит, не пушит и не развёртывает сервер.

Правило действует и в будущих ветках. Порядок работы:

1. Сначала сверить изменённое поведение и актуализировать содержательные
   регрессии/фикстуры под согласованные правила. Баг не маскировать заменой want.
2. Выполнить полный локальный All на актуальном дереве, разобрать ошибки,
   предупреждения, находки безопасности и пропуски; после исправлений
   повторить необходимые проверки и полный итоговый прогон.
3. Перед разрешённым push проверить, что отчёт относится к отправляемому
   коду. После push должен пройти обязательный GitHub Actions CI.
4. Перед merge проверить локальный результат и зелёный CI именно текущего
   PR/head; новый код или разрешённый конфликт делает старый результат
   недостаточным. Повторный локальный прогон не нужен, если проверяемое
   дерево не изменилось и результат относится к нему.
5. Merge и deployment — отдельные действия/статусы, не результат запуска
   скрипта. Существующие обязательные gates и отдельные разрешения сохраняются.

Инструменты проверок, спецификации, виртуальное окружение, тестовые БД и
отчёты — материалы разработки, а не файлы клиента игроков. Не добавлять
их в client/base.txt, client/extra.txt, client/files/ или установочный res/.
Сборщик отклоняет пути локального стенда/проверок в клиентском manifest;
deploy/rsync.filter также исключает новые локальные runner-файлы и окружение
из серверного пакета. Общие runtime-генераторы tools/widescreen.py и
tools/export_texts.py нужны серверной сборке, их исключать нельзя.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\run_local_checks.ps1 -Mode All -Res 'D:\lava-reborn\res'
```

См. `tools/LOCAL_CHECKS.md`: зависимости, ограничения и чтение отчёта.
Режим All запускает native-наборы через штатный `tools/suite.py`, затем
в локальных одноразовых Docker-контейнерах проверочные скрипты текущего CI:
syntax, экспорт строк, три SQLite-шарда, merge exactly-once, PostgreSQL
через `deploy/ci/pg_suites.sh` и локальную упаковку. Ресурсы читаются с диска;
SSH к production, получение ключей и деплой не выполняются. Это локальная
проверка этапов CI, а не воспроизведение сервиса GitHub Actions: его
cache/artifact transport, права, сеть и удалённый gate остаются проверкой CI.
Сам `.github/workflows/ci.yml` не изменяется и остаётся обязательным.

Тестовые БД изолированы. PostgreSQL создаётся только в собственном временном
контейнере; скрипт не принимает URL внешней рабочей БД. Недоступные ресурсы,
Flash, Docker, сканеры и пропуски отражаются как неполная проверка, а не OK.
Известные падения/успешные повторы CI сохраняются в отчёте и требуют разбора.
Нельзя править ожидания/выключать тесты ради зелёного результата.

Отчёт `logs/local-checks/<run>/report.md` содержит коды возврата, длительности,
предупреждения, пропуски и все результаты доступных сканеров. Bandit —
статический анализ Python; pip-audit — известные уязвимости пакетов текущего
Python-окружения с запросами к advisory-сервису. Ни один из них не доказывает
отсутствия уязвимостей в игре, Flash, C#, инфраструктуре или бизнес-логике.
Автоматического исправления/установки пакетов на хосте нет. CPU/RSS —
выборочные замеры тестового дерева процессов, Docker stats — отдельно;
это не измерение FPS, SQL-нагрузки или производительности production.

Текущая пауза тестов сохраняется: добавление скрипта не запускает его.
Дальнейшие запуски агентом — только по команде владельца.

## Регрессии боя, квестов и предметов

Для наборов с игровыми данными задаётся `LAVA_RES` на каталог клиентских
ресурсов. Все перечисленные команды запускаются отдельно:

```text
python -B server/test_action_order.py
python -B server/test_action_sync.py
python -B server/test_healing_completion.py
python -B server/test_reload_sync.py
python -B server/test_quest_state.py
python -B server/test_quest_transactions.py
python -B server/test_weaponcraft_completion.py
python -B server/test_weapon_upgrade_integrity.py
python -B server/test_repair_policy.py
python -B server/test_release_sets.py
python -B server/test_weapon_requirements.py
python -B server/test_abuhamed_miner_loot.py
python -B server/test_combat_xp_cap.py
python -B server/test_boss_hotfix.py
python -B tools/test_action_hotkeys.py
python -B tools/test_quick_medicine.py
python -B tools/test_widescreen.py
```

Проверки действий моделируют отложенные callback, отмену, замену и серверные
кадры. Квестовые наборы используют изолированный Store в памяти для ошибок
взятия/сдачи/отмены, коммита, потери ответа и повторной сдачи.

Целостность оружейных улучшений проверяется на реальных обработчиках:
доступность источников и чертежей, пары A/G, объявленные эффекты, взятие,
сдача, износ и отказанные операции окна мастера. `tools/audit_weapon_upgrades.py`
используется этим набором как общий обход источников и рецептов; это
зависимость регрессии, а не файл результатов проверки.

Предметные проверки покрывают коэффициенты ремонта и обе валюты, базовые
уровни допуска к броне, опыт с бонусами навыков, независимые броски лута,
совместимые обычные патроны и суммарный лимит боевого опыта за одного моба
при прокачиваемом навыке 17+. Реальное поведение ОС/Flash и PostgreSQL
при аварийном отказе этими in-process наборами не подтверждается.

Хоткей медицины проверяется при смене ws: в бою выбирается только боевая
медицина, в мире — приоритет обычной с резервной боевой, сразу после убийства последнего врага
и без движения. Недавний урон и старый клиентский дедлайн выбор не меняют.
В `test_quick_medicine.py` добавлены регрессии порядка смешанных средств
и численного выбора восстановления HP/выносливости при полном/неполном HP.
В `test_healing_completion.py` проверяется смена допустимой категории
медицины при включении ws без списания отменённого предмета и ОД,
а также завершение боевого лечения после перехода комнаты в мир. `test_quest_transactions.py` содержит
сдачу «Поставок провизии» с покупным фулем, списанием и защитой от повтора.
`tools/test_action_hotkeys.py` исполняет AVM1 проверки ОД выбранной медицины
с сохранением исходного допуска остальных действий, а также сброса старой
цели остановленного маршрута без повторной отправки активного маршрута.
Ассортимент проверяется в `test_stall_bands.py`, `test_abuhamed_trade.py`
и `test_dongola_trade.py`: доступность A/G, порядок полных комплектов,
лимит 64 товара и покупка в правильной валюте. У Марата только подсумки;
полная полоса комплектов Абу-Хамеда остаётся у Симоны.

Тестовые правки истории через отдельное SQL-подключение должны запросить
`q_list` перед проверкой доступности: такое изменение намеренно не обходит
двухсекундный снимок подключения. Боевые фикстуры ждут `mobs.HEX_MS` за шаг;
ранний выстрел по правилам отменяет остаток пути.

Проверка лута Абу-Хамеда удерживает точную границу 5% золотого портсигара
даже при совпадении с общим ценным лутом уровня. Обычный Золотой Алмаз
отсутствует, квестовый Алмаз сохраняет прежние условия и границу 10%.
Тест улучшений также проверяет активную перезарядку: откат сохраняет её
завершение, успешное удаление не порождает кадр для старого экземпляра.

Временный хотфикс боссов от 26.10 проверяется `test_boss_hotfix.py`:
HP ×1,5 без изменения SP/урона/множителя опыта, прежние 22 типа носителей
золота получают региональные награды: Нубийка/Хальфа 1 G, Абри 2 G,
Донгола 3 G, Абу-Хамед 4 G, слитками по 1 G. Остальным золото не
добавляется. Мировые боссы — чётные часы МСК каждые 2 часа, склады
отдельно в 20:00. Тюрьмы в текущих Changes — 13/17/21 МСК; это расписание
согласуется с часовыми фикстурами городов и подписями карты. Старые обмены, включая два слитка
за 2 G у Джерраха и комиссию Мортимера, остаются прежними. Долгие городские
наборы слитков сохраняют сокетные проверки с актуальными ожиданиями;
лёгкий набор их полный прогон не заменяет.

`test_reload_sync.py` проверяет отложенное списание патронов и ОД, отмену
сменой оружия, движением, принятым выстрелом и лечением, сохранение при
отказе команды, повторный callback, ошибку записи и изменение входных
предметов. Используется SQLite в памяти без ожиданий и игровых симуляций.
Набор включается в CI общим обнаружением `server/test_*.py`.
Сокетный `test_inventory.py` проверяет единственную выдачу нового состояния
патронов и магазина после завершения; точный порядок относительно дедлайна
проверяет in-process набор, независимо от скорости машины CI.

После ревью также проверяются отказ завершения лечения с освобождением
предмета, отмена перезарядки при продаже на аукционе, отсутствие квестовой
обёртки у перезарядки и безопасное закрытие при неподтверждённом коммите.
Сценарии тира ожидают завершения перезарядки; учебный сценарий ждёт
восстановления ОД при отказе, как и перед выстрелом. Ассортимент Абу-Хамеда
проверяется с покупкой брони у Симоны. Клиентская проверка `moving=1`
подтверждает отсутствие повторного события движения и изменения маршрута/ОД.
Отдельно проверяются неполные списки требований пулемётов, повторное
использование рассчитанных характеристик без общих изменяемых списков и
сортировка A/G по семейству при изменении отображаемого имени.

## Какие бывают наборы

| Где | Что проверяет | Как |
|---|---|---|
| `server/test_*.py` | механику сервера | секция «in process» с формулами, потом живой сервер и клиент на сокете |
| `server/test_*.py` без сервера | порядок, который на сокете не поймать | `server.Session` в процессе, кадры пишутся в подставной `Writer` (`test_relogin`) |
| `data/test_*.py` | таблицы мира | читает `data/*.json` и сверяет с клиентом, вики, кодом сервера |
| `tools/test_*.py` | инструменты | `tools/test_<имя>.py` для `tools/<имя>.py`; `--affected` берёт его при правке инструмента |

Набор это обычный скрипт: ни pytest, ни unittest. Код выхода 0 значит
зелёный, всё остальное красный. Каждый набор запускается сам по себе:
`python server/test_combat.py` (с `LAVA_RES`, если ему нужен клиент).

## Скелет набора

```python
"""Одна строка: что за механика (она же «механика» в report.html).

Абзац: что проверяется, по каким файлам клиента это ожидание выведено
(recon/as-src, recon/analysis), какие переменные сокращают время и почему.

    LAVA_RES=.../client/res python3 server/test_something.py
"""
import os, sys, tempfile, ...

HERE = os.path.dirname(os.path.abspath(__file__))
DB = os.path.join(tempfile.mkdtemp(), "something.db")
os.environ["LAVA_DB"] = DB          # до импорта модулей, которые читают окружение

sys.path.insert(0, HERE)
import combat  # noqa: E402
from testkit import check, fails  # noqa: E402

# --- the formulas, in process ------------------------------------------------
check("label: the rule in words", combat.something(1, 2), 3)

# --- the server ----------------------------------------------------------------
srv = subprocess.Popen(...)
try:
    ...
except Exception:
    import traceback
    fails.append("test crashed:\n" + traceback.format_exc())
finally:
    srv.terminate()
    srv.wait(timeout=5)
    # хвост лога сервера в fails: Traceback всегда, остальное при провале

print()
if fails:
    print("FAILED %d:" % len(fails))
    for f in fails:
        print(" -", f)
    sys.exit(1)
print("something OK")
```

Обязательное:

- **Docstring.** Первая строка попадает в отчёт как механика (или
  `MECHANIC = "..."`, если первая строка для этого не годится). Дальше
  объяснение: почему ожидается именно это, со ссылками на клиент и разбор.
- **Окружение до импорта.** `server.py`, `accounts`, `quests` читают
  `LAVA_*` при импорте: `LAVA_DB`, `LAVA_QUESTS` и прочее ставятся в
  `os.environ` раньше, чем импортируется модуль (`# noqa: E402` у импортов
  после этого).
- **`check` и `fails` только из `server/testkit.py`.** Свой `check` или
  `assert` работают, но их проверки не попадают в `<набор>.jsonl` и
  `report.html`. `data/` и `tools/` импортируют `testkit` так же, добавив
  `server/` в `sys.path`.
- **Заголовки секций** `# --- имя ---`: по ним отчёт режет набор на тесты.
  Последний заголовок над `check` и есть имя теста.
- **Падение набора не теряет проверки.** Живую часть оборачивать в
  `try/except Exception`, исключение класть в `fails`, сервер гасить в
  `finally`. Набор, упавший с трассировкой посередине, без этого не скажет,
  что успел проверить.
- **Хвост с `fails` и `sys.exit(1)`**, как в образце: запускалка смотрит на
  код выхода.

## Как писать `check`

`check(label, got, want)` сравнивает через `==`, печатает `  ok  label` или
кладёт в `fails` подпись с `got` и `want`.

- **Подпись это правило игры словами**, а не имя переменной: «a free
  resurrection is the penalised one: a tenth of HP and stamina», а не
  `hp check`. Упавшая проверка должна читаться без исходника.
- **Продолжение предыдущей проверки** начинается с `"  .."`: так в отчёте
  видно, что это следствие, а не новое правило.
- **`want` вычисляется из правила, а не переписывается из вывода.** Если
  `want` это число, которое показал прогон, тест ничего не проверяет.
  Брать формулу из вики или клиента, константу из модуля (`combat.WEAR_PER_ROUND`),
  или объяснить число в комментарии.
- **Несколько связанных фактов одной проверкой** через кортеж:
  `check("...", (a, b, c), (1, True, 0))`. Так видно всё сразу, а не только
  первое расхождение.
- **Проверка должна уметь упасть от настоящей ошибки.** Не проверять
  арифметику и пересказ кода (`paced(x) == x * SCALE`, константа равна
  самой себе): такая проверка падает только вместе с языком. Правило
  проверяется там, где его нарушение видно: в живом наборе, на кадрах,
  которые получит клиент. Перед новой проверкой спросить, какую поломку
  она поймает и не ловит ли её уже другой набор.
- **Нельзя ослаблять проверку, чтобы она прошла.** Если сломалась сцена
  (моб умер раньше, шанс попадания поменялся), чинить сцену.

## Секция «in process»

### Существующие регрессионные TestCase

Для сценариев отмены действий, лечения, снимка квестов и исполнения AVM1
сохранены стандартные `TestCase`/`IsolatedAsyncioTestCase`: они дают очистку
фикстур и отдельный цикл asyncio без своего тестового движка. Такие файлы
остаются обычными запускаемыми скриптами и вызывают
`testkit.run_cases(ИменноЭтотКласс)`, а не `unittest.main()`.
Каждый сценарий проходит через общий `check`, попадает в JSONL/HTML и влияет
на код выхода. Ошибки class-fixture также учитываются; пропуск не выдаётся
за успешную проверку. Импортированные классы фикстур повторно не запускаются.
Это исключение сохраняет полезные регрессии без переписывания их утверждений;
остальные наборы следуют обычному формату `check/fails` выше.

`tools/avm_test.py` — общий исполнитель ограниченного набора инструкций AVM1
для тестов хоткеев и подбора медицины. Он исполняет собранные байты и не
доказывает корректность фокуса Windows или отрисовки Flash. Для этого остаётся
ручная проверка. Новые проверки из этой области добавляются в существующий
набор; копировать интерпретатор или извлекать его переписыванием AST не нужно.

Всё, что считается без сервера, проверяется в начале набора напрямую:
формулы, таблицы, геометрия, решения вроде `RoomCombat.hostilities`. Она
отрабатывает за секунды и прогоняется при каждой правке. Объекты для неё
собираются вручную (`combat.Fighter(seat)`, `RoomCombat.__new__` с
подставной комнатой), без сокета.

Если проверке нужно другое окружение (переменная читается при импорте),
её задают отдельному процессу:
`subprocess.run([sys.executable, "-c", "..."], cwd=HERE, env=dict(os.environ, LAVA_X="..."))`.

## Живой сервер

**Изоляция.** Каждый набор поднимает свой сервер и не мешает соседям,
запущенным параллельно:

- порт: `free_port()` (bind на 0), в `LAVA_PORT`, `LAVA_HOST="127.0.0.1"`;
- `LAVA_POLICY_PORT="0"`: иначе сервер займёт 843, и второй параллельный
  набор не стартует («server did not start»);
- база: свой файл в `tempfile.mkdtemp()`, в `LAVA_DB`; аккаунты
  регистрируются заранее через `accounts.Store(DB).register(...)`;
- свои таблицы, если набор зависит от строки, которой в данных может не
  стать: копия таблицы во временный файл с нужной строкой и путь в
  переменную (`LAVA_QUESTS`, `LAVA_PLACEMENTS`, `LAVA_PASSAGES`). Так
  `test_combat` держит квест «Голодные собаки», которого в `quests.json`
  больше нет.

**Сцена.** Набор сам говорит, какой мир ему нужен, а не полагается на
значения по умолчанию, которые меняются:

| Переменная | Зачем |
|---|---|
| `LAVA_GX`, `LAVA_GY` | стартовая клетка карты для новых персонажей |
| `LAVA_START` | стартовый посёлок (181 или 183) |
| `LAVA_CHEATS="1"` | `/goto`, `/give`, `/money`, `/skill`, `/spec` в чате для расстановки сцены |
| `LAVA_SEED` | случайность сервера с зерном |
| `LAVA_AP_REGEN` | быстрее ОД, чтобы бой не ждал полосы |
| `LAVA_RESPAWN`, `LAVA_OBJECT_RESPAWN`, `LAVA_LEAVE_COMBAT` | короче возрождение (существ 300 с, предметов 45 с; `LAVA_RESPAWN` сокращает оба) и таймер выхода |
| `LAVA_START_AFRO` | деньги на старте |
| `LAVA_ACTION_SCALE` | короче паузы боя (прицел, замах, перезарядка); только если набор не проверяет сами длительности, ОД при этом не ускоряются (`server/pace.py`) |
| `LAVA_TEST_LOG="1"` | хвост лога сервера даже в зелёном прогоне (читает сам набор в `finally`, ставят руками при отладке) |

У каждой переменной в `env` комментарий, почему такое значение: что набор
проверяет и почему ему не годится игровое. Сокращать можно только то, что
набор не проверяет: если проверяется сам таймер выхода, его оставляют
игровым (так в `test_combat`).

**Старт.** Сокет к серверу только через `testkit.connect(PORT, srv, log)`
(`log` это список строк, которые сливает поток, или путь к файлу лога), а не
свой цикл с окном в десять секунд. В одиночку сервер стартует за секунду-две.
Когда CI шёл на раннерах GitHub и поднимал дюжину разом на двух ядрах,
короткое окно роняло четверть наборов «server did not start», которые потом
проходили одни; на своём раннере CI поднимает восемь разом на четырёх
ядрах. `connect` ждёт
до `LAVA_START_WAIT` (120 с), а если процесс сервера умер раньше, падает сразу
с хвостом его лога.

**Клиент.** Класс `Client` копируется из соседнего набора: `send` с нулевым
байтом в конце, `frames(wait)` (всё за окно), `until(pred, wait)` (до
нужного кадра). Порядок входа как у настоящего клиента: `hello`, `login`,
`newPers` и `actPlayer` или `selPers`, `lenter`. Если сомневаешься, что
шлёт клиент и в каком порядке, читать `recon/as-src/lol/`, а не угадывать.

**Протокол.**

- Ждать кадр через `until`, а не `time.sleep`: под нагрузкой параллельного
  прогона фиксированная пауза то мала, то велика.
- `frames(wait)` всегда ждёт окно целиком, даже если ответ пришёл сразу.
  Когда нужен «весь ответ на команду», а последнего кадра не назвать,
  послать маяк: сервер обрабатывает команды по очереди, каждую до конца,
  поэтому ответ на `q_status` несуществующего типа приходит после всех
  кадров предыдущих команд (`Client.sync` в `test_halfa_training`). Кадры,
  которые сервер шлёт позже по таймеру (ходьба, выход из боя, `lcall` после
  драки), маяк не ловит: их ждать по имени через `until`.
- Фиксированное окно оправдано, только когда проверяется, что за это время
  ничего не пришло («карта не открылась, никто не сдвинулся»).
- `cmdAck` у клиента строго FIFO, ровно один на команду из `EXPECTS_ACK`
  (`PROTOCOL.md` §7). Набор, который проверяет новую команду, проверяет и
  число ack: лишний или пропущенный вешает настоящий клиент молча.
- Комната шлёт свой трафик (респаун, край войны, ходьба мобов). Фильтровать
  нужные кадры (`only(frames, "faAim", "faShot")`), а не требовать, чтобы
  других не было.

**Лог сервера.** Вывод сервера собирается потоком в список. В `finally`:
`Traceback` в логе это провал набора, даже если все проверки зелёные; при
любом провале хвост лога идёт в `fails`.

## Случайность и время

- Бой случаен по-настоящему. Проверять форму (каждый выстрел внутри пары
  `faShot`, урон в пределах оружия, опыт по формуле), а не запись
  конкретного боя. Цикл «стрелять, пока не умрёт» с пределом попыток лучше
  расчёта на число выстрелов.
- `LAVA_SEED` делает прогон повторяемым, но не защищает от смены формулы.
  После правки шансов набор может стать хрупким: чинить сцену (ближе
  подойти, сильнее оружие, моб слабее), а не расширять допуск без причины.
- Набор ждёт игровые часы, а не процессор. Долгие паузы сокращать
  переменными сервера, а не ожиданием покороче в тесте: тест с коротким
  ожиданием просто начнёт падать под нагрузкой.
