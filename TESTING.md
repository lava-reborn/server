# Как писать тесты

Как запускать наборы, описано в README («Запуск»). Здесь: как устроен набор,
как его написать и чего в нём не делать. Образцы для копирования:
`server/test_relogin.py` (короткий, в процессе) и `server/test_combat.py`
(живой сервер, бой со случайностью).

## Какие бывают наборы

| Где | Что проверяет | Как |
|---|---|---|
| `server/test_*.py` | механику сервера | секция «in process» с формулами, потом живой сервер и клиент на сокете |
| `server/test_*.py` без сервера | порядок, который на сокете не поймать | `server.Session` в процессе, кадры пишутся в подставной `Writer` (`test_relogin`) |
| `data/test_*.py` | таблицы мира | читает `data/*.json` и сверяет с клиентом, вики, кодом сервера |
| `tools/test_*.py` | инструменты | `tools/test_<имя>.py` для `tools/<имя>.py`; `--affected` берёт его при правке инструмента |

Набор это обычный скрипт: ни pytest, ни unittest. Код выхода 0 значит
зелёный, всё остальное красный. Каждый набор запускается сам по себе:
`python server/test_combat.py` (с `LAVA_RES`, если ему нужен клиент).

## Скелет набора

```python
"""Одна строка: что за механика (она же «механика» в report.html).

Абзац: что проверяется, по каким файлам клиента это ожидание выведено
(recon/as-src, recon/analysis), какие переменные сокращают время и почему.

    LAVA_RES=.../client/res python3 server/test_something.py
"""
import os, sys, tempfile, ...

HERE = os.path.dirname(os.path.abspath(__file__))
DB = os.path.join(tempfile.mkdtemp(), "something.db")
os.environ["LAVA_DB"] = DB          # до импорта модулей, которые читают окружение

sys.path.insert(0, HERE)
import combat  # noqa: E402
from testkit import check, fails  # noqa: E402

# --- the formulas, in process ------------------------------------------------
check("label: the rule in words", combat.something(1, 2), 3)

# --- the server ----------------------------------------------------------------
srv = subprocess.Popen(...)
try:
    ...
except Exception:
    import traceback
    fails.append("test crashed:\n" + traceback.format_exc())
finally:
    srv.terminate()
    srv.wait(timeout=5)
    # хвост лога сервера в fails: Traceback всегда, остальное при провале

print()
if fails:
    print("FAILED %d:" % len(fails))
    for f in fails:
        print(" -", f)
    sys.exit(1)
print("something OK")
```

Обязательное:

- **Docstring.** Первая строка попадает в отчёт как механика (или
  `MECHANIC = "..."`, если первая строка для этого не годится). Дальше
  объяснение: почему ожидается именно это, со ссылками на клиент и разбор.
- **Окружение до импорта.** `server.py`, `accounts`, `quests` читают
  `LAVA_*` при импорте: `LAVA_DB`, `LAVA_QUESTS` и прочее ставятся в
  `os.environ` раньше, чем импортируется модуль (`# noqa: E402` у импортов
  после этого).
- **`check` и `fails` только из `server/testkit.py`.** Свой `check` или
  `assert` работают, но их проверки не попадают в `<набор>.jsonl` и
  `report.html`. `data/` и `tools/` импортируют `testkit` так же, добавив
  `server/` в `sys.path`.
- **Заголовки секций** `# --- имя ---`: по ним отчёт режет набор на тесты.
  Последний заголовок над `check` и есть имя теста.
- **Падение набора не теряет проверки.** Живую часть оборачивать в
  `try/except Exception`, исключение класть в `fails`, сервер гасить в
  `finally`. Набор, упавший с трассировкой посередине, без этого не скажет,
  что успел проверить.
- **Хвост с `fails` и `sys.exit(1)`**, как в образце: запускалка смотрит на
  код выхода.

## Как писать `check`

`check(label, got, want)` сравнивает через `==`, печатает `  ok  label` или
кладёт в `fails` подпись с `got` и `want`.

- **Подпись это правило игры словами**, а не имя переменной: «a free
  resurrection is the penalised one: a tenth of HP and stamina», а не
  `hp check`. Упавшая проверка должна читаться без исходника.
- **Продолжение предыдущей проверки** начинается с `"  .."`: так в отчёте
  видно, что это следствие, а не новое правило.
- **`want` вычисляется из правила, а не переписывается из вывода.** Если
  `want` это число, которое показал прогон, тест ничего не проверяет.
  Брать формулу из вики или клиента, константу из модуля (`combat.WEAR_PER_ROUND`),
  или объяснить число в комментарии.
- **Несколько связанных фактов одной проверкой** через кортеж:
  `check("...", (a, b, c), (1, True, 0))`. Так видно всё сразу, а не только
  первое расхождение.
- **Проверка должна уметь упасть от настоящей ошибки.** Не проверять
  арифметику и пересказ кода (`paced(x) == x * SCALE`, константа равна
  самой себе): такая проверка падает только вместе с языком. Правило
  проверяется там, где его нарушение видно: в живом наборе, на кадрах,
  которые получит клиент. Перед новой проверкой спросить, какую поломку
  она поймает и не ловит ли её уже другой набор.
- **Нельзя ослаблять проверку, чтобы она прошла.** Если сломалась сцена
  (моб умер раньше, шанс попадания поменялся), чинить сцену.

## Секция «in process»

Всё, что считается без сервера, проверяется в начале набора напрямую:
формулы, таблицы, геометрия, решения вроде `RoomCombat.hostilities`. Она
отрабатывает за секунды и прогоняется при каждой правке. Объекты для неё
собираются вручную (`combat.Fighter(seat)`, `RoomCombat.__new__` с
подставной комнатой), без сокета.

Если проверке нужно другое окружение (переменная читается при импорте),
её задают отдельному процессу:
`subprocess.run([sys.executable, "-c", "..."], cwd=HERE, env=dict(os.environ, LAVA_X="..."))`.

## Живой сервер

**Изоляция.** Каждый набор поднимает свой сервер и не мешает соседям,
запущенным параллельно:

- порт: `free_port()` (bind на 0), в `LAVA_PORT`, `LAVA_HOST="127.0.0.1"`;
- `LAVA_POLICY_PORT="0"`: иначе сервер займёт 843, и второй параллельный
  набор не стартует («server did not start»);
- база: свой файл в `tempfile.mkdtemp()`, в `LAVA_DB`; аккаунты
  регистрируются заранее через `accounts.Store(DB).register(...)`;
- свои таблицы, если набор зависит от строки, которой в данных может не
  стать: копия таблицы во временный файл с нужной строкой и путь в
  переменную (`LAVA_QUESTS`, `LAVA_PLACEMENTS`, `LAVA_PASSAGES`). Так
  `test_combat` держит квест «Голодные собаки», которого в `quests.json`
  больше нет.

**Сцена.** Набор сам говорит, какой мир ему нужен, а не полагается на
значения по умолчанию, которые меняются:

| Переменная | Зачем |
|---|---|
| `LAVA_GX`, `LAVA_GY` | стартовая клетка карты для новых персонажей |
| `LAVA_START` | стартовый посёлок (181 или 183) |
| `LAVA_CHEATS="1"` | `/goto`, `/give`, `/money`, `/skill`, `/spec` в чате для расстановки сцены |
| `LAVA_SEED` | случайность сервера с зерном |
| `LAVA_AP_REGEN` | быстрее ОД, чтобы бой не ждал полосы |
| `LAVA_RESPAWN`, `LAVA_OBJECT_RESPAWN`, `LAVA_LEAVE_COMBAT` | короче возрождение (существ 300 с, предметов 45 с; `LAVA_RESPAWN` сокращает оба) и таймер выхода |
| `LAVA_START_AFRO` | деньги на старте |
| `LAVA_ACTION_SCALE` | короче паузы боя (прицел, замах, перезарядка); только если набор не проверяет сами длительности, ОД при этом не ускоряются (`server/pace.py`) |
| `LAVA_TEST_LOG="1"` | хвост лога сервера даже в зелёном прогоне (читает сам набор в `finally`, ставят руками при отладке) |

У каждой переменной в `env` комментарий, почему такое значение: что набор
проверяет и почему ему не годится игровое. Сокращать можно только то, что
набор не проверяет: если проверяется сам таймер выхода, его оставляют
игровым (так в `test_combat`).

**Старт.** Сокет к серверу только через `testkit.connect(PORT, srv, log)`
(`log` это список строк, которые сливает поток, или путь к файлу лога), а не
свой цикл с окном в десять секунд. В одиночку сервер стартует за секунду-две.
Когда CI шёл на раннерах GitHub и поднимал дюжину разом на двух ядрах,
короткое окно роняло четверть наборов «server did not start», которые потом
проходили одни; на своём раннере CI поднимает восемь разом на четырёх
ядрах. `connect` ждёт
до `LAVA_START_WAIT` (120 с), а если процесс сервера умер раньше, падает сразу
с хвостом его лога.

**Клиент.** Класс `Client` копируется из соседнего набора: `send` с нулевым
байтом в конце, `frames(wait)` (всё за окно), `until(pred, wait)` (до
нужного кадра). Порядок входа как у настоящего клиента: `hello`, `login`,
`newPers` и `actPlayer` или `selPers`, `lenter`. Если сомневаешься, что
шлёт клиент и в каком порядке, читать `recon/as-src/lol/`, а не угадывать.

**Протокол.**

- Ждать кадр через `until`, а не `time.sleep`: под нагрузкой параллельного
  прогона фиксированная пауза то мала, то велика.
- `frames(wait)` всегда ждёт окно целиком, даже если ответ пришёл сразу.
  Когда нужен «весь ответ на команду», а последнего кадра не назвать,
  послать маяк: сервер обрабатывает команды по очереди, каждую до конца,
  поэтому ответ на `q_status` несуществующего типа приходит после всех
  кадров предыдущих команд (`Client.sync` в `test_halfa_training`). Кадры,
  которые сервер шлёт позже по таймеру (ходьба, выход из боя, `lcall` после
  драки), маяк не ловит: их ждать по имени через `until`.
- Фиксированное окно оправдано, только когда проверяется, что за это время
  ничего не пришло («карта не открылась, никто не сдвинулся»).
- `cmdAck` у клиента строго FIFO, ровно один на команду из `EXPECTS_ACK`
  (`PROTOCOL.md` §7). Набор, который проверяет новую команду, проверяет и
  число ack: лишний или пропущенный вешает настоящий клиент молча.
- Комната шлёт свой трафик (респаун, край войны, ходьба мобов). Фильтровать
  нужные кадры (`only(frames, "faAim", "faShot")`), а не требовать, чтобы
  других не было.

**Лог сервера.** Вывод сервера собирается потоком в список. В `finally`:
`Traceback` в логе это провал набора, даже если все проверки зелёные; при
любом провале хвост лога идёт в `fails`.

## Случайность и время

- Бой случаен по-настоящему. Проверять форму (каждый выстрел внутри пары
  `faShot`, урон в пределах оружия, опыт по формуле), а не запись
  конкретного боя. Цикл «стрелять, пока не умрёт» с пределом попыток лучше
  расчёта на число выстрелов.
- `LAVA_SEED` делает прогон повторяемым, но не защищает от смены формулы.
  После правки шансов набор может стать хрупким: чинить сцену (ближе
  подойти, сильнее оружие, моб слабее), а не расширять допуск без причины.
- Набор ждёт игровые часы, а не процессор. Долгие паузы сокращать
  переменными сервера, а не ожиданием покороче в тесте: тест с коротким
  ожиданием просто начнёт падать под нагрузкой.

## Набор по данным (`data/`)

- Сверять таблицу с источником: с файлами клиента (`LAVA_RES`), вики
  (`data/wiki/`), кодом сервера (`travel.rock_for` и т.п.), чтобы таблица и
  код не разошлись.
- Если таблицу строит скрипт (`data/build_*.py`), проверить, что файл на
  диске равен выводу скрипта.
- Число, которое должно уменьшаться (вроде 20 отрезанных посёлков в
  `test_borders`), фиксируется точно: расти ему нельзя.
- Если в наборе есть известное падение, оно записано в
  `tools/known_failures.txt` с причиной и шаблоном вывода. Добавлять туда
  строку, чтобы прогон стал зелёным, нельзя: только решение, которое ещё
  не принято.

## Запуск и отчёт

- Свой набор: напрямую, потом через запускалку
  `tools\run_suite.ps1 -Out <папка> -Res <client\res> -Only test_x`.
  Проверить, что проверки видны в `<папка>\test_x.jsonl` и `report.html`.
- После правки сервера: `-Affected` (наборы, которые исполняли изменённые
  функции; нужна карта `tools/impact_map.json`, её пишет `-RecordMap`).
- Перед PR: всё, что затронуто; перед большим слиянием весь прогон
  `-Jobs 8`. Упавший под нагрузкой набор перегнать один, прежде чем считать
  падение настоящим.
- Самый долгий набор задаёт длину всего прогона (`FIRST` в
  `tools/suite.py`). Новый долгий набор думать, как сократить, до того, как
  он станет самым долгим.

## Перед PR

- Docstring объясняет, что и почему проверяется.
- Импорт `check, fails` из `testkit`, заголовки `# --- ... ---` над тестами.
- Подписи читаются как правила, `want` выведен из правила.
- Свой порт, `LAVA_POLICY_PORT="0"`, своя база, у каждой переменной
  комментарий.
- Ни одного `time.sleep` там, где можно дождаться кадра.
- Набор зелёный отдельно и через запускалку, в `.jsonl` столько строк,
  сколько проверок.
- Новый набор упомянут в README, если он открывает новую механику.
