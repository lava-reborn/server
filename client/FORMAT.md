# Формат релиза клиента

Этот файл — договор между тремя сторонами: сборщиком релиза
(`client/build.py`), публикатором на сервере (`client/publish.py`) и
лаунчером (`launcher/Release.cs`, `launcher/Sync.cs`). Меняется формат —
меняются все трое, и номер формата в первой строке документа растёт.

## Где что лежит

Всё, что качает лаунчер, лежит под одним адресом, дальше он называется ROOT:

    https://lava-reborn.ru/download/client/        (снаружи)
    /opt/lava-site/download/client/                 (на сервере)

    ROOT/
      current.txt                  указатель на действующий релиз; подписан ключом ресурсов
      manifests/<serial>.txt       список файлов релиза; не меняется после записи
      store/<aa>/<sha256>          содержимое файла; имя — его sha256, aa — первые два знака
      launcher/<version>.exe       сборка лаунчера
      launcher/<version>.txt       заявление о сборке; подписано ключом лаунчера

Раздаёт nginx сайта: папка `/opt/lava-site/download` уже смонтирована в него
как `/download/`. Отдельной настройки для клиента не нужно.

## Общие правила

- Текст — UTF-8 без BOM, строки через LF, последняя строка тоже кончается LF.
- Хэш — sha256, 64 строчных шестнадцатеричных знака.
- Размер — число байт, десятичное, без знака.
- Путь — относительно папки `res`, через `/`, с регистром как в оригинале.
  Каждая часть пути состоит только из `A-Z a-z 0-9`, пробела и `. _ ( ) -`:
  этим знакам хватает всех имён оригинала, а Python и C# не могут разойтись
  в регистре и длине строки только из ASCII. Ещё запрещено: пустые части,
  `.` и `..`, часть, которая кончается точкой или пробелом (Windows их
  отрезает, и два пути становятся одним файлом), имена устройств Windows
  (`con`, `prn`, `aux`, `nul`, `com0`–`com9`, `lpt0`–`lpt9`, `conin$`,
  `conout$`, с расширением или без), первая часть `.lava`, путь длиннее 150
  знаков.
- В одном релизе запрещены два пути, которые отличаются только регистром
  (Windows их не различает), и файл, который одновременно служит папкой
  другого пути. Одни и те же правила проверяют `build.py`
  (`check_path`, `check_tree`), `publish.py` и лаунчер (`Manifest`).

## Подписанный документ

Подписанный документ — это тело и последней строкой подпись:

    <тело, каждая строка кончается LF>
    sig <keyid> <base64>

Подпись — RSASSA-PKCS1-v1_5 с SHA-256 над телом байт в байт: всё до начала
строки `sig`, включая LF перед ней. Ключи RSA, 3072 бита, открытая экспонента
65537. `keyid` — первые 16 знаков sha256 от модуля ключа, записанного
беззнаковым big-endian без ведущих нулей.

Строка `sig` одна и стоит последней. Документ с чем-то после неё отвергается.

## Указатель current.txt

    lava-pointer 1
    serial 1791260000
    created 2026-10-06T12:00:00Z
    manifest <sha256> <size> manifests/1791260000.txt
    launcher 3 <sha256> <size> launcher/3.exe
    sig <keyid> <base64>

Подписан ключом ресурсов. Порядок строк именно такой; строки `launcher`
может не быть, тогда лаунчеры себя не обновляют.

- `serial` — номер релиза, целое число. Строго растёт: публикатор берёт
  секунды Unix в момент публикации, но не меньше прежнего номера плюс один.
  Откат на прежний набор файлов — это новый релиз с новым номером.
- Лаунчер помнит наибольший номер, который принял, и отвергает указатель с
  меньшим. Так нельзя подсунуть старый подписанный релиз.
- `manifest` — хэш, размер и путь списка релиза. Сам список не подписан:
  его подлинность доказывает хэш в подписанном указателе.
- `launcher` — версия, хэш, размер и путь действующей сборки лаунчера.

Указатель меняется одной операцией: запись во временный файл и rename. Пары
файлов, которые могли бы разойтись, нет: подпись внутри.

## Список релиза manifests/<serial>.txt

    lava-manifest 1
    serial 1791260000
    source 9f0e6660a42...
    files 29836 2179741234
    <sha256>\t<size>\t<path>
    ...

- `source` — коммит репозитория, из которого собран релиз.
- `files` — число файлов и их общий размер; лаунчер сверяет их со строками.
- Строки файлов разделены табуляцией и отсортированы по пути (порядок байтов
  UTF-8). Один и тот же файл может стоять под несколькими путями: в хранилище
  он лежит один раз.
- В релизе ровно те файлы, которые получает игра. Лаунчер не отдаёт игре ни
  одного файла, которого здесь нет.

## Заявление о сборке лаунчера launcher/<version>.txt

    lava-launcher 1
    version 3
    sha256 <sha256 файла exe>
    size 22563328
    created 2026-10-06T12:00:00Z
    sig <keyid> <base64>

Подписано ключом лаунчера. Лаунчер ставит новую сборку, только если подпись
сошлась с вшитым ключом лаунчера, хэш и размер совпали со скачанным exe и
версия больше его собственной. Версия — целое число из `launcher/VERSION`.

## Хранилище

`store/<aa>/<sha256>` — файл ровно с этим содержимым. Файлы в хранилище не
перезаписываются: другое содержимое — другое имя. Публикатор кладёт новый
файл через временное имя и проверяет хэш до переименования.

## Ключи

| Ключ | Подписывает | Закрытая часть | Открытая часть |
|---|---|---|---|
| ресурсов | `current.txt` | `/opt/lava-ci/client/resource.pem` на проде, только root | `client/keys/resource.keys` |
| лаунчера | `launcher/<v>.txt` | у владельца, вне репозитория и вне OneDrive | `client/keys/launcher.keys` |

Файл `.keys` — строка на ключ: `<keyid> <e> <n в hex>`. Строки с `#` —
комментарии. Действуют все перечисленные ключи; так ключ меняется без
разрыва: новый лаунчер несёт оба, старый ключ убирают, когда все обновились.
`build.ps1` вшивает ключи в лаунчер при сборке.

Закрытый ключ — PEM, PKCS#1 (`RSA PRIVATE KEY`) или PKCS#8 (`PRIVATE KEY`)
без пароля. `client/lavasig.py genkey` делает такой и печатает строку для
`.keys`.

## У игрока

    <папка игры>/
      LavaReborn.exe
      res/                       файлы игры ровно как в релизе
      .lava/
        current.txt              последний принятый указатель
        manifest.txt             его список
        index.tsv                проверенные файлы: путь, размер, время, sha256
        staging/                 скачанное, но ещё не поставленное
        replaced/<время>/...     файлы, которые лаунчер заменил, не зная их

`index.tsv` — кэш проверки: файл с тем же размером и временем изменения, что в
индексе, при запуске заново не хэшируется. Всё, что игра загружает, лаунчер
всё равно проверяет по хэшу в момент отдачи.
