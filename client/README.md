# Клиент: релизы и обновления

Лаунчер ставит игру целиком с нашего сервера и держит её ровно такой, какой
её описывает подписанный релиз. Релиз собирается и публикуется шлюзом при
каждой выкатке сервера, поэтому клиент и сервер всегда меняются вместе. Новый
лаунчер шлюз тоже собирает и подписывает сам, когда выкатка меняет его код:
версию руками никто не поднимает. Точный формат всех файлов описан в
[FORMAT.md](FORMAT.md).

## Как это устроено

```
 репозиторий (main)
   патчи, списки, генераторы, код лаунчера
        │ PR слит
        ▼
 CI на раннере lava-prod
        │ дерево кода по SSH
        ▼
 шлюз на проде
   4b. client/build.py в контейнере: оригинал + патчи
       (сеть выключена, всё кроме вывода только на чтение)
   4c. лаунчер менялся? launcher/build.sh в контейнере Mono,
       номер = опубликованный + 1
   5-9. бэкап, подмена, проверка здоровья сервера
   9b. таблица строк релиза == таблица сервера?
       publish.py: файлы в хранилище, список, подпись ────► /download/client/
   9c. заявление о лаунчере, подпись ключом лаунчера ───►    current.txt (подписан)
                                                              manifests/<N>.txt
                                                              store/<aa>/<sha256>
                                                              launcher/<v>.exe, .txt
                                                            /download/LavaReborn.exe
        │
        ▼
 лаунчер игрока при каждом запуске
   указатель: подпись, номер не меньше прежнего
   новый лаунчер? заявление, подпись, хэш → заменить себя → перезапуск
   список релиза: хэш из указателя
   файлы: размер и время по индексу, хэш для остального → докачать → поставить
   игра: каждый файл хэшируется при отдаче; чего нет в релизе — не отдаётся
```

## Что здесь лежит

| Файл | Что это |
|---|---|
| `FORMAT.md` | формат указателя, списка, заявления, подписи, хранилища |
| `base.txt` | оригинальная игра пофайлово: хэш, размер, путь (29 832 файла) |
| `remove.txt` | файлы оригинала, которые игрокам не нужны |
| `extra.txt` | наши крупные файлы, которые лежат только в хранилище сервера |
| `files/` | наши небольшие файлы, в git как есть |
| `objects/` | свои объекты локаций: картинки и `manifest.json`, сборка делает из них файлы спрайтов ([objects/README.md](objects/README.md)) |
| `keys/` | открытые ключи, которые вшиваются в лаунчер |
| `build.py` | сборщик релиза; на сервере работает в контейнере шлюза |
| `publish.py` | публикатор; на сервере ставится в `/opt/lava-ci/client/` и держит ключ |
| `lavasig.py` | подпись RSA на чистом Python: ключи, подпись, проверка |
| `devserve.py` | стенд разработчика: весь конвейер на одной машине |
| `test_client.py` | тесты сборщика, публикатора и подписи, гоняются в CI |

Генерируемые файлы релиза собираются тем же кодом, что и раньше:
`main.swf` — `tools/widescreen.py` по оригиналу, `database/texts.xml` —
`tools/export_texts.py`, `database/locations.xml` — `server/map_labels.py`,
`hints/hints.xml` — пустой документ. Плитки карты `globalmap/full/<n>.jpg`, на
которых нарисованы квадраты снятых мест (клетки `data/retired.json` и
`data/map_cells.json`), — `server/map_cells.py`: квадраты закрашены, остальные
блоки плитки байт в байт оригинальные. В отчёте сборки это строки
`generated: ... globalmap/full/<n>.jpg` и `map: N squares and M caption boxes
painted over in K tiles`. Свои объекты локаций из `client/objects/` —
`tools/custom_objects.py`: каждый становится файлом
`locations/libs/sprite/<id>.swf` (или `locations/libs/background/<id>.swf`),
в отчёте это строки `object: ...` и `objects: N from client/objects/`. Объект,
чей файл есть в оригинале или в `extra.txt` хотя бы в другом регистре,
останавливает сборку. На сервере отчёт сборки уходит в журнал выкатки; в
отчёт выкатки попадают первые четыре строки публикации (`client: since ...:
N changed` и до двух путей).

## Кто что делает

- **Любой разработчик** выпускает правку клиента или лаунчера обычным PR:
  патч в `tools/widescreen.py`, подпись карты в `data/map_labels.json`,
  квадрат на карте в `data/map_cells.json`, файл в `client/files/`, код в
  `launcher/`. После слияния в main она уходит к
  игрокам сама.
- **Шлюз** собирает и подписывает релиз ключом ресурсов, а новый лаунчер —
  ключом лаунчера. Оба ключа лежат только на сервере.
- **Владелец** держит root на сервере и запасной ключ лаунчера. Он заливает
  крупные файлы, делает первую установку, откат клиента отдельно от сервера
  и, если шлюз не может выпустить лаунчер, выпускает его вручную.

Слитый PR теперь становится программой, которую запустят у себя все игроки.
Право слияния в main давайте только тем, кому это доверяете.

## Выпустить правку клиента

1. Сделайте правку: патч в `tools/widescreen.py`, правку в
   `data/map_labels.json` или `data/map_cells.json`, или файл в
   `client/files/<путь под res>`.
2. Проверьте локально: `python3 client/test_client.py` и тесты самого патча
   (`tools/test_widescreen.py`). Увидеть игру с правкой можно на стенде
   разработчика (ниже).
3. Отправьте PR. Правку, которой нужен и новый сервер, и новый клиент,
   делайте одним PR: шлюз выкатит их вместе.
4. После слияния CI выкатит сервер и опубликует релиз. В отчёте выкатки
   будут строки `client:` с номером релиза и списком изменённых файлов.
5. Игроки получат правку при следующем запуске лаунчера. Кто сидит в игре во
   время выкатки, получит её после перезапуска.

## Добавить, заменить или убрать файл игры

- **Небольшой файл** положите в `client/files/` по его пути под `res/`.
  Файл с тем же путём из оригинала будет заменён.
- **Крупный файл** заливает владелец. Он копирует файл на сервер и кладёт его
  в хранилище:

  ```
  python3 /opt/lava-ci/client/publish.py add --root /opt/lava-site/download/client FILE
  ```

  Команда печатает хэш и размер. Строку `хэш TAB размер TAB путь` добавляют в
  `extra.txt` обычным PR.
- **Убрать файл оригинала**: впишите его путь в `remove.txt`. У игроков файл
  останется на диске, но игре он отдаваться не будет.
- **Свой объект для локаций** (картинка или анимация): папка
  `objects/<id>/` и запись в `objects/manifest.json`, порядок в
  [objects/README.md](objects/README.md).

## Новый лаунчер

Лаунчер выпускает шлюз, отдельного шага нет.

1. Поменяйте код в `launcher/` обычным PR. Проверьте его на Windows
   (`launcher\test\run.ps1`) и сборку так, как её делает шлюз (раздел
   «Тесты»).
2. При выкатке шлюз считает хэш всего, из чего сделан exe: `launcher/*.cs`,
   `launcher/build.sh`, картинки и фильмы из `launcher/assets/`,
   `client/keys/*.keys`, проектор Flash, адрес сервера и образ сборки. Если
   хэш тот же, что у опубликованного лаунчера, в отчёте будет
   `launcher: unchanged, version N`, и игроки ничего не качают.
3. Если хэш другой, шлюз до бэкапа собирает exe по `launcher/build.sh` в
   контейнере Mono без сети и даёт ему номер на единицу больше
   опубликованного. Не компилируется или в `client/keys/` нет ключей этого
   сервера — выкатка останавливается целиком, ни сервер, ни клиент не
   меняются, ошибки компилятора в логе выкатки.
4. После выкатки и релиза шлюз подписывает заявление о сборке ключом
   лаунчера, переподписывает указатель и кладёт exe по ссылке сайта, прежний
   остаётся как `LavaReborn.exe.prev`. В отчёте строки
   `launcher: launcher N published ...`.
5. Лаунчеры игроков заменят себя при следующем запуске.

Если публикация лаунчера не удалась, сервер и релиз остаются выкаченными, а в
отчёте будет `launcher: NOT PUBLISHED` с причиной. Игроки остаются на прежнем
лаунчере, следующая выкатка попробует снова.

### Аварийный выпуск ключом владельца

Нужен, только если шлюз не может выпустить лаунчер (ключ сервера пропал или
утёк, шлюз сломан). Работает, пока ключ владельца остаётся в
`keys/launcher.keys`.

1. Узнайте номер опубликованного лаунчера (`publish.py status`, раздел
   «Обслуживание») и прибавьте единицу.
2. Соберите и подпишите:

   ```
   powershell -ExecutionPolicy Bypass -File launcher\build.ps1 -Build <N> -SignKey C:\Users\<вы>\.lava-keys\launcher.pem
   ```

   Получатся `dist\LavaReborn.exe` и подписанное заявление `dist\<N>.txt`.
3. Опубликуйте:

   ```
   bash deploy/client/publish_launcher.sh dist/LavaReborn.exe dist/<N>.txt
   ```

   Скрипт проверяет подпись на сервере, переподписывает указатель и кладёт
   exe по ссылке сайта. Следующая выкатка, которая поменяет код лаунчера,
   выпустит `<N>+1` уже сама.

## Ключи

| Ключ | Где закрытая часть | Открытая часть |
|---|---|---|
| ресурсов | `/opt/lava-ci/client/resource.pem` на проде, делает `install.sh` | `keys/resource.keys` |
| лаунчера (шлюза) | `/opt/lava-ci/client/launcher.pem` на проде, делает `install.sh` | `keys/launcher.keys` |
| лаунчера (запасной) | у владельца, например `C:\Users\<вы>\.lava-keys\launcher.pem` | `keys/launcher.keys` |

- **Запасной ключ владельца** делается один раз:
  `python3 client/lavasig.py genkey C:/Users/<вы>/.lava-keys/launcher.pem`.
  Команда печатает строку для `keys/launcher.keys`. Храните ключ вне
  репозитория и вне OneDrive, вторую копию на флешке. Пока его строка в
  `keys/launcher.keys`, им можно выпустить лаунчер в обход шлюза.
- **Закрепить ключи.** Ключи вшиваются в лаунчер из репозитория, а дописать
  строку туда может любой, у кого есть право слияния. Поэтому рядом со своим
  ключом держите `pinned.txt` со строками `resource <id>` и
  `launcher <id>` (по строке на каждый ключ). `build.ps1` сверяет ключи
  репозитория с этим списком и отказывается собирать при расхождении;
  осознанная смена ключа — с `-AcceptKeys`, после чего обновите
  `pinned.txt`. Шлюз проверяет только, что ключи этого сервера в списке есть:
  лаунчер, который их не знает, отказался бы от всех следующих обновлений.
- **Сменить ключ ресурсов** (плановая замена или утечка). Старые лаунчеры
  проверяют указатель только старым ключом, поэтому порядок такой:
  1. На сервере сделайте новый ключ рядом со старым:
     `python3 /opt/lava-ci/client/lavasig.py genkey /opt/lava-ci/client/resource-new.pem`.
  2. Допишите его строку в `keys/resource.keys` второй строкой и слейте PR:
     шлюз сам выпустит лаунчер с обоими ключами. Указатель с ним шлюз ещё
     подписывает старым ключом, так что все лаунчеры его примут и обновятся.
  3. Когда игроки обновились, переименуйте `resource-new.pem` в
     `resource.pem`, затем следующим PR уберите старую строку из
     `resource.keys`. В обратном порядке шлюз откажет: в дереве не будет
     ключа, которым он подписывает.

  Если старый ключ утёк, тот, кто им владеет, может подписывать указатели для
  ещё не обновившихся лаунчеров, пока они не обновятся. Поэтому при утечке
  шаги 1–3 делайте сразу, одним днём.
- **Пропал или утёк ключ лаунчера шлюза** (например, сервер собран заново).
  Лаунчеры игроков знают только старый ключ шлюза и ключ владельца, поэтому
  новый ключ шлюза приносит лаунчер, подписанный владельцем:
  1. `install.sh` сделает новый ключ и напечатает его строку. Поставьте
     `CLIENT_LAUNCHER=0` в `gate.conf`: пока строки нет в
     `keys/launcher.keys`, шлюз останавливает любую выкатку.
  2. В ветке впишите новую строку в `keys/launcher.keys`, при утечке уберите
     старую. Соберите из этой ветки аварийный лаунчер ключом владельца и
     опубликуйте его (раздел «Аварийный выпуск»).
  3. Слейте ветку, перезапустите `install.sh` и верните `CLIENT_LAUNCHER=1`.
     Шлюз выпустит ещё одну сборку уже своим новым ключом.
- **Пропал ключ владельца**: сделайте новый и замените его строку в
  `keys/launcher.keys` обычным PR, шлюз выпустит лаунчер с ней. Перезапустите
  `install.sh`, чтобы сервер принимал заявления, подписанные новым ключом.
- **Пропали оба ключа лаунчера**: самообновление остановится. Сделайте новые
  ключи и выпустите лаунчер с ними. Игрокам придётся один раз скачать его с
  сайта вручную.

## Первая установка на сервере (один раз, владелец)

1. **До слияния ветки** обновите шлюз. Скопируйте `deploy/` и `client/` в
   `/root/lava-ci-src` и запустите
   `bash /root/lava-ci-src/deploy/remote/install.sh --pubkey '<ключ CI>'`
   (строка ключа есть в `authorized_keys`, с пометкой lava-ci). Он сам
   допишет `client` в `ALLOWED_DIRS` в `gate.conf`: без этого шлюз откажет
   любой выкатке дерева с папкой `client/`, даже с выключенным релизом.
   Ещё он скачает образ Mono для сборки лаунчера (по хэшу образа).
2. `install.sh` сделает ключ ресурсов и ключ лаунчера шлюза и напечатает их
   строки. Впишите первую в `keys/resource.keys`, вторую — в
   `keys/launcher.keys` рядом с ключом владельца, обе — в свой `pinned.txt`.
3. Положите проектор Flash туда, откуда шлюз берёт его для лаунчера (в git
   его нет):

   ```
   scp tools/flash/fp32_sa.exe root@159.194.247.90:/opt/lava-ci/client/fp32_sa.exe
   ```

   Папка `/opt/lava-site/download`, куда шлюз кладёт exe для сайта, должна
   принадлежать root и не быть ссылкой: `chown root:root` и `chmod 755`.
4. Залейте оригинальную игру в хранилище:

   ```
   scp "LAVA.zip" root@159.194.247.90:/root/LAVA.zip
   python3 /opt/lava-ci/client/publish.py import-base --root /opt/lava-site/download/client \
       --base /root/lava-ci-src/client/base.txt --zip /root/LAVA.zip --prefix LAVA/res/
   ```

   Все 29 832 файла должны сойтись с `base.txt`; в хранилище ляжет 16 971
   уникальный файл, около 1,25 ГБ.
5. В `/opt/lava-ci/gate.conf` добавьте строки `CLIENT_RELEASE=1` и
   `CLIENT_LAUNCHER=1` и сразу слейте ветку в main. Не раньше: с включённым
   релизом выкатка дерева без `client/build.py` не пройдёт.
6. Первая выкатка опубликует первый релиз и лаунчер версии 1.
7. Нынешние лаунчеры у игроков сами себя не заменят: они увидят новую сборку
   на сайте и попросят скачать её. Это последнее ручное скачивание.

## Откат

- **Сервер и клиент вместе**: выкатите прежний коммит обычным путём. Шлюз
  соберёт релиз из прежнего кода, и лаунчеры вернут файлы.
- **Только клиент** (на сервере, root):

  ```
  python3 /opt/lava-ci/client/publish.py rollback --root /opt/lava-site/download/client \
      --key /opt/lava-ci/client/resource.pem [--to <номер>]
  ```

  Указатель получит новый номер и назовёт прежний список. Таблица строк при
  этом разойдётся с сервером, если она менялась, поэтому так откатывают
  только правки клиента.
- **Лаунчер**: номер версии только растёт. Чтобы вернуть прежнюю сборку,
  откатите её код в `launcher/` обычным PR: шлюз соберёт её с большим
  номером и выпустит.

## Что проверяет лаунчер у игрока

- **При запуске** сверяет размер и время всех файлов со своим индексом, это
  около секунды. Если что-то не сошлось, считает хэш этого файла и при
  расхождении скачивает его заново.
- **При отдаче в игру** хэширует каждый файл. Не сошёлся — восстанавливает
  его из хранилища сервера до того, как отдать.
- **Отдаёт только файлы релиза.** На любой другой путь отвечает 404.
- **Чужие файлы не выбрасывает.** Файл, который он заменяет, не зная его,
  переносит в `.lava/replaced/<время>/`. Хранит пять последних таких папок.
- `LavaReborn.exe --verify` пересчитывает хэши всех файлов. На машине
  владельца это около 2 секунд.

Если сервер обновлений не отвечает, подпись не сошлась, обновление не
скачалось или новый лаунчер не встал, лаунчер пускает в игру на последнем
принятом релизе, если тот цел, и пишет почему. Если игра ещё ни разу не была
установлена, играть нельзя, и лаунчер предлагает повторить.

## Что где хранит публикатор

На сервере публикатор пишет в две папки. `/opt/lava-site/download/client` —
то, что раздаёт сайт; ей он не верит. `/opt/lava-ci/client/state` (только
root) — копии всего, что он подписал: указатель и списки релизов. Номер
следующего релиза, список, который переподписывает публикация лаунчера,
релиз для отката и то, что оставляет `gc`, берутся только оттуда. Поэтому
подмена файлов в раздаваемой папке не попадёт под подпись. Папки
раздаваемого дерева должны принадлежать root и не быть ссылками, иначе
публикатор ничего не пишет.

## Стенд разработчика

Весь конвейер на одной машине, с тестовыми ключами в `client/dev/` (папка не
попадает ни в git, ни на сервер):

```
python3 client/devserve.py --zip "LAVA.zip" --prefix LAVA/res/ --res /путь/к/своему/res
```

Если ваша копия игры не совпадает с `base.txt` байт в байт, добавьте
`--own-base`: эталоном станет ваша копия. Лаунчер для стенда:

```
powershell -ExecutionPolicy Bypass -File launcher\build.ps1 -Site http://127.0.0.1:8098 `
    -ResourceKeys client\dev\keys\resource.keys -LauncherKeys client\dev\keys\launcher.keys `
    -SignKey client\dev\keys\launcher.pem -Out dist\dev\LavaReborn.exe
```

## Тесты

| Что | Где идёт |
|---|---|
| `client/test_client.py` | CI, в общем прогоне |
| `tools/test_swfgen.py` | CI, в общем прогоне: файлы своих объектов, манифест, расстановка |
| `bash tools/flash_headless/run.sh <локация.xml>` | вручную, Linux или WSL с docker: настоящий Flash Player 32 рисует локацию со своими объектами, без окон и без сети ([tools/flash_headless/README.md](../tools/flash_headless/README.md)) |
| `launcher\test\run.ps1` | вручную на Windows: лаунчер ставит, обновляет, чинит, отказывает, заменяет себя; без окон |
| `launcher\test\check_netfx.ps1 <exe>` | вручную на Windows: exe, собранный шлюзом, работает на .NET Framework этой машины; без окон |
| `CLIENT_ORIG=<папка> CLIENT_PROJECTOR=<fp32_sa.exe> bash deploy/remote/test_gate.sh ...` | вручную, Linux с docker: шлюз собирает, проверяет, публикует и откатывает релиз и лаунчер |

Собрать лаунчер так, как его соберёт шлюз (Linux или WSL с docker, из корня
репозитория), и проверить его на Windows:

```
mkdir -p dist/mono
docker run --rm -v "$PWD:/src:ro" -v "$PWD/tools/flash/fp32_sa.exe:/projector.exe:ro" -v "$PWD/dist/mono:/out" \
    mono@sha256:34d816779b1248b5cfd095770b64ecbaf1798e2aca693a91c11a018dce9c7ad5 \
    bash /src/launcher/build.sh --out /out --build 1 --projector /projector.exe
powershell -ExecutionPolicy Bypass -File launcher\test\check_netfx.ps1 dist\mono\LavaReborn.exe
```

Последняя команда должна закончиться словами `0 failed`. Если сборка Mono
задела метод, которого нет в .NET Framework, здесь он и найдётся.

## Обслуживание

```
python3 /opt/lava-ci/client/publish.py status --root /opt/lava-site/download/client
python3 /opt/lava-ci/client/publish.py gc --root /opt/lava-site/download/client \
    --base /root/lava-ci-src/client/base.txt --extra /root/lava-ci-src/client/extra.txt [--dry-run]
```

Шлюз хранит восемь последних списков (`CLIENT_KEEP`). `gc` удаляет из
хранилища файлы, которые не нужны ни одному из них и не входят в оригинал.
