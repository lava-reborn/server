# Аудит загрузки и запросов — 28.10.2026

Локальные Changes; без коммита, пуша, CI и деплоя. Визуальную приёмку выполняет владелец.

## Решения

TestLauncher.exe использует существующие Theme.cs, hero.jpg, logo.png и lava.ico из игрового лаунчера. Это локальный тестовый режим: производственный updater и авторизация не подключались. Подготовка идёт в лаунчере, «Играть» доступна после ready. Flash открывает main.swf напрямую. Старый tester-start.swf с родной рамкой остаётся запасным входом для прямого запуска start.py.

Закрытие Flash сохраняет серверы. Закрытие лаунчера просит закрыть игру, позволяет сохранить отключение и завершает свои серверы. При занятом порте чужая готовность не принимается: каждый запуск имеет отдельный случайный идентификатор. Проверка готовности — максимум два раза в секунду, один запрос одновременно; после ready опрос прекращается. Полоса отражает этапы, а не предсказанное время.

Сохраняется только производная карта в state/map-cache.zip (~0,6 МБ). Проверяются SHA256 кода, плана и прочитанных исходных ресурсов. Обновление этих зависимостей или повреждение кэша вызывает однократную подготовку. Запись атомарна. Прочие обновления не требуют пересчёта карты. Ошибка сохранения кэша не мешает играть с уже подготовленной картой в памяти. Деньги, инвентарь и состояния квестов в этот ZIP не записываются. Новый кэш данных БД не вводился.

## Что обнаружено и исправлено

- Повреждённый DEFLATE внутри ZIP мог прервать подготовку: теперь кэш отвергается и строится заново.
- Ошибка удаления временного файла кэша могла перекрыть готовый результат: теперь только запись в журнал.
- Отмена до запуска HTTP могла ждать длительный таймаут: ожидание прерывается сигналом остановки.
- Занятый порт мог оставить backend в блокирующем диалоге ошибки, а лаунчер — прочитать ready другого экземпляра: введены проверка принадлежности и выход backend с ошибкой без модального окна.
- Ошибка запуска отсутствующего/повреждённого Flash показывается в статусе лаунчера.
- Исправлен разбор JoinStyle в LINESTYLE2 при извлечении рамки SWF; добавлены отдельные фикстуры для miter/end-cap.
- Исходник tools/TesterLauncher.cs был скрыт общим tools/* в .gitignore: добавлено точечное исключение, чтобы он оставался в Changes для будущего коммита. Бинарные файлы по-прежнему исключены.
- Убран доступ к частному _tiles: Served получил необязательный prepared_tiles, обычный вызов сохраняет поведение.
- Убрана лишняя оконная сортировка истории квестов. Группировка и коррелированный MIN используют существующий индекс (char_id, type, done_at, id). Сохранены выбор первой даты, развязка одинаковых дат по id, область персонажа и live-проверки действий.

Изменения не вводят миграций и не меняют списания/начисления. Это не гарантия отсутствия любых ошибок: PostgreSQL и производственный профиль нагрузки отдельно не проверялись.

## Замеры

Все измерения на одном локальном компьютере, изолированная синтетическая БД, без окна Flash. Контроль без кэша использует текущий painter/backend с отключённым дисковым кэшем, чтобы выделить его эффект; это не запуск исторического релиза целиком.

| Сценарий | До готовности backend |
| --- | ---: |
| Без дискового кэша, контроль | 60,46 с |
| Первый запуск с построением кэша | 61,12 с |
| Повторные полные запуски с кэшем | 3,71–3,78 с |

Медиана тёплого запуска 3,72 с: примерно в 16 раз быстрее контроля. Это подготовка серверов; не полное время входа и отрисовки Flash. При сохранённом лаунчере новый backend вообще не запускается.

Суммарное CPU-время backend/игрового/HTTP процессов: 63,09 с без кэша против медианы 5,00 с с кэшем. Сумма working set при ready: 384,4 против ~297–298 МиБ; это не пик, не уникальная физическая память и не оценка ёмкости прода. GUI/Flash исключены.

Повторное TCP-подключение до lenter: ~2,1–4,4 мс. Это только протокол, без пользовательского ввода и загрузки графики. Во всех контрольных переподключениях деньги и предметы совпали; backend остался работающим.

HTTP main.swf, 30 запросов до/после ревью: медиана 15,79 → 16,51 мс, p95 30,33 → 30,13 мс. Существенного ухудшения не обнаружено. Все ответы main.swf побайтно совпали (1 762 215 Б). Эксперимент TCP_NODELAY не применён: малой разницы медиан недостаточно для изменения серверной настройки.

Отдельный попарный SQLite-замер запроса истории, 10 000 строк, чередование старого/нового запроса, 7 повторов по 30 вызовов:

| Локация | До | После |
| --- | ---: | ---: |
| 36 | 0,340 мс | 0,228 мс |
| 102 | 0,259 мс | 0,171 мс |
| 49 | 0,332 мс | 0,218 мс |
| 127 | 0,377 мс | 0,248 мс |

Ускорение запроса ~33–35%, абсолютная экономия ~0,09–0,13 мс. Это не ускорение всей игры на треть. Существующий кратковременный снимок доступности уменьшает число SQL-запросов, но в локальном SQLite не всегда уменьшает суммарное время: дополнительные кэши и индексы без доказанной выгоды не добавлялись. Оплата/сдача по-прежнему проверяют актуальные данные.

## Приёмка вручную

1. Закрыть старую игру и лаунчер. Открыть dist/actual-tester-client/TestLauncher.exe (или Start.vbs).
2. Убедиться, что подготовка показана в лаунчере и «Играть» включается после готовности. Проверить оформление и отсутствие отдельной консоли.
3. Войти тестовым аккаунтом. Проверить портрет слева, выход на глобальную карту и возврат; отдельно полный сет Налётчика (все пять частей), движение и релог. Налётчик/Пустынник пока не подтверждён как ошибка данных, res=107/103 не менялись.
4. Закрыть только Flash, оставить лаунчер, снова нажать «Играть». Подготовка карты повторяться не должна. Проверить сохранение предметов/баланса и работу хоткеев.
5. Закрыть весь лаунчер и открыть снова: должен использоваться сохранённый кэш.
6. По желанию при закрытом лаунчере переименовать state/map-cache.zip: следующий запуск один раз готовит карту (~минута на измеренном компьютере), затем снова быстрые запуски. Не удалять tester.sqlite/accounts.csv.
7. У Саида проверить условия действующих P/ВНЖ и замену P на ВНЖ: предупреждение только о потере оставшихся дней, без обещания опыта. Действующий статус повторно не сдаётся.

После обновлений, меняющих карту/подготовку, однократная задержка ожидаема; после остальных — сохраняется кэш. При сомнениях расширение ресурсов сервера рассматривается по производственным замерам, а не заменяется обязательным переносом данных в кэш.
