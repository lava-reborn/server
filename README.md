# LAVA Online — сервер

Сервер для MMO **LAVA Online** (VR-Ocean, 2008–2018), восстановленный по
оригинальному клиенту и фанатской вики: бой, квесты, торговля, кланы,
транспорт, аукцион, банк, глобальная карта. Клиент — оригинальный, на Flash.
Игрок получает лаунчер, который ставит игру с сервера и обновляет её
([client/README.md](client/README.md)).

## Что нужно

- Python 3.12 и Docker с compose.
- Оригинальный клиент игры — папка `res/`, около 2 ГБ. Серверу из неё нужен
  срез примерно в 35 МБ: `locations/{static,deadloc,desert}/*.xml`,
  `database/mobs.xml`, `database/objects.xml`, `avatars/list.xml`. Тестам
  нужен тот же срез.
- Для игры на своей машине — Flash Player projector 32
  (`flashplayer_32_sa.exe`) в `tools/flash/`.

## Запуск на своей машине

```bash
./run.sh            # серверы и клиент
./run.sh servers    # только серверы
./run.sh stop
./run.sh log        # хвост logs/game.log
```

Путь к папке `res/` задаётся переменной `RES_WSL` в начале `run.sh`.
Серверы работают под Python из WSL. Регистрация — `http://127.0.0.1:8080/`.

## Развёртывание в Docker

```bash
cp .env.example .env            # указать LAVA_RES_DIR и LAVA_PUBLIC_HOST
docker compose up -d --build
docker compose logs -f game
docker compose down             # сервер сохраняет всех, кто в игре
```

Два сервиса из одного образа: `game` — игровой сокет (9775) и политика Flash
(843), `http` — страница регистрации, админ-панель `/admin` и `/status`.

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `LAVA_RES_DIR` | — | папка `res/`, монтируется только для чтения |
| `LAVA_PUBLIC_HOST` | `127.0.0.1` | адрес сервера, который видят игроки |
| `LAVA_GAME_PORT`, `LAVA_HTTP_PORT` | `9775`, `8080` | опубликованные порты |
| `LAVA_BIND` | `0.0.0.0` | интерфейс публикации портов |
| `LAVA_POLICY_PORT`, `LAVA_POLICY_PUBLIC_PORT` | `8430`, `843` | порт политики Flash в контейнере и снаружи |
| `LAVA_DB_URL` | пусто | адрес Postgres; пусто — SQLite в томе `lava-db` |
| `LAVA_ADMINS` | пусто | игровые логины через запятую с доступом к `/admin`; пусто — панели нет |
| `LAVA_ADMIN_HOURS` | `12` | сколько часов держится вход в панель |
| `LAVA_LOG_LEVEL` | `INFO` | `DEBUG` пишет в лог весь протокол |
| `LAVA_HTTP_RES` | `0` | раздавать ли `res/` по HTTP; держите `0` |
| `LAVA_SERVER_CHAT` | `0` | `1` — сервер пишет в чат причины отказов |
| `LAVA_BOSS_HOURS`, `LAVA_BOSS_TZ`, `LAVA_BOSS_STAY` | см. `.env.example` | часы появления боссов, часовой пояс, сколько минут босс стоит |
| `LAVA_WAREHOUSE_HOURS` | `20` | час прихода хозяина складов |
| `LAVA_NOOB_VALLEY_SAFE` | `0` | `1` — в Нубийской долине нет ПвП вне арены |
| `LAVA_SMTP_*`, `LAVA_MAIL_FROM`, `LAVA_SITE_URL` | пусто | почта игрокам: подтверждение адреса и сброс пароля |
| `LAVA_REGISTER_EMAIL` | `0` | `1` — без почты регистрация не проходит |

## База данных

По умолчанию — файл SQLite в томе `lava-db`. С `LAVA_DB_URL` сервер работает
с Postgres. Схема одна на обе базы (`SCHEMA` в `server/accounts.py`),
недостающие таблицы и колонки создаются при старте. Проверка на Postgres —
`server/test_storage_pg.py` с заданным `LAVA_DB_URL`; базе нужна своя,
одноразовая.

## Выкладка на сервер

```bash
LAVA_DEPLOY_HOST=user@host LAVA_RES_SRC=/path/to/res bash deploy/deploy.sh --with-data   # первый раз
LAVA_DEPLOY_HOST=user@host bash deploy/deploy.sh             # дальше: код, пересборка, рестарт
```

Перед рестартом игроки получают отсчёт (`--warn=SECONDS`, `--now` — без
него). `--data-only` обновляет только срез `res/`. Каталог на сервере —
`LAVA_DEPLOY_DIR`, по умолчанию `/opt/lava`. Файл `.env` на сервере
создаётся из `deploy/env.example` при первой выкладке и дальше не
перезаписывается. База лежит в томе docker, выкладка её не трогает.

## Админ-панель

`/admin` на HTTP-сервисе, вход игровым логином и паролем. Доступ — логинам
из `LAVA_ADMINS`. Учётки администраторов:

```bash
python3 tools/admin_account.py list
python3 tools/admin_account.py create NAME     # спросит пароль
python3 tools/admin_account.py delete NAME --yes
```

## Клиент и лаунчер

Релиз клиента собирается из оригинального `res/` и наших правок и
подписывается; лаунчер ставит его и проверяет по хэшам. Порядок выпуска,
ключи и сборка лаунчера — в [client/README.md](client/README.md), формат
файлов — в [client/FORMAT.md](client/FORMAT.md).

Новому серверу нужны свои ключи подписи и свой лаунчер с его адресом
(`launcher/build.ps1 -ServerHost ... -Site ...`): уже установленные
лаунчеры доверяют только тем ключам, с которыми собраны.

## Тесты

```bash
bash tools/run_suite.sh . /tmp/lava_suite 8                      # все наборы по 8 разом
bash tools/run_suite.sh . /tmp/lava_suite 8 --only test_combat   # выбранные
bash tools/run_suite.sh . /tmp/lava_suite 8 --affected           # затронутые правкой
```

Под Windows — `tools\run_suite.ps1 -Out D:\lava_suite -Jobs 8`. Итог — в
`summary.txt` и `report.html` папки результатов. Набор, зависящий от
времени, под нагрузкой может упасть; перед тем как считать падение
настоящим, его гоняют отдельно. `test_bootstrap` сверяет размер `main.swf`
и падает на другой копии клиента. Как устроены наборы — в
[TESTING.md](TESTING.md).

## CI/CD

[`.github/workflows/ci.yml`](.github/workflows/ci.yml) гоняет тесты на push
в `main` и на pull request, а после зелёных тестов на `main` выкладывает
код на сервер через шлюз из `deploy/ci/`. Тесты идут на раннерах GitHub
(бесплатно для публичного репозитория, все задачи сразу), выкладка на
self-hosted раннере с меткой `lava` на боевом сервере; переменная
репозитория `CI_TEST_RUNNER` (`["self-hosted","lava"]`) возвращает тесты
на него. Нужны секреты `ASSETS_SSH_KEY` (ключ шлюза, которому можно только
забрать ресурсы для тестов) и `DEPLOY_KNOWN_HOSTS`, окружение `production`
с правилом «только `main`» и секретом `DEPLOY_SSH_KEY` (ключ выкладки: его
получает только задача выкладки на `main`, ни одна ветка и ни один pull
request). Push в `main` —
это выкладка, поэтому работа идёт в ветках. Push, который меняет только
`README.md`, `TASKS.md`, `UNDONE.md`, `ROADMAP.md`, `PROTOCOL.md` или
`recon/`, прогона не запускает.

## Что где лежит

| Папка | Что там |
|---|---|
| `server/` | игровой сервер, HTTP-сервис, тесты |
| `data/` | таблицы игры в JSON и сборщики, которые их строят |
| `client/` | сборка, подпись и публикация релизов клиента |
| `launcher/` | лаунчер игрока (C#) |
| `tools/` | редактор локаций, экспорт строк, запуск тестов и прочее |
| `deploy/` | выкладка, compose, шлюз CI |
| `recon/` | разбор оригинального клиента |

Протокол клиент–сервер — [PROTOCOL.md](PROTOCOL.md).

## Правовая рамка

Восстановление сервера для мёртвой игры ради совместимости и сохранения —
обычная практика (MaNGOS, rAthena, L2J). Здесь только серверный код и
результаты анализа. Ассеты остаются у правообладателя. Данные с вики —
CC-BY-SA, при использовании указывать источник.

## Редактор границ глобальной карты

`LAVA_RES=/path/to/res python3 tools/map_editor.py` открывает редактор на
`127.0.0.1:8090`. Для изображений локаций нужен Pillow в Python редактора
(либо `--art-python /path/to/python-with-pillow`). Для проверок интерфейса нужен Node.js.
Исходная карта собирается из игровых ресурсов; служебные цвета рисуются только
в редакторе. В игровые текстуры эти цвета, сетка и предупреждения не попадают.

Начальный снимок — `data/boundary_editor_draft.json`. Редактируемая копия и её
исходная резервная копия находятся в `outputs/boundary-editor/`; сохранение
черновика не меняет игру. `--source` и `--workspace` позволяют продолжить другую
сохранённую работу. Редактор поддерживает воду, стены, скалы, побережье,
патрули и тоннели, раздельную видимость цветов, прозрачность, перемещение
средней кнопкой мыши, родные изображения и гексы, отдельные позиции мобов для
каждой клетки и сравнение с установленным снимком.

Игра читает только экспортированный `data/boundary_world.json`. Новый экспорт:
`python3 tools/export_boundary_world.py --draft /path/to/working.json --out /path/to/boundary_world.json`.
Экспорт и установка — отдельные действия. `LAVA_BOUNDARY_WORLD=off` позволяет
проверить исходный мир; путь к другому manifest включает конкретный снимок.
У каждой новой клетки собственная игровая привязка, бой и обитатели; графика
и исходные шаблоны используются повторно. Вода и стены непроходимы; у скал
и побережий дополнительно учитывается родная геометрия. Выходы соединяют
совместимые доступные стороны. У внутренних тоннелей нет выхода на глобал.
Неизвестная старая цель входа 163 Абу-Хамеда остаётся отключённой.

Квесты мастеров горных троп Хальфы, Донголы и Абу-Хамеда временно закрыты:
их нельзя взять или сдать, включая разборку и сборку оружия. Определения
заданий, уже взятые задания и сами NPC сохранены для последующего включения.
Исходные тёмно-красные значки троп в игре сохраняются; цвета редактора
используются только для обозначений в редакторе.

Бонусы опыта от прописки/ВНЖ, предметов и выходных складываются, но общий
множитель ограничен x2 (+100%). Избыток не начисляется; отрицательные
эффекты применяются после ограничения. Предел указан в описаниях предметов,
активных бафов опыта, статусов и заданий на оформление прописки/ВНЖ.

Перед применением INTUX, если положительные бонусы после замены текущего
INTUX превысят x2, штатное окно спрашивает подтверждение: «ОК» / «ОТМЕНА».
При сумме ровно x2 дополнительного окна нет. Отмена сохраняет предмет и ОД.
Сервер проверяет подтверждение для конкретного предмета, сессии и состояния
персонажа; при изменении бонусов до окончания применения проверяет предел
повторно. Старый клиент без окна не может потратить INTUX с превышением.
Для CI добавлены серверные регрессии подтверждения и атомарного списания
на SQLite/Postgres, а также проверки собранных клиентских обработчиков.

Временно запрещены к новой выдаче и использованию ровно три дополнительные
модели MP-40: 26692 (11), 26695 (15), 26698 (17). Сервер отклоняет экипировку,
перезарядку и атаку, включая уже надетый экземпляр и завершение прицеливания,
с сообщением «Это оружие временно недоступно для использования». Отказ не
расходует ОД, патроны или прочность. Предметы не объявлены выведенными из игры:
владельцы, характеристики, состояние и серийные номера сохраняются.

Обычный случайный слот экипировки использует явный каталог
`data/mob_equipment_release.json`: каждому ID сопоставлены реально продающие
его NPC и локации. При старте проверяется и текущий ассортимент; одних только
названия и цены из общего A-каталога недостаточно. Ограничение выше 17 уровня
сохраняется. Из обычного дропа также исключены неподтверждённые A-шаблоны,
которых нет в этом каталоге; это не запрещает использование уже имеющихся АК
26242 или шаблона 45278. Квестовые, коллекционные, ивентовые модели,
излучатели и обычный MP-40 уровня 9 с его модификациями не включены в запрет.
«Пустынник» 10629–10633 продаётся NPC 1166 в Абри (187) и остаётся в дропе.
Пул вооружения мобов, характеристики оружия и брони не менялись.

Новые патрули — только Магриб 19 уровня: удвоенное HP обычного бойца,
существующий голдовый пулемёт с модификацией на урон. Перехват возможен только
над клеткой с патрулём, с учётом снижения шанса транспортом. Он использует
уже стоящих бойцов, не создавая дополнительный отряд. Крокодилы берегов
Хальфы/Абри/Донголы/Абу-Хамеда имеют уровни 4/11/12/17 и обычные параметры
защиты и живучести своего уровня. Их естественная атака «Клыки» использует
урон, стоимость и время удара голдового ножа; для нечётных уровней значения
интерполируются между соседними ножами. И те и другие дают обычный опыт
своего уровня без предметов и денег. Квестовые животные прежних локаций
сохраняют свои параметры и добычу. В Эдеме и Нубии новые группы не размещаются.

Старые лагерные патрули ограничены одним квадратом 3×3: центр, существующая
локация ПБ и семь патрульных клеток. У Пиратов квадрат сдвинут на ряд к северу,
чтобы включить ПБ и не ставить патрули в реку. ПБ не расширяет квадрат. Удалены только строки
патрулей за его пределами; сами ПБ, квестовые NPC и оставшиеся позиции сохранены.
У Нубийского лагеря (34) и Аванпоста Северного Альянса (168) остаётся прежний
состав «центр + 8»: отдельный ПБ для них не создаётся.
Хальфа и Абу-Хамед повторяют полную форму горных троп Донголы. Существующие
входы и комнаты мастеров перенесены внутрь схемы; два нижних подхода используют
одну исходную комнату мастеров, как в Донголе, без копирования NPC.

CI проверяет исходные таблицы как фиксированный набор прежних сценариев и
отдельно весь установленный снимок (`tools/test_boundary_snapshot.py`):
геометрию, реальные взаимные переходы, отдельные привязки и сохранность
типов/гексов всех прежних обитателей. Команды для отдельных отчётов:
`tools/audit_boundary_runtime.py`, `tools/audit_boundary_population.py` и
`tools/audit_boundary_access.py`; у каждой есть `--help`.
