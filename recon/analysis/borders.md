## 0. Главное в десяти строках

1. **Непроходимости как отдельного слоя данных в LAVA не было вообще.**
   Клиент не знает о рельефе глобальной карты ничего (§3), а сервер решал
   вопрос единственным способом: у клетки есть локация, и локация сама
   перечисляет, в какие стороны из неё можно выйти (узел `outzones`).
2. **Стена — это клетка, у которой в `outzones` нет кода нужной стороны.**
   Ничего больше. Кодировка: `1` = левый край сетки, `2` = верхний,
   `3` = правый, `4` = нижний; `a`/`b` — внутренние двери (§2).
3. **Клетка, которой сервер не назвал файл, всегда проходима во все четыре
   стороны.** Все одиннадцать шаблонов `res/locations/desert/00NN.xml` несут
   полный набор кодов `1234` (§6). То есть «пустыня» по определению открыта.
4. В `res/locations/static` лежит **полный набор скальных плиток**: четыре
   стороны по два варианта, четыре угла, четыре тупика-кармана, два прохода,
   остров, озеро — 21 файл с `fn="B_*"` плюс безымянный `4`. Все `war=1`,
   `library="Mountains"`, заголовок «Скалы» (§1).
5. **Набор ставился на карту поклеточно.** Доказательство — три файла
   `NoPvP_UpSide1/2` (178, 179) и `NoPvP_LeftSide2` (180): побайтово та же
   геометрия, что у 15, 16 и 2, отличие только `pvp="0"`. Такие копии имеют
   смысл ровно в одном случае — как стена вокруг стартовой бесPvP-зоны (§7).
6. **Инверсии координат нет.** `pos = y*width + x`, `1`=W, `2`=N, `3`=E,
   `4`=S — ровно то, что сервер считает сейчас. Доказано на данных, а не по
   именам файлов (§4). Имена плиток при этом указывают на **открытую**
   сторону, а не на стену, поэтому «B_LeftSide» — это восточная стена.
7. **Прямоугольник `5833..6305 × 1600..2110` — не граница мира, а описанный
   прямоугольник 414 подписей** `res/database/locations.xml` (§8). На его
   западном и северном краю подписи прямо говорят «Западные Предгорья» и
   «Северные Предгорья», и локации там наружу действительно не выпускают.
   На восточном и южном краю локации наружу **выпускают** — мир там
   продолжается.
8. **Нынешний рельеф по шероховатости фотографии противоречит клиенту.**
   Он закрывает 6130 из 241703 клеток (2.54 %), и каждая из них, если в неё
   войти, откроется обычной пустошью с четырьмя выходами. 18 из 949 выходов
   известных посёлков ведут в клетку, которую рельеф называет скалой (§9).
9. Гипотеза «граница = кольцо локаций по периметру» **подтверждена по
   механизму и опровергнута по геометрии**: кольцо из этих плиток — ровно
   тот способ, каким делалась стена, но периметр не совпадает с нынешним
   прямоугольником, а тот же набор стоял и внутри карты («Горные тропы»,
   «Ущелье Смерти», «Перевал Смерти», острова).
10. Предложение: `data/borders.json` + `data/build_borders.py`. **Принято и
    сделано — §13**: проходимость по фотографии убрана (осталась вода),
    кольцо поставлено на периметр мира (2088 клеток), восточная и южная
    границы отодвинуты до последней нарисованной клетки, тупик открывается
    карманом. Числа §8 и §9 ниже — какими они были до правки.

## 2. Формат узлов локации, и как читается сторона выхода

Клиент разбирает XML локации в `core/location/LDParser.as:41-113` и трогает
ровно пять узлов: `obstacles`, `zones`, `bgdecoration`, `sprite`,
`background`. `inzones`, `outzones`, `warinzones`, `mobs`, `serverdata` он
молча пропускает — это серверные узлы.

Разбор координат — `LDParser.as:121-152`:

```as
static function getHexCoord(str, offX, offY, d)
{
   var _loc12_ = !d ? 4 : d;            // шаг записи, по умолчанию 4 символа
   ...
   _loc6_ = "0x" + str.substr(_loc2_,2);      // x
   _loc5_ = "0x" + str.substr(_loc2_ + 2,2);  // y
   ...
   _loc2_ += _loc12_;
}
```

`obstacles` читаются с шагом 5 (`LDParser.as:46`:
`getHexCoord(_loc15_,null,null,5)`), `zones` — с шагом по умолчанию
(`LDParser.as:51`). Пятый символ препятствия клиент отбрасывает.

Проверка длин по всем 1381 файлам: `outzones` делится на 5 во всех 1357
файлах, где узел непуст (на 4 — только в 293); `zones`, `inzones`,
`warinzones` делятся на 4. **Множество клеток `zones` совпадает с множеством
клеток `outzones` во всех 1381 файлах** — то есть `outzones` это те же
клетки выхода плюс один символ.

Что этот символ значит, видно по нормированным центроидам всех записей всех
файлов (`recon/notes/borders_side_codes.py`, сводка от агента-разведчика):

| код | записей | meanX/width | meanY/height | край сетки |
|---|---|---|---|---|
| 1 | 98027 | **0.006** | 0.505 | левый, `x≈0` |
| 2 | 96783 | 0.479 | **0.012** | верхний, `y≈0` |
| 3 | 80165 | **0.979** | 0.509 | правый, `x≈w-1` |
| 4 | 109879 | 0.506 | **0.991** | нижний, `y≈h-1` |
| a | 80590 | 0.448 | 0.516 | середина — дверь внутрь |
| b | 90579 | 0.445 | 0.502 | середина — дверь внутрь |

Это уже было записано в `recon/analysis/world.md §5` и реализовано в
`data/build_exits_sides.py`; здесь оно перепроверено на всём корпусе.

Клиент использует только флаг «клетка — зона»: `LocationGrid.as:190-204`
(`setZones` → `CellsGrid[y][x].zone = true`) и
`core/location/Location.as:175-183`:

```as
function finishMove(obj){
   var _loc2_ = obj.target;
   if(_loc2_ == this.gamer.walker && this.getCellFromNumber(_loc2_.numPos).zone){
      this.exitLocation();
   }
```

— дошёл до зоны, открылось окно выхода. Какая это сторона, клиент не
вычисляет и серверу не сообщает: `CSM_ChangeWorld` несёт только `to`
(`server/mess/CSM_ChangeWorld.as`). Сторону обязан вывести сервер из клетки,
на которой стоит игрок.

`obstacles` — непроходимые клетки **внутри** локации
(`LocationGrid.as:175-189`, `unreachable = true`), к глобальной карте
отношения не имеют. `warinzones` — клетки появления в боевом режиме.
`inzones` — клетки появления при входе; они лежат тем же кольцом у краёв,
что и `outzones`, но без кода стороны, поэтому «с какой стороны вошёл»
сервер тоже вычисляет сам.

## 3. Знает ли клиент о непроходимости глобальной карты — нет

Проверено всё дерево `lol/core/globmap/` (7 файлов) плюс `SSEmulator.as`.

* Движение по карте — безусловная отправка вектора, никакой проверки цели
  (`GlobalMap.as:81-86`):

  ```as
  function playerMove(dx, dy) {
     var _loc2_ = new lol.server.mess.CSM_GM_MovePlayer(dx,dy);
     this.XMC.Send(_loc2_);
     this.dispatchEvent({type:"startMove"});
  }
  ```
  `dx`/`dy` — смещение от текущей позиции в сотых долях клетки
  (`DisplayGlobalMap.as:143-160`: `Math.floor(100 * (_xmouse/mapScale - x))`).
  Ответ `moveAck` несёт только `vx, vy, t`; поля «отказ» нет
  (`GlobalMap.as:91-124`).
* **`canMove` — мёртвый код.** Объявлено на `GlobalMap.as:13`, присваивается
  на `:89` (`this.canMove = !obj.success;` в обработчике `changeWorld`), и
  больше нигде во всём дереве не читается (grep по `as-src`: только эти две
  строки). Смысл у него был «идёт переход между мирами», а не «сюда нельзя».
* `DisplayLandscape` только грузит тайлы-картинки
  (`SSEmulator.as:19-44`, `getGMTURL`) и рисует декоративную сетку
  (`DisplayLandscape.as:90-120`, `drawCellBorder`). Пиксели карты клиент не
  анализирует.
* Отказ сервера на движение по карте клиент никак не показывает:
  `Master.changeWorldAck` (`Master.as:148-168`) различает только `res==0` и
  `res==39` («режим боя»), всё остальное — молчаливый откат. Текстов «туда
  нельзя», «непроходимо», «скалы» в клиенте нет; таблица `ErrorReport.as:56-83`
  привязана к `cmdAck`, а «Невозможно пройти» (код 8) — это результат
  локального поиска пути по гексам внутри локации (`Location.as:626, 692`).
* В ресурсах нет ни одного файла вида «координата → id локации» или карты
  проходимости. `res/cli.bin` — PE-лаунчер, `res/cache.db` — .NET-кэш версий
  апдейтера. Единственные данные, индексируемые координатами, — растровые
  тайлы и 414 текстовых подписей.

**Вывод: весь рельеф был на сервере. Клиент узнаёт о скалах только тем, что
сервер прислал ему `lcall` с id скальной локации.**

## 4. Система координат: инверсии нет

### 4.1 `pos = y*width + x` — из кода, однозначно

`LocationGrid.as:27-52`, `createCells`: внешний цикл по `y`, внутренний по
`x`, сквозной счётчик инкрементируется во внутреннем цикле и пушится в
`CellsNum` по порядку. Плюс `LocationGrid.as:64-67`
`getCellFromGrid(x,y){ return this.CellsGrid[y][x]; }`. Значит
`num = y*gridW + x`. Сервер считает так же.

### 4.2 Оси отрисовки: x вправо, y вниз

`LocDeclaration.as:3-6, 10-17` плюс смещение полурядов в `HexCell`
(`LocationGrid.as:43-44`) дают экранные координаты клетки:

```
screen_x = 40 * x + 20 * (y % 2)
screen_y = 15 * y
```

Ни одной инверсии знака (`-y`, `_yscale=-100`, `_rotation`) в
`DisplayLocScene.as` / `LocBuilder.as` нет. На глобальной карте так же:
`DisplayGlobalMap.as:138-142` `obj._x = mapScale*x; obj._y = mapScale*y;`.

### 4.3 Где на глобальной карте север и запад — из подписей клиента

Это единственное место, где стороны света названы прямо. В
`res/database/locations.xml`:

```xml
<location x="5833" y="1607" text="Западные Предгорья." />
<location x="5840" y="1600" text="Северные Предгорья" />
```

`5833` — минимальный `x` среди всех 414 подписей, `1600` — минимальный `y`.
То есть **меньший `gx` = запад, меньший `gy` = север**. Картинка карты
north-up, как и ожидалось, но теперь это факт из данных, а не допущение.

### 4.4 Какой край сетки локации какой стороне света соответствует

Имена плиток тут бесполезны: `B_LeftSide` — это стена **справа**, а
`B_DownSide` — стена **сверху** (§1). Имя указывает на открытую сторону, то
есть на то, с какой стороны гряды стоит игрок. Поэтому вопрос решался на
данных — `recon/notes/borders_neighbour_test.py`.

Идея: две соседние клетки карты, на которых стоят **разные** посёлки, должны
быть соединены — у левой должен быть выход в сторону правой, у правой в
сторону левой. Таких пар среди 262 восстановленных клеток — 84. Привязка
клеток к файлам делалась по подписям карты и никак не зависит от того, какой
код какой стороне соответствует (`data/place_settlements.py` использует
`exits_sides.json` только как фильтр «есть хоть один выход на карту» и как
часть ключа дедупликации), так что проверка не круговая.

| гипотеза | соединено | односторонне | из 18 «различающих» пар |
|---|---|---|---|
| **A: 1=W 2=N 3=E 4=S** (как сейчас у сервера) | **83** | 1 | **17** |
| C: 1=E 2=N 3=W 4=S (зеркало по x) | 79 | 5 | 13 |
| D: 1=W 2=S 3=E 4=N (зеркало по y) | 74 | 10 | 8 |
| B: 1=E 2=S 3=W 4=N (поворот на 180°) | 70 | 14 | 4 |

Отдельные пары, которые решают вопрос по каждой оси:

* по **x**: `(6261,1825)` loc 184, коды `{3}` — единственный выход;
  `(6262,1825)` loc 183, коды `{1,3}`. При A: 184 выходит на восток в 183,
  183 возвращается на запад в 184 и идёт дальше на восток. Цепочка сходится.
  При C коды смотрят в обратные стороны, и 184 открывается в пустое место, а
  соседний посёлок оказывается недостижим. Так же ведут себя
  `(5965,1728)` loc 41 `{3}` → `(5966,1728)` loc 52 и
  `(5967,1725)` loc 107 `{3}` → `(5968,1725)` loc 119. Против A — одна пара
  из шести (`(6000,1800)` loc 305 → loc 307).
* по **y**: `(5840,1600)` loc 322, коды `{1,4}`, и под ней `(5840,1601)`
  loc 323, коды `{2,4}`. При A: 322 стоит на северном краю (кода `2` нет —
  на север нельзя), выходит на юг в 323, 323 возвращается на север. При D и B
  322 открывалась бы на север, то есть с края карты наружу. Ещё восемь пар
  в том же духе, против A — ни одной.

### 4.5 Независимое подтверждение: бесPvP-копии

`NoPvP_UpSide1/2` (178, 179) — побайтовые копии `B_UpSide1/2` (стена на
`y-max`), `NoPvP_LeftSide2` (180) — копия `B_LeftSide2` (стена на `x-max`), и
только они. Стартовая зона — северо-западный угол карты: обе подписи
«Предгорья» стоят на минимальных `gx` и `gy`, а их файлы (182, 322) имеют
`library="Noob_Zone_Nord"` и `pvp="0"`. Внутренние границы угловой области —
это её юг и восток. Стена на `y-max` = юг и стена на `x-max` = восток —
ровно те две, копии которых и сделали. Никаких `NoPvP_DownSide` или
`NoPvP_RightSide` в клиенте нет.

**Ответ на вопрос об инверсии: инверсии нет. `pos = y*width+x`, `1`=W,
`2`=N, `3`=E, `4`=S, запад ведёт в `gx-1`, север в `gy-1` — сервер считает
правильно.** Плохое поведение границ объясняется не осями, а тем, откуда
берётся рельеф (§9).

## 5. Геометрия плиток: что именно нарисовано

Полные схемы — в приложении. Коротко, что из них следует.

**Стороны.** У каждой стороны скала занимает не ровную полосу, а
диагональную массу, и открытая часть клетки сужается от одного края к
другому. Например `B_LeftSide1` (1) открыт на север почти во всю ширину
(`x 0..47` из 64) и на юг только на `x 1..23`; `B_LeftSide2` (2) — наоборот
(север `0..37`, юг `1..52`). Это и есть смысл двух вариантов: их края
стыкуются друг с другом, и вертикальный прогон `…1,2,1,2…` даёт непрерывную
гряду без шва (`recon/notes/borders_edge_profiles.py`: стык «низ 2 → верх 1»
даёт 0.87 по Жаккару, «низ 1 → верх 2» — 0.62, тогда как одна и та же плитка
дважды подряд — 0.68 и 0.49).

**Углы.** Ровно два выхода, скала занимает противоположную четверть. Имя
называет свободную четверть: `B_LeftUpCorner` открыт на запад и на север,
значит стоит в **юго-восточном** углу мира.

**Проходы.** `B_HolisontalPass` (5) открыт только `1` и `3` — сквозь него
можно пройти с запада на восток, но не с севера на юг: это разрыв в
меридиональной гряде. `B_VerticalPass` (6) — зеркально. Имена, в отличие от
`Left/Right`, читаются буквально: «горизонтальный» = вдоль оси x, и это
независимо подтверждает, что x — горизонтальная (запад-восток) ось.

**Карманы.** Ровно один выход каждый: 14 — только запад, 40 — только север,
4 — только восток, 7 — только юг. Файл `4` не имеет атрибута `fn`, поэтому
его и не заметили раньше; по геометрии это недостающий «правый карман»,
замыкающий набор из четырёх. Карман — это тупик: войти и выйти можно только
с одной стороны. Для сервера это самая правильная сцена в ответ на «пошёл в
скалы»: сейчас `travel.rock_exit` подставляет плитку-**сторону**, у которой
открыты ещё две стороны, и игрок, попав в скалы, может из них уйти не туда,
откуда пришёл.

**Остров.** 51 и 428 — скальная клякса в середине при четырёх открытых
сторонах: это не стена, а гора посреди проходимой клетки. Клетку можно
пересечь в обход. Значит внутри карты скальные плитки тоже стояли.

**Озеро.** 1298 `B_Lake_MWM`, заголовок не «Скалы», а **«Засада»**:
6146 препятствий из 8192 клеток, `outzones` пуст вовсе, `inzones` —
25 клеток в самой середине (`x 29..35, y 57..63`). Из такой локации нельзя
выйти на карту ни в одну сторону, а попасть в неё можно только тем, что
сервер поставит игрока в середину. Это сценарная ловушка, а не элемент
границы.

**`B_DownSide_Out` (218)** — побайтово та же геометрия, что у
`B_DownSide1` (10): те же 2761 препятствие, те же 411 клеток выхода, те же
144 боевых. Это копия под другим именем, а не отдельная роль.

## 6. Как клетка превращалась в локацию

`services/SSEmulator.as:45-80`, `getLocDescription` — четыре ветки, а не три:

```as
_loc1_ = "locations/static/" + locID + ".xml";                      // :48
var _loc4_ = lol.local.SBase.getInstance().getLocDef(_loc1_);       // :49
if(!_loc4_)
{
   if(locID >> 28 == 4)                                             // :55
      _loc1_ = "locations/deadloc/" + (locID >> 26 & 3) + ".xml";   // :57
   else if(locID >> 26 == 0)                                        // :59
   {
      _loc6_ = locID >> 13;                                         // gx
      _loc5_ = locID & 0x1FFF;                                      // gy
      _loc3_ = (_loc6_ + _loc5_ & 3) + 1;                           // ((gx+gy)&3)+1
      _loc1_ = "locations/desert/" + strPad(_loc3_,"0",4,LEFT) + ".xml";
   }
   else
      _loc1_ = "";                                                  // :68 — провал загрузки
}
```

Первая ветка — не «файл существует», а «есть запись в манифесте
`xml/loc_defs.xml`» (1381 запись). Значит **любой скальной клетке сервер
слал обычный маленький id из этого диапазона** — никакой особой кодировки
для границ не нужно и не существует. Одним файлом можно закрыть сколько
угодно клеток, ровно как четырьмя файлами пустыни закрыт весь остальной мир.

Поля geo-id — `utils/LocIdToCoordinate.as`: `x = (id & 0x3FFE000) >> 13`,
`y = id & 0x1FFF`, `z = id >> 26`. `z != 0` означает «подлокация»
(`Location.as:793-802` `isSubLocation`), и тогда кнопка «на глобальную
карту» гаснет (`ExitLocationInterface.as:24-27`, `LocationInterface.as:704`).
Бит 31 — поле боя (`Location.as:803-810`).

**`deadloc` — «Граница пустоши».** Четыре файла
`res/locations/deadloc/0..3.xml`, `library="Desert"`, `bg_desert1.jpg`,
**ноль препятствий**, и клетки выхода ровно на одном краю:

| файл | код | край | смысл |
|---|---|---|---|
| 0 | 1 | `x 0..1` | выход на запад |
| 1 | 2 | `y 0..2` | выход на север |
| 2 | 3 | `x 62..63` | выход на восток |
| 3 | 4 | `y 126..128` | выход на юг |

Индекс выбирается сервером битами 26-27 при выставленном бите 30. Это
вторая, независимая от скал реализация «края мира»: голая пустошь, из
которой можно уйти только назад. Сервер сейчас использует её для шага за
прямоугольник (`travel.destination`), и это разумно.

Никакой третьей «ветки для границ» в клиенте нет: имена `B_*`, `MWM`, `ARM`,
`IVM` встречаются только в атрибуте `fn` самих файлов локаций, в
`recon/notes/main_swf_strings.txt` их ноль, слов «Скалы», «горы»,
«непроходимо» в коде нет.

## 7. Карманы, проходы, бесPvP-копии — что они говорят о размещении

Набор перекрывает все случаи, которые возникают, когда гряду **рисуют на
карте**, а не когда ставят рамку: сторона гряды, угол поворота гряды, разрыв
гряды (проход), тупиковая бухта в гряде (карман), одиночная скала (остров).
Для голого прямоугольного кольца нужны только стороны и углы; проходы,
карманы и острова в кольце смысла не имеют.

Подписи карты это подтверждают прямо
(`recon/notes/borders_foothills.py`: 33 подписи из 414 называют камень):

* «**Горные тропы**» — четыре комплекса по три клетки, файлы
  `MP_Enter1 / MP_Center / MP_Enter3`, `library="Mountains"`, около
  `(5908,2003)`, `(6016,1745)`, `(6211,1946)`;
* «**Ущелье Смерти**» — четыре вертикальных прогона ровно по 5 клеток
  (`5844,1826..1830`; `5851,1986..1990`; `5941,1697..1701`;
  `6145,1993..1997`), у верхней клетки каждого — файл `FV_MainGate_*`
  с единственным кодом `4` (выйти можно только на юг);
* «**Перевал Смерти**» `(5982,1866)`;
* «**Западные / Северные Предгорья**» на западном и северном краю.

То есть внутри карты стояли настоящие гряды с проходами и ущельями, а не
только рамка по периметру.

Самое сильное свидетельство о способе размещения — бесPvP-копии. Чтобы
поставить стену вокруг стартовой зоны, дизайнеру пришлось **сделать копии
плиток с `pvp="0"`** — потому что иначе стена унаследовала бы PvP от
шаблона. Копий ровно три и ровно тех, которые нужны юго-восточной границе
северо-западного угла. Это возможно только при поклеточной расстановке
файлов.

## 8. Сколько клеток нужно кольцу, и где оно стоит

Периметр нынешнего прямоугольника `5833..6305 × 1600..2110` (473 × 511) —
**1964 клетки**. Двенадцати файлов (4 стороны × 2 варианта + 4 угла) для
этого более чем достаточно: один файл спокойно обслуживает сотни клеток, как
это делают четыре файла пустыни. Два варианта на сторону — это именно то,
что нужно для чередования вдоль длинного прогона, и их края стыкуются (§5).

Но сам прямоугольник взят не из клиента. Это описанный прямоугольник
414 подписей `res/database/locations.xml` — что подтверждено прямым
подсчётом (`recon/notes/borders_extremes.py`): экстремумы подписей и
экстремумы посёлков совпадают точно, `5833..6305 × 1600..2110`.

Что рисует клиент:

* `res/globalmap/client/` — **1024 тайла 256×256 при `mapScale=1`**, то есть
  весь мир 8192×8192 клеток по одному пикселю на клетку
  (`DisplayLandscape.as:121-134`). Это обзорная картинка континентов;
  игровая область на ней — пятнышко.
* `res/globalmap/full/` — 273 тайла при `mapScale=8`, 8×8 пикселей на клетку.
  Они покрывают `tx 182..197, ty 50..66`, то есть
  **`gx 5824..6335, gy 1600..2143`** (512 × 544 клетки), плюс один
  одиночный тайл `(163,57)` далеко на западе (`gx 5216..5247,
  gy 1824..1855`). За пределами этого блока карту просто нечем нарисовать.

Что стоит на краях прямоугольника (`recon/notes/borders_edge_walls.py`):

| край | клетка | подпись | файл | свои выходы | наружу |
|---|---|---|---|---|---|
| запад `gx=5833` | 5833,1607 | «Западные Предгорья.» | 182 `NoobZone_Cow`, `pvp=0` | `{4}` | **закрыт** |
| север `gy=1600` | 5840,1600 | «Северные Предгорья» | 322 `Evan_01`, `pvp=0` | `{1,4}` | **закрыт** |
| восток `gx=6305` | 6305,1841 | «Выход с карьера» | 303 `Silver_Noob_e_Enter` | `{1,3,4}` | **открыт** |
| юг `gy=2110` | 5943,2110 | «Шахта Мероэ» | 280 `MR_Plumbum_Mine_IN` | `{1,2,3,4}` | **открыт** |

Вывод: западная и северная границы мира стоят там, где сейчас, и подтверждены
самим клиентом — и подписью, и отсутствием выхода наружу. Восточная и южная
— **не там**: мир продолжается дальше, и предел, который можно назвать
твёрдым, — край нарисованного, `gx ≤ 6335`, `gy ≤ 2143`.

Наконец, картинка карты **не рисует никакой каменной рамки по периметру**
(`recon/notes/borders_full_map_overview.py`): и за `gx=6305`, и за `gy=2110`
продолжается ровно такая же гладкая пустыня, а шероховатых мест на всей
карте мало и они разбросаны. Границу в оригинале держали данные сервера, а не
рисунок.

## 9. Проверка нынешнего рельефа на данных

`data/build_terrain.py` строит проходимость по шероховатости фотографии
(порог `ROUGH=26`). Что получается (`recon/notes/borders_terrain_conflict.py`):

* прямоугольник 473 × 511 = **241703 клетки**, закрыто **6130 (2.54 %)**:
  4562 «скала» и 1568 «вода»;
* **каждая из этих 6130 клеток, если в неё войти, откроется обычной
  пустошью с четырьмя выходами** — сервер не назначает им скальный файл
  (`world.location_at` возвращает упакованную клетку, то есть
  `locations/desert/000N.xml`, а все одиннадцать шаблонов пустыни несут коды
  `1234`). Рельеф и то, что увидит игрок, расходятся полностью;
* **18 из 949** выходов известных посёлков ведут в клетку, которую рельеф
  называет скалой. То есть файл локации говорит «отсюда можно на восток», а
  сервер отвечает пограничной сценой. Среди них — `6305,1841` loc 303
  (два выхода из трёх), `6272,1840` loc 34 (север и юг), `5863,1837` loc 459
  (запад и восток);
* прямая проверка «закрытая сторона смотрит на более шероховатый грунт»
  не даёт сигнала вообще (`recon/notes/borders_orient_test.py`): для всех
  четырёх возможных ориентаций осей разница между шероховатостью у закрытой
  и у открытой стороны отрицательна (−0.36 … −1.16 при p50 ≈ 16.5). Стены
  посёлков не коррелируют с фотографией никак.

Про подсказки и посёлки: все 414 подписей и все 262 клетки посёлков лежат
внутри прямоугольника по построению; на самом периметре стоят четыре клетки
посёлков (перечислены в §8), и `data/borders.json` их не трогает.

## 10. Вывод: подтвердилась ли гипотеза и что делать серверу

### Что подтвердилось

**Механизм — полностью.** Граница и любая непроходимость в LAVA была кольцом
(или линией, или пятном) **локаций**, а не рельефом. Плитка стены — это
обычный файл из `res/locations/static`, у которого в `outzones` нет кода
наружной стороны. Набор плиток в клиенте полон, симметричен, снабжён двумя
вариантами на сторону для чередования, стыкуется по краям и имеет
бесPvP-копии — то есть его ставили на карту поклеточно.

**Ориентация — подтвердилась в пользу сервера.** Инверсии нет ни по одной
оси; `1`=W, `2`=N, `3`=E, `4`=S; `pos = y*width + x`. Имена файлов (`Left`,
`Up`) указывают на открытую сторону, а не на стену, и как ориентир не
годятся — таблица `travel.ROCK_WALL` уже читает это из данных и читает
верно.

### Что опровергнулось

**Геометрия кольца.** Прямоугольник `5833..6305 × 1600..2110` — это
описанный прямоугольник подписей, а не край мира. На западе и севере он
случайно совпал с настоящим краем (и это подтверждено «Предгорьями»), на
востоке и юге — нет: тамошние посёлки выпускают игрока наружу, а рисунок
карты идёт ещё на 30 и 33 клетки дальше.

**«Кольцо» как исчерпывающее описание.** Тот же набор стоял и внутри карты:
«Горные тропы», четыре «Ущелья Смерти», «Перевал Смерти», острова. Проходы и
карманы в рамке вообще не нужны — они нужны гряде. Полная таблица «клетка →
скальный файл» для внутренних гряд утрачена и из клиента не выводится:
подписи дают только 33 клетки из ~1900, которые заняты камнем на вид.

### Что делать

По убыванию отдачи.

1. **Перестать выводить проходимость из фотографии.** Это единственное
   изменение, которое действительно чинит «ложные горы посреди пустыни».
   Правильная база — «клетка проходима, пока сервер не назначил ей скальный
   файл», потому что именно так устроен клиент. `data/map_terrain.json`
   в нынешнем виде противоречит клиенту в 6130 клетках и ломает 18 выходов
   из посёлков.
   Объём: удалить зависимость `world.passable` от `map_terrain.json`, оставив
   воду (озеро Насер — единственное, что фотография находит надёжно, и оно
   заведомо не пустыня), и переключить `travel` на таблицу скальных клеток.
   Полдня.
2. **Взять проходимость из самих локаций.** У 262 клеток посёлков стороны уже
   известны точно — они лежат в `data/exits_sides.json`. Выход в сторону,
   которой нет в `outzones`, вообще не должен рассматриваться; а сторона,
   которая есть, должна вести в соседнюю клетку без оглядки на рельеф. Это
   убирает все 18 расхождений даром.
   Объём: правка в `travel.plan_exit` (там, где сейчас стоит проверка
   `world.passable` на соседней клетке). Час.
3. **Поставить кольцо.** `data/borders.json` (приложен, §11) — готовая
   таблица «клетка периметра → id файла», 1960 клеток. Она не меняет ничего
   в сервере сама по себе: id в ней — те же, что уже перечислены в
   `travel.ROCK_SIDE` и `travel.ROCK_CORNER`.
   Объём: `world.location_at` сначала смотрит в `borders.json`, потом в
   `settlements.json`, потом отдаёт пустыню. Два часа с тестом.
4. **Решить, где восточная и южная границы.** Сейчас у сервера
   `MAP_X=(5833,6305)`, `MAP_Y=(1600,2110)`. Данные говорят: запад 5833 и
   север 1600 верны, восток и юг — минимум 6306 и 2111, максимум 6335 и 2143
   (дальше нечего рисовать). Это решение владельца; `build_borders.py`
   принимает `--bounds artwork` и перестраивает таблицу под
   `5824..6335 × 1600..2143`.
5. **Заменить сцену «вошёл в скалы» на карман.** `travel.rock_exit` сейчас
   подставляет плитку-сторону, у которой открыты ещё две стороны; правильная
   сцена тупика — карманы `14` (вход с запада), `40` (с севера), `4` (с
   востока), `7` (с юга). Тогда «зашёл в скалы — вышел обратно» работает
   буквально.
   Объём: одна таблица из четырёх строк. Полчаса. (Проверить на живом
   клиенте: у карманов очень узкая полоса выхода, и `arrival_cell` должен
   попадать именно в неё.)
6. **Внутренние гряды — отдельная задача и отдельные данные.** Их положение
   восстановимо только по памяти игрока и по 33 подписям. Пока их нет,
   честнее оставить карту открытой: лишний проход игрок заметит как удобство,
   лишняя гора — как поломку.

### Чего делать точно не стоит

Подгонять порог `ROUGH`. Сигнала там нет: проверка §9 показывает, что
шероховатость фотографии не связана с закрытыми сторонами известных локаций
вообще никак.

## 11. Предлагаемая таблица `data/borders.json`

Строится `data/build_borders.py`. Формат:

```json
{ "bounds": {"gx0": 5833, "gx1": 6305, "gy0": 1600, "gy1": 2110,
             "which": "server"},
  "tiles":  {"side":   {"W": [12,13], "E": [1,2], "N": [10,11], "S": [15,16]},
             "corner": {"WN": 3, "EN": 9, "WS": 0, "ES": 8}},
  "skipped_settlement_cells": [...],
  "cells":  {"5833,1600": 3, "5833,1601": 12, "5833,1602": 13, ...} }
```

Правила: клетка на стороне получает плитку, стена которой смотрит наружу;
из двух вариантов берётся `(gx+gy) % 2`, чтобы прогон чередовался, а одна и
та же клетка всегда показывала одни и те же скалы; углы получают свою плитку.
Клетка периметра, на которой уже стоит посёлок, пропускается — таких четыре,
и они перечислены в файле вместе с их собственными выходами.

Перед записью скрипт проверяет набор по самим файлам клиента: у каждой
боковой плитки должны быть ровно три стороны кроме заявленной, у углового —
ровно две. Если ресурсы не сойдутся, файл не пишется.

Получается 1960 клеток из 1964 возможных, 38 КБ. Сервер её пока не читает.

**Побочный эффект, который надо иметь в виду:** если кольцо поставить по
самому периметру, «Граница пустоши» (`deadloc`) станет недостижимой — за
кольцо уже не выйти. Если хочется сохранить и то и другое, кольцо надо
ставить на одну клетку наружу от жилой области, а периметр оставить
проходимым. Данных, которые сказали бы, как было в оригинале, нет: в клиенте
есть и скальные плитки, и четыре файла «Граница пустоши», и обе схемы ими
реализуемы.

сетки 64x128; строка сверху — север, столбец слева — запад.

## 13. Что из этого сделано в сервере

Ветка `wave5/borders-impl`. Ниже — только то, что изменилось, и почему
именно так; числа перепроверены на данных заново, а не переписаны из §9.

### 13.1 Проходимость: осталась одна вода

`world.BLOCKED` теперь `"~"`, а не `"#~"`. Колонка «скала» в
`data/map_terrain.json` осталась лежать как есть — это честная запись того,
что говорит фотография, — но сервер её больше не спрашивает. Обоснование в
§3 и §9: слоя проходимости не было, а каждая из 6130 «скальных» клеток
открылась бы пустошью с четырьмя выходами.

Вода отделима от шероховатости и проверена отдельно: критерий у неё
независимый (средний синий выше среднего красного, порог 2.0 уровня), он не
подгонялся ни под какую связность, даёт 1568 клеток, из них 1378 — одним
куском (озеро Насер при 6062,1621), остальные 64 пятна по 1–17 клеток.
Главное: **ни один из 949 выходов известных посёлков не ведёт в воду**
(в скалу вели 18). То есть данные клиента с водой не спорят нигде, а со
скалой спорили в восемнадцати местах.

Числа после правки: мир 503 × 544 = 273 632 клетки, закрыто 1568 (0.57 %),
все до одной — вода. Пешком от старта 5970,1730 доходимы 272 003 клетки;
61 сухая клетка не доходима — это островки внутри озера.

`world.in_map` теперь считает по прямоугольнику мира, а не по границам
растра: растр меньше мира (см. ниже), и «за краем картинки» не значит «за
краем мира».

### 13.2 Восточная и южная границы: до последней нарисованной клетки

Решение: `world.MAP_X = (5833, 6335)`, `world.MAP_Y = (1600, 2143)`.

Запад и север не двигались: у них есть слово клиента (§8) — подписи
«Западные Предгорья» и «Северные Предгорья» и отсутствие выхода наружу у
стоящих там файлов 182 и 322. Восток и юг двигались с 6305 и 2110 до 6335 и
2143. Три довода, по убыванию силы:

1. **Данные прямо противоречили старому краю.** На старом восточном крае
   стоит 303 «Выход с карьера» с выходом на восток, на старом южном — 280
   «Шахта Мероэ» с выходом на юг. При старом прямоугольнике эти два выхода
   упирались в край мира, то есть сервер отвечал бы стеной там, где файл
   локации говорит «отсюда можно». Это ровно тот сорт противоречия, который
   и требовалось убрать. После сдвига таких выходов **ноль**.
2. **Старый прямоугольник не был границей ничего.** Это описанный
   прямоугольник 414 подписей карты (§8), то есть «где есть названия», а не
   «где кончается мир».
3. **6335 и 2143 — предел, который можно обосновать.** `res/globalmap/full`
   покрывает тайлы tx 182..197, ty 50..66, то есть gx 5824..6335,
   gy 1600..2143. Дальше клиенту нечего рисовать: игрок вышел бы на чёрное
   поле. Западный край картинки (5824) при этом не берётся — там слово
   клиента сильнее: «Западные Предгорья» стоят на 5833.

Цена решения: 30 столбцов и 33 строки нарисованной пустоши без единого
посёлка и без подписей. Проверено, что там действительно есть что рисовать
(тайлы на месте) и что вода туда не заходит (растр фотографии кончается
раньше, а за ним по картинке — та же гладкая пустыня, §8).

Альтернатива «оставить 6305/2110» отвергнута: она сохраняет оба
противоречия. Альтернатива «взять весь прямоугольник картинки 5824..6335»
отвергнута из-за западного края, где данные говорят иначе.

### 13.3 Кольцо скал стоит на карте

`data/build_borders.py` перестроен под прямоугольник мира: 2088 клеток из
2090 на периметре, две заняты посёлками (182 на 5833,1607 и 322 на
5840,1600 — и ни один из них наружу не выпускает, что как раз и есть край
мира в файлах). Использованы 12 файлов: стороны по два варианта вперемешку
(1/2, 10/11, 12/13, 15/16) и четыре угла (0, 3, 8, 9).

`world.location_at` отвечает тремя таблицами по убыванию надёжности:
посёлок → кольцо → пустошь. Кольцо после посёлков, потому что посёлок — это
улика, а кольцо — предложение.

Плитки выбраны только по данным. Проверка в `data/test_borders.py` для
каждой из 2088 клеток берёт `outzones` самого файла, вычисляет стену как
сторону, которой в них нет, и сверяет со стороной, смотрящей наружу из
прямоугольника. Совпадает везде; заодно сверено с `travel.ROCK_WALL` и с
тем, что выбрала бы `travel.rock_for` — таблицы сервера и файл данных
разойтись не могут.

Побочный эффект, обещанный в §11, подтвердился: «Граница пустоши»
(`deadloc`) стала недостижима из игры — за кольцо не выйти. Файлы оставлены
рабочими: `travel.destination` по-прежнему отвечает ими для клетки вне мира,
и это путь для персонажа, чья сохранённая клетка оказалась снаружи.

### 13.4 Сторона выхода — это то, что написано в файле

`travel.plan_exit` больше не спрашивает рельеф про соседнюю клетку. Сторона
есть в `outzones` — игрок идёт в соседнюю клетку, и там его встречает то,
что там стоит. Конфликтов с `data/exits_sides.json` не осталось: 7211
объявленных выходов у 2350 локаций, стоящих на карте (262 посёлка + 2088
клеток кольца), и ни один не ведёт за карту.

Остаётся 31 выход **в воду** — все у плиток кольца на западном крае, где
озеро подходит к самому краю мира. Посёлки в воду не выходят ни разу. Эти
31 отвечают карманом (§13.5), а не ошибкой.

Стены при этом никуда не делись, они просто стали приходить оттуда, откуда
приходили в оригинале. Из 262 клеток посёлков наружу выпускают во все четыре
стороны 209, в три — 25, в две — 12, и **в одну — 16**. Замурованных наглухо
нет ни одной. То есть направление движения по-прежнему ограничено, но
ограничивает его файл локации, а не яркость пикселей.

### 13.5 Тупик — это карман, а не окно ошибки

`travel.rock_exit` заменён на `travel.dead_end`: сцена тупика теперь один из
четырёх карманов набора, а не боковая плитка с двумя лишними открытыми
сторонами. Таблица `travel.POCKET` по направлению хода: E → 14, W → 4,
N → 7, S → 40. Она тоже из данных: у 14 открыт только запад, значит именно
14 нужен идущему на восток — он входит западным краем.

Клетка карты при этом не меняется, как у интерьера, так что обойти что-либо
через карман нельзя, а `to=1` из него возвращает ровно туда, откуда вошли.
Проверено, что клетка прибытия в узкой полосе выхода кармана не попадает в
препятствие (у карманов выход — одна полоса, и это была отдельная оговорка
в §10).

Сцена «упёрся в скалы» теперь встречается двумя разными способами, и это
намеренно: у края мира игрок **входит** в клетку кольца (там настоящая
локация со скалами, и выхода наружу у неё нет), а карман открывается только
там, где идти некуда по другой причине — озеро или (для персонажа снаружи
мира) следующий шаг наружу.

### 13.7 Чего не сделано

* **Внутренние гряды.** «Горные тропы», четыре «Ущелья Смерти», «Перевал

  юг и восток, то есть это внутренняя граница стартовой зоны, а не край
  мира; где именно она проходила, из клиента не выводится (§7).
* **Квест выхода из долины** — не трогали, по прямой просьбе владельца.
* ~~**Комната на плитку, а не на клетку.**~~ **Сделано.** `rooms.Rooms`
  заводила комнату по id локации, а одна плитка кольца стоит на сотнях
  клеток: двое игроков на разных концах западной стены оказывались в одной
  комнате — видели друг друга, стояли друг в друге и могли стрелять сквозь
  скалу. Ключ комнаты теперь `(id, gx, gy)` для сцен кольца, карманов и
  `deadloc` и остаётся просто id для всего остального (`travel.room_key`).
  Придумывать новые id локаций, как было в оригинале, не понадобилось:
  комната — наша внутренняя книга «кто кого видит», клиенту она не едет, он
  по-прежнему получает id файла и по нему берёт графику. Проверка в
  `server/test_two_clients.py`: двое на одной стене в двухстах клетках друг
  от друга, локация одна и та же, а видимости нет; без починки набор
  падает.
* **Выход в воду у 31 клетки кольца** отвечает скалами, а не водой. В наборе
  есть «озеро» (1298), но у него нет ни одного выхода вообще — попавший туда
  игрок не смог бы выйти через `to=1`, поэтому оно не используется.
