# Мир и социальные системы LAVA Online — разбор клиента

Источник: `recon/as-src/lol/` (AS2, декомпиляция). Ссылки вида `файл:строка`
относятся к этому каталогу, если не сказано иное. Данные — `res/` клиента
(`C:\Users\gmkrt\OneDrive\Desktop\LAVA\res`). Что уже реализовано в
`server/server.py`, отмечено отдельно; найденные там расхождения с клиентом
собраны в разделе 12.

## 0. Главное в десяти строках

1. **`id=0` всегда значит «я»** (`core/player/Gamer.as:31`, `PlayerRegister.as:27`).
   Любой кадр с id игрока сервер обязан переписывать под получателя:
   свой id → `0`, чужие → их глобальные id. Это единственная «трансляция»,
   без неё мультиплеер не собрать.
2. **Сущность игрока на клиенте живёт вечно** (`PlayerRegister.removePlayer`
   :104-123 удаляет только NPC/мобов). Поэтому id игроков и id NPC не должны
   пересекаться за всю сессию: `server.py` раздаёт NPC id от 100 на каждую
   локацию — игрокам нужен отдельный диапазон (например `1_000_000 + char_id`).
3. Чужой игрок в локации = `lch;newUser=<id>;pos=<hex>;rtype=-1;` +
   ответ на его `getInfo;type=0;id=<id>` кадром `userInfo_Player`, +
   `lch;lostUser=<id>` при уходе, + эхо `userMove;id=<id>;path=|..|` о его шагах.
4. Клиент **не читает `inzones/outzones/warinzones`** — `LDParser.parseLD`
   (:41-113) разбирает только `obstacles`, `zones`, спрайты и фон. Зоны
   выхода = `zones`; `outzones` = те же клетки плюс пятый символ — **сторона
   выхода**: `1`=запад, `2`=север, `3`=восток, `4`=юг, `a`/`b` — «двери»
   (позиция произвольна). Куда ведёт сторона — было в `serverdata`.
5. Переход из локации: встал на клетку `zone` → окно «выход» → `chWorld;`
   (на карту) или `chWorld;to=1;` (в соседнюю локацию). Какая именно
   соседняя — сервер решает сам по клетке игрока и стороне выхода.
6. Чат: клиент **сам печатает своё сообщение** по `cmdAck;res=0`
   (`core/Chat.as:242-256`); эхо от сервера даёт дубль. `res=9` = «персонаж
   офлайн». Приват идёт по нику (`to=@ник@`, без `group`).
7. На карте чужой игрок исчезает через 6 с без `userMove`
   (`MapObject.as:61-84`); `newUser` несёт смещение с **обратным знаком**
   (`GlobalMap.as:46-47`: `x = my.x - dx`).
8. `updMark` отправляется **без регистрации `cmdAck`** (`GlobalMap.as:246-247`);
   `insMark`/`rmMark` — с ней. `server.py` шлёт ack на `updMark` и сдвигает очередь.
9. Смерть: `lch;dead=0` → окно возрождения → `resurrect;res_type=0|1|2` →
   `cmdAck;res=0`; куда возродить — решает сервер (`lcall`). «Дом» =
   `on_conv;mob=<npc>;op=0;` у NPC с `can_set_home=1`.
10. `KB_*` (96 файлов) — клановые базы: по 5–8 локаций на клан
    (`Enter`, `Block_Post`, `Backdoor`, `lvl2_01`, `Sorting`, `Lvl2_Transport`,
    `Bunker_glavaria_klana`, `Desert_point_NN`), привязаны к клеткам с
    подсказкой «Собственность клана …» в `database/locations.xml`.

## 1. Сущности и идентификаторы

### Реестр игроков на клиенте

`core/player/PlayerRegister.as`:

- `addPlayer(id, rtype)` :51-62 — создаёт сущность, если её нет или это
  «прокси»; если уже есть и `rtype == -1`, просит экипировку заново
  (`equipment.getStuff(3,id)`). Класс по `rtype` (`createPlayer` :63-103):
  `0` Mob, `1` Trader, `2` Teacher, `3` Upgrader, `4` Commoner, `5` Healer,
  `6` Lessor, `7` Auctioner, **всё остальное → `Player`**. Для игроков
  оригинал явно рассчитан на `rtype=-1` (ветка :55-58).
- `removePlayer(id)` :104-123: `Player` не удаляется никогда; `Mob` живёт
  ещё 1 с как прокси (чтобы допоказать смерть); NPC удаляются сразу.
- Подписки на `userInfo*`, `usrUp`, `e_list`, `ss_obj_move` :6-22.

Следствия для сервера:

- id игроков глобальны и стабильны на всю сессию клиента; при повторной
  встрече клиент **не переспросит** `getInfo` (сущность уже есть), значит
  один id = один и тот же человек.
- id игроков и NPC/мобов не пересекаются (иначе `lch;newUser=<npc>` вернёт
  старую сущность `Player`, и торговец не откроется).

### Конструктор сущности

`core/player/Entity.as:26-43` — при создании любой чужой сущности клиент сам
шлёт `getInfo`. Для `Player` (`Player.as:19-24`): `getInfo;lvl=0;id=<id>;type=0;`
Для NPC/мобов (`Entity.as:44-48`): `type=1`. `lvl` всегда 0.

`Player.as:11-18`: если состояние `LOCAL_STATE`, дополнительно
`ss_get;target=<id>;slot=3;` (`StuffManager.getStuff` :18-25 →
`CSM_SSGet(slot,target)`), ответ ждётся в отдельной FIFO-очереди `ss_ack`.
Маска 3 = экипировка (6 слотов `slots_arr` `PersEquip.as:68`) + оружие
(2 слота `action_arr` :69). Пустой `ss_ack;o_list=|;` клиент переживает —
`server.py` уже так отвечает на собственный запрос игрока.

### Что ждёт клиент в `userInfo_Player` для чужого игрока

`Entity.userInfo` :49-87 + `Player.userInfo` :25-30 + `Gamer.userInfo` :54-63
(последнее только для `id=0`):

    userInfo_Player;id=<id>;name=@Ник@;sex=<0|128>;res=@<avatar id>@;ail=0;
                    ally=1;lvl=<N>;rep=|0|;bg_rep=0;bg_pen=0;hl=0;pr=<0|1|2>;
                    [только для id=0: afro=;gold=;tr=;tr_hours=]

- `name` для `Player` — **строка**, не id текста (`Entity.as:66-70`);
  пустое имя клиент заменяет на «Солдат СА» (`PlayerRegister.as:163-172`).
- `sex` задаёт `persType` → папку фигуры `personages/<persType>`; `res` —
  портрет (`persGen.getAvatar(res)`), обязан быть id из `avatars/list.xml`,
  иначе на карте `showAvatar` (`GlobalMapInterface.as:619-627`) упадёт.
- `pr` — премиум (0/1/2), рисует звезду и ограничивает аренду транспорта.
- Подпись над головой: `[lvl] Ник` и `<Клан>` строкой ниже
  (`CharInfo.as:226-288`), полосы HP/SP видны у игроков (скрыты только у NPC,
  :84-88), их наполняет `usrUp;id=<id>;hcur=;hmax=;scur=;smax=;`
  (`Entity.userUpdate` :102-111). Без `usrUp` полосы пустые.

## 2. Мультиплеер в локации

### Подписки локации

`core/location/Location.as:26-44`: `lch`, `prepare`, `userMove`, `breakMv`,
`cor_pos`, `ss_loot`, боевые `fa*`/`ca*`, `heal`.

### `lch` — один кадр, много независимых полей

`Location.lch` :45-92, все ветки независимы, поля можно комбинировать:

| Поле | Действие |
|------|----------|
| `ws=0/1` | режим боя локации (`warState` :274-292: звук, очки действий) |
| `newUser=<id>;pos=<hex>;rtype=<r>` | добавить сущность на клетку (все три поля обязательны) |
| `newUser=..;pos=..;rtype=..;refl=1` | зарегистрировать без фигуры (`addPlayer(id,undefined,rtype)`) |
| `lostUser=<id>` | убрать сущность; в журнал событий пишется «Персонаж &nick& покидает локацию» (`GameEvents.as:58`) — имя должно быть уже известно |
| `enemy=<id>` | пометить врагом (красная подсветка, `setEnemy` :477-481) |
| `dead=<id>` | сущность умерла; `dead=0` — умер я (`Resurrector.lch` :46-58) |
| `friend=` | принимается, но не используется (:74-76) |

`addPlayer` :106-132: клетка помечается `busy`, для NPC — `alwaysBusy`;
создаётся `LocWalker`. `removePlayer` :134-151 освобождает клетку.

### Движение чужих

- `userMove;id=<id>;path=|c0|c1|..|;` (`Location.userMove` :184-200) —
  `path[0]` = текущая клетка, шаг 200 мс/гекс (`LocWalker.as:74`),
  занятость клеток обновляется на `finishPart` (:166-174). Неизвестный id
  молча игнорируется.
- `breakMv;id=;pos=;` :249-260 и `cor_pos;id=;pos=;` :261-273 работают и
  для чужих (для себя `cor_pos` ещё перевыдаёт путь).
- `prepare;id=;time=;` :94-100 — таймер над головой (`time-2` секунд,
  `Player.as:31-35`).
- `heal;id=;target=;hp=;sp=;` :456-464 — прямая установка HP/SP.

### Действия над чужим игроком

- Клик по фигуре → `Gamer.gotoWalker(id,"contact")` (`CursorManager.as:446`)
  → подойти вплотную → для `Player` открывается **обмен** (`Barter`,
  `Gamer.proposeContact` :200-204): `ss_create;s_type=2;target=<id>;`
  (`StuffManager.SESSION_BARTER`).
- Из списка игроков чата: приглашение в отряд `p_op;op=0;id=<id>;`
  (`Gamer.sendInviteToParty` :104-124, `cmdAck;res=31` = «нельзя пригласить»),
  приват, осмотр (`InspectInterface` — публичные трофеи через `ss_get`).
- Атака: `fireUser` (`Location.as:304`) — боевая подсистема, вне темы.

### Модель для сервера

Комната = `(loc_id, экземпляр)`. Для боевых локаций и перехватов на карте
экземпляр создаётся под пару/группу, для посёлков — один общий. Обязанности
комнаты:

1. При входе новичка (после `lenter` и `populate`): новичку — `lch;newUser`
   по каждому присутствующему; присутствующим — `lch;newUser` о новичке.
   `rtype=-1`, `pos` — клетка, где тот стоит.
2. Ответы на `getInfo;type=0;id=<other>` и `ss_get;target=<other>;slot=3`.
   Полезно сразу после `lch` пушить `usrUp` по новичку.
3. `moveTo;path` → проверить путь (препятствия + занятость в `war=1`),
   `cmdAck;res=0` отправителю, `userMove;id=0;path` ему же и
   `userMove;id=<he>;path` остальным. Позицию двигать по 200 мс/гекс, а не
   прыжком в конец — иначе занятость клеток разойдётся с клиентами.
4. При уходе/разрыве — `lch;lostUser=<id>` всем оставшимся.
5. Порядок кадров: `lch` с `pos` строит фигуру сразу и требует `persType`
   (см. комментарий в `server.py:populate`), поэтому для игроков, как и для
   NPC, лучше `lch;…;refl=1` → `userInfo_Player` → `lch;newUser;pos` без `refl`
   (второй `lch` для уже известного id создаст `walker` и поставит на клетку,
   `Location.addPlayer` :106-132 не проверяет повтор).

## 3. Глобальная карта

### Вход и выход

- `gmap;x=<gx>;y=<gy>;v_rad=<R>;` (`Master.gmap` :187-202): локация
  убивается, создаётся `GlobalMap`, затем клиент сам шлёт `getInfo` (id=0)
  и `q_list`. Если `playerInfo.dead` — сразу окно возрождения.
- `lcall;id=;ws=;ie=;g_id=;` (`Master.lcall` :203-222). Если `lcall` пришёл в
  `GLOBAL_STATE` и игрок **не нажимал** кнопку входа, клиент считает, что его
  перехватили: заголовок прелоадера «Внимание! На Вас напали в локации …»
  (`Master.playerIntercepted` :169-176, `LocGen.loadSources` :59-71). Поэтому
  автоматический вход по прибытии в клетку выглядит как нападение — и
  `server.py` правильно его не делает.
- Кнопка «Перейти в локацию» / хоткей → `chWorld;` без параметров
  (`GlobalMapInterface.toLocation` :356-363; `CSMessage.toString` :21-44
  пропускает `undefined`). `cmdAck;res=0` → ждём `lcall`; `res=39` → «нельзя
  выйти в бою N сек» (`Master.changeWorldAck` :148-168).

### Другие игроки на карте

`core/globmap/GlobalMap.as` подписан на `newUser`, `userLost`, `userMove`,
`moveAck`, `marks` (:19-23).

| Кадр | Формат | Семантика |
|------|--------|-----------|
| `newUser` | `newUser;id=<id>;dx=<D>;dy=<D>;` | **`x = my.x - dx`** (:46-47) — смещение с обратным знаком, целые клетки |
| `userMove` | `userMove;id=<id>;dx=<X>;dy=<Y>;vx=<vx>;vy=<vy>;t=<t>;` | `dx/dy` — **абсолютные** координаты (клетки, дробные), `vx/vy` — клеток/с, `t` не используется (:95-117, `MapObject.startMove` :28-40). Неизвестный id создаётся на лету (:103-106) |
| `moveAck` | `moveAck;vx=;vy=;t=;` | ответ на свой `moveTo`: задаёт скорость от текущей экстраполированной позиции (:91-94) |
| `userLost` | `userLost;id=<id>;` | убрать (:50-54) |

Heartbeat (`MapObject.checkLive` :61-84): счётчик секунд сбрасывается только
`userMove`; >3 с — объект тускнеет (`faraway`), >6 с — удаляется (`lost`).
**Сервер обязан слать `userMove` по каждому видимому игроку не реже раза
в 3 с, даже стоящему (`vx=0;vy=0`).** Проще всего — тик раз в 2 с по всем
парам в радиусе.

Отрисовка: `DisplayGlobalMap.addPlayer` :65-83 (`mU`), подпись `[lvl] Ник`
цветом клана/отношений (`DisplayMapObject.showInfo` :109-168, зелёный —
свой клан/союзник, красный — враг по `standingArray`). Список игроков справа
(`GlobalMapInterface.initUsers/addPlayer` :525-557), по выбору — портрет
(`showAvatar` :619-627 → `res` из `userInfo_Player`). Радиус `v_rad` рисуется
кругом вокруг себя (`configurePlayerMO` :54-64); чужие дальше радиуса
сервер просто не показывает.

Контекстное меню по чужому (`DisplayGlobalMap.playerMcOnPress` :89-108):
«перехватить» (`moveTo;trg=<id>;`), «приват», «подойти» (`moveTo;dx;dy` к
его точке). Кнопка «следовать» (`GlobalMapInterface.interceptPlayer`
:1159-1172) — то же `trg`; отмена — `moveTo;dy=1;dx=0;` (`GlobalMap.interceptPlayer`
:329-346). Любой `startMove` сбрасывает тумблер «следовать» (:1173-1176).

Своё движение: `moveTo;dx=<сотые>;dy=<сотые>;` относительно текущей позиции
(`DisplayGlobalMap.playerMove` :143-149). Скорость клиент не считает —
только `moveAck`/`userMove` от сервера; `server.py` использует 0.35 кл/с.

### Перехват (`trg`)

Клиент посылает цель, но не вычисляет момент перехвата. У B
`playerIntercepted()` истинно при незапрошенном `lcall`: прелоадер сообщает
«На Вас напали».

Текущий сервер (`Session.pursue/schedule_chase/caught`) меняет направление
погони раз в секунду, а контакт рассчитывает между проверками по относительной
скорости обоих игроков. Радиус контакта 0.3 клетки. Расчёт действует только
до ближайшего прибытия или изменения вектора; смена движения цели обновляет
таймер преследователя. Оба входят в клетку позиции цели в момент контакта,
даже если обработчик таймера задержался. Разрешение PvP определяется локацией;
сам перехват не создаёт отдельный боевой экземпляр и не включает `war=1`.

Подготовка перед боем: в клиенте есть `prepare;id=;time=;` с цифрами над
персонажем (`Location.as:94`, `Player.as:31`, `CharInfo.as:147`). Клиент
показывает `time-2` секунд; исходную длительность задавал сервер, в этих
обработчиках её нет. Текущий сервер `prepare` не отправляет. Связь этого
таймера именно с перехватом пока не подтверждена. Отдельная строка
«Начало сражения через N сек.» принадлежит battlegrounds:
`LocationInterface.as:1267`, `BattleGroundManager.as:236`. Это другой
обработчик, не доказательство длительности подготовки при перехвате.

### Метки

## 4. Транспорт

`core/transport/TransObject.as:26-35` (поля `ts_si`):

    ts_si;type=<typeID>;speed_mod=<k>;aggro_mod=<k>;g_cost=<сотые голды>;
          cost=<афро>;res=<..>;premium=<0|1|2>;name=<strid>;desc=<strid|пусто>;

- `speed_mod` — множитель: UI показывает `(speed_mod-1)*100 %` к скорости,
  `aggro_mod` — `(1-aggro_mod)*100 %` к агрессии мобов (`gpui/Annotation.as:944-945`).
  На **вес транспорт не влияет** (веса нет ни в `TransObject`, ни в UI).
  Как скорость применяется — решает только сервер (клиент скорость не считает).
- Запросы `ts_get_si;type=<id>;` идут окном 5 (`TransportFactory.as:7,16-49`);
  каждый обязан получить `ts_si` (`ts_si` уменьшает счётчик :51-56).
- Иконка `transport/<typeID>.swf` (`SSEmulator.getTransportIcon` :314-328);
  в `res/transport/` есть 1–36, 39–53, 60, 776–778, `FatBoy.swf`;
  `res/xml/transport.xml` — только манифест файлов (href/hash/size), без
  характеристик. Характеристики транспорта в клиенте отсутствуют.
- Арендодатель: `userInfo_Lessor;…;give_transport=|typeID..|;`
  (`Lessor.as:192-209`) → фабрика запрашивает `ts_si` по каждому.
- Аренда (`Rent.getTransport` :19-26, `CSM_TS_on_conv`):
  `on_conv;op=2;mob=<lessor id>;p1=<typeID>;p2=<дней>;` → `cmdAck;res=0`
  успех, иначе «недостаточно денег» (`TransRentInterface.getTransportAck`

## 5. Переходы между локациями

### Что читает клиент из XML локации

`LDParser.parseLD` :41-113: `obstacles` (шаг 5), `zones` (шаг 4), `sprite`,
`bgdecoration`, `background`. Ничего больше. `zones` → `LocationGrid.setZones`
:190-204 → флаг `cell.zone`. `inzones`, `warinzones`, `outzones`, `mobs`,
`serverdata` — **чисто серверные** (у нас `world.py` уже берёт `inzones` и
`mobs`; `warinzones` — точки появления в боевом состоянии, не используется).

### Как выглядит выход

`Location.finishMove` :175-183: мой ходок закончил путь на клетке с `zone` →
`exitLocation` :482-486 → окно `exitLoc` (`gpui/ExitLocationInterface.as`).
Две кнопки (:47-54): «на карту» → `Master.changeWorld()` → `chWorld;`;
«в другую локацию» → `changeWorld(1)` → `chWorld;to=1;` (`Location.exitLoc`
:487-500). В подлокации (`z != 0` в `g_id`, `Location.isSubLocation`
:793-801) кнопка «на карту» выключена (`ExitLocationInterface.as:24-27`);
кнопка выхода на панели тоже (`LocationInterface.as:704`). Кнопка выхода на
панели работает **с любой клетки** (`toGlobal` :712-719) — только на карту.
Во время боевого таймера выход запрещён (`startExitTimer` :1230-1245,
`leave_combat_timeout`).

Клиент **не сообщает, через какую зону выходит** — только `to=1`. Сервер
знает клетку игрока (конец последнего `path`) и по `outzones` находит сторону.

### Что в `outzones`

Проверено по всем 1381 файлам (`res/locations/static`): у 1357 есть
`outzones`, и множество клеток `outzones` == `zones` во всех 1357. Пятый
символ записи — сторона:

| Символ | Файлов | Где лежат клетки |
|--------|--------|------------------|
| `1` | 655 | западный край (x≤1) |
| `2` | 617 | северный край (y≤2) |
| `3` | 660 | восточный край |
| `4` | 682 | южный край |
| `a` | 362 | где угодно — «дверь A» |
| `b` | 273 | где угодно — «дверь B» |

Сторон на файл: одна — 537, две — 230, три — 127, четыре — 444, пять — 19.
Пустынные шаблоны (`desert/0001..0011`) и посёлки на клетках имеют `1..4`;
интерьеры — `a`/`b` (только `b`: 156 файлов — «Штаб», «Заброшенный
блок-пост», «Комната управления»; только `a`: 252 — «Минибункер»,
«Гробница», «Тир»; `a+b`: 76 — ярусы шахт). Клановые базы: `Enter` — `134`,
`lvl2_01` — `a`, `Sorting` — `2a`, `Lvl2_Transport` — `4`.

Что могло быть в `serverdata` (клиент не даёт подсказок, но из структуры
соседних тегов): список «сторона → id локации назначения + клетка/сторона
прибытия», параметры мобов. Восстановить из клиента нельзя.

### Предложение по восстановлению графа

1. **Уровень карты (z=0), стороны `1..4` — детерминированно, без данных.**
   Выход на западной стороне посёлка в клетке `(gx,gy)` ведёт в локацию
   клетки `(gx-1,gy)`: посёлок из `settlements.json` или пустыня
   (`world.location_at`). Прибытие — клетки `inzones` (в `war=1` —
   `warinzones`) у противоположного края. Так возвращается механика «идти
   пешком по пустыне», и клановые базы из 2–3 смежных клеток
   (`locations.xml`: «Плешь смерти» 5906×1888/1889, «Blackwater» 5923/5924×1838)
   соединяются сами.
2. **Интерьеры (`a`/`b`) — таблица `data/exits.json`** вида
   `{loc_id: {"a": target, "b": target, "1": …}}`, собранная руками по:
   - именам `fn`: региональные префиксы `WH_/DN_/Ab_/AH_/VH_/Top_/Dongola_`,
     суффиксы `_Enter/_lvl1/_lvl2/_Sorting/_Transport/_Bunker/_Mine_Enter`;
     цепочки заголовков («Шахта: Первый ярус» → «Второй ярус»);
   - клановым базам: родитель — клетка с «Кланбаза/Собственность клана …»,
     дочерние — все `KB_<клан>_*`;
   - фан-вики (описания локаций с «входами/выходами»);
   - правилу: если у интерьера ровно один выход, он ведёт к родителю.
   Инструмент: скрипт, который для каждого файла печатает стороны, число
   клеток, `fn`, `title` и кандидатов по префиксу, плюс проверка полноты
   (каждая сторона каждого файла покрыта). Пока таблицы нет — `/goto`.
3. Подлокациям выдавать `g_id` с `z != 0` (`LocIdToCoordinate.as:3-18`,
   `z = id >> 26`), чтобы кнопка «на карту» была выключена; выход `b`/`a`
   вести на родителя с `z = 0`.

### `deadloc/0..3`

Все четыре — «Граница пустоши», `war=1`, 64×128, пустой `obstacles`, а
`zones` — одна сплошная сторона: `0` — запад, `1` — север, `2` — восток,
`3` — юг. Id вида `0x40000000 | (k<<26)` (`SSEmulator.getLocDescription`
:55-58). Клиент к смерти их не привязывает (смерть — только окно
возрождения). Рабочая гипотеза: «тупиковые» локации края мира — их сервер
отдавал за пределами игрового прямоугольника, с единственным выходом
назад. Использовать так же: клетки вне `5833..6305 × 1600..2110` → `deadloc`
со стороной, обращённой внутрь.

## 6. Чат

`core/Chat.as:13-20` каналы: `0` локация, `1` отряд, `2` клан, `3` события,
`4` торговый, `5` помощь, `6` мир, `-1` приват. Каналы 3–6 создаются только
если включены в настройках (`Chat.userMsg` :154), иначе кадр молча
теряется; каналы 0, 1, 2 и приват — всегда.

### Клиент → сервер

`CSM_ChatMessage`: `userMsg;entry=@текст@;group=<N>;to=@ник@;`
- обычный канал: `group=N`, без `to`;
- приват: без `group`, `to=@ник@` (`ChatPan.sendMessage` :845-910 вырезает
  префикс `private Ник: `). Адресация **по нику**, id не участвует.
- Ограничения: ≤80 символов, пауза 3 с (`ChatPan.as:45-46`), длинные тексты
  режутся по 70 и шлются с префиксами `^0^…`, `^1^…`, `^2L^…` (:915-969);
  получатель склеивает по ключу `(group, from)` (`Chat.userMsg` :92-145) —
  **`entry` пересылать дословно, порядок сохранять**.
- Ответ: `cmdAck;res=0` — клиент **сам** печатает своё сообщение
  (`Chat.delivery` :242-256 → `newMessage`); `res=9` — печатает «Персонаж
  находится в офлайне … напишите ему письмо» (`ChatPan.showMessage` :712-714);
  другой `res` — тоже печатает (как от себя).

### Сервер → клиент

    userMsg;group=<N>;from=<id>;nick=@Ник@;entry=@текст@;      канал
    userMsg;from=<id>;nick=@Ник@;entry=@текст@;                приват (без group)
    userMsg;group=2;player=<id>;nick=@Ник@;entry=@..@;         клан: from := player (:79-82)

- `nick` — имя отправителя; без него клиент возьмёт `getName(from)`
  (:160-171) — имя сущности по id, если её нет → `***`. **Всегда слать `nick`.**
- `from` — id отправителя в системе координат получателя (свой = 0, но
  своё эхо слать не нужно). Для привата id может быть любым стабильным
  числом (ключ для склейки длинных сообщений).
- Служебные: `from=@server@`/`from=@events@` печатаются без ника
  (`createNewChannel` :331-334, `showMessage` :672-681, :702-713); для
  `group=3` («события») клиент ждёт `events`.
- Клик по нику в чате → `private Ник: ` в поле ввода; с карты — по id
  (`ChatPan.setPrivateToInputStr` :127-130).

Минимум для переписки двух игроков: канал 0 — рассылка по комнате
(кроме отправителя), приват — поиск сессии по нику, `res=9` если не в сети,
`group=6` — всем в мире.

Формат письма (`LetterObject.as`):
- `flag` :571-580: биты 0–3 тип, 4 «возвращённое», 5 «есть вложения»,
  6 «непрочитано», 7 «исходящее».
- `date` :670-693: `"YYYY-MM-DD HH:MM:SS"` в **UTC** (клиент сдвигает на
  локальный пояс).
- `body` :617-665: перед текстом может идти описание вложений
  `=?HS:<кол-во>?=`, `=?HC:<заряды>?=`, `=?BS:<износ>/<макс>?=` по одному
  блоку на предмет, затем текст. `items` — oid как строки (`"0"`/короткие
  игнорируются :722-730).
- Вложений до 5 предметов + афро + голда.
- Тарифы `svml` (`MailParam.as:742-752`): `data[0..7]` = торговое обычное
  (афро), торговое срочное (голда×100), клановое обычное, клановое срочное
  (голда×100), за кг обычное, за кг срочное, доставка обычная, доставка
  срочная; `time[i]` — секунды (UI делит на 60). Нечётные индексы — голда в
  сотых. Комментарий в `server.py:cmd_chkml` описывает раскладку неточно.
- Индикатор нового письма — по `read` у входящих
  (`GlobalMapInterface.checkNewLetter` :1177-1194); клиент спрашивает ящик
  сам, пуш не нужен, но `lsml` можно слать и без запроса — он просто
  дописывает.

## 10. Поля боя

`core/battlegrounds/BattleGroundManager.as` (:48-60 подписки `bg_init`,
`bg_op`, `bg_res`). Описания типов — `xmldocs/battlegrounds.xml` (HTTP,
:249-294): `0` «Гладиатор», `1` «Убей генерала».

Клиент → сервер `bg_op;type=<тип>;ts=<размер>;op=<N>;` (:21-28):
`0` встать в очередь (ждёт `cmdAck`, :337-356), `1` очередь отрядом,
`2` выйти из очереди (`cmdAck`), `3` согласен, `4` отказ, `5` покинуть
незавершённое, `6` запросить состояние, `7` покинуть завершённое.
Для `op` 3–7 `cmdAck` **не регистрируется** (PROTOCOL §7).

Сервер → клиент:
- `bg_init;type_list=|..|;ts_list=|..|;` (:199-221) — доступные типы и
  размеры (UI `BattleGroundInterface`).
- `bg_op;type=;ts=;op=;par=;` (:222-248): `op=0` приглашение (окно
  да/нет), `op=1` до начала `par` секунд (таймер «Начало сражения через …»,
  `LocationInterface.startBGPrepareTimer` :1267-1283), `op=2` бой идёт.
- `bg_res;team_win=;players_0=|..|;kills_0=|..|;deaths_0=|..|;players_1=;kills_1=;deaths_1=;`
  (:179-198) — итоги (id в координатах получателя, свой = 0).
- Локация БГ — `g_id` с установленным битом 31 (`Location.isBGLocation`
  :802-810); тогда через 1.5 с после загрузки клиент сам шлёт `op=6`
  (`Master.locLoaded` :236-239). `bg_rep`/`bg_pen` в `userInfo` — репутация
  и штраф БГ.

## 11. Дом, смерть, возрождение, админ-команды

- «Прописка»: NPC с `can_set_home=1` в `userInfo_*` получает услугу
  `Attendance.SET_HOME` (`NPC.as:44-50`), активация →
  `on_conv;mob=<npc id>;op=0;` (`Attendance.activate` :38-45,
  `CSM_Conv(mob, op)`), ответ `cmdAck`. `SetHomeInterface` пустой —
  никакого UI подтверждения. Лечение у медика — `op=1` (`Healer.as:18`).
  Сервер хранит `home_loc` персонажа; `server.py` уже ставит
  `can_set_home=1` коммонерам.
- Флаг смерти: `persInfo;…;death=1` (`PersGenerator.persInfo` :116-132) и
  `lch;dead=0`. В обоих случаях после `lenter`/`gmap` открывается окно
  `regeneration` (`Master.as:196-199, 283-286`; `Resurrector.resurrectGamer` :12-18).
- Окно (`gpui/RegenerationInterface.as`): бесплатно (`res_type=0`,
  автоматически через 15 с, :122-142), за 5 голды (`1`), за 500 афро (`2`)
  → `resurrect;res_type=N;` → `cmdAck;res=0` закрывает окно и возвращает
  `LOCAL_STATE` (`resurrectAck` :27-45); при `res≠0` таймер идёт дальше.
  Куда и с каким HP возродить — сервер (`lcall` в дом / та же локация).
- `deadloc` — см. §5: к смерти не привязаны.
- `kickban;admin=@@;seconds=N;reason=@@;` и `shutdown;seconds=N;`
  (`core/Session.as:199-221`) — только показывают окно; соединение сервер
  рвёт сам.

## 12. Расхождения `server/server.py` с клиентом

1. `EXPECTS_ACK` содержит `updMark` (`server.py:40`), а клиент на `updMark`
   `cmdAck` не регистрирует (`GlobalMap.editMark` :231-251) → лишний ack
   сдвигает FIFO. Убрать.
2. `cmd_userMsg` (`server.py:384`) возвращает отправителю его же `userMsg` —
   по коду клиента (`Chat.delivery` :242-256) это дубль строки. Проверить
   в игре; если дублируется — слать только `cmdAck`.
3. `cmd_getInfo` (`server.py:517`) шлёт `tr=0;tr_hours=0` — клиент считает,
   что транспорт есть (§4). Не слать без транспорта.
4. `cmd_chWorld` (`server.py:334`) игнорирует `to`: «в другую локацию»
   (`to=1`) сейчас выкидывает на карту. Нужна ветка по стороне выхода (§5).
5. После `gmap` не отправляется `marks` — метки не инициализируются.
6. NPC id `100+` на локацию (`FIRST_NPC_ID`, `server.py:71`) — при появлении
   второго игрока нужен непересекающийся диапазон id игроков (§1).
7. Комментарий к `svml` в `cmd_chkml` (`server.py:625`): индексы 4–5 —
   «за кг», 6–7 — «доставка» (`MailParam.as`), а не повтор четырёх тарифов.

## 14. Минимум «два игрока видят друг друга и переписываются»

Ровно эти кадры, ничего сверх:

1. **Сессии и id.** Игроку A назначить `id_A = 1_000_000 + char_id`. В
   каждом кадре, идущем клиенту X, id X заменять на `0`.
2. **Вход в локацию** (после `lenter` и `populate`):
   - A получает по каждому B в комнате:
     `lch;newUser=<id_B>;pos=<pos_B>;rtype=-1;`
   - каждый B получает: `lch;newUser=<id_A>;pos=<pos_A>;rtype=-1;`
3. **Ответы на запросы клиента** (он пришлёт их сам):
   - `getInfo;type=0;id=<id_B>` → `userInfo_Player;id=<id_B>;name=@Ник@;sex=<0|128>;res=@<avatar>@;ail=0;ally=1;lvl=1;rep=|0|;bg_rep=0;bg_pen=0;hl=0;pr=0;`
     и следом `usrUp;id=<id_B>;hcur=100;hmax=100;scur=100;smax=100;`
   - `ss_get;target=<id_B>;slot=3` → `ss_ack;o_list=|;` (уже есть).
4. **Движение.** На `moveTo;path` от A: `cmdAck;res=0` → A, затем
   `userMove;id=0;path=|..|` → A и `userMove;id=<id_A>;path=|..|` → всем B.
   `pos_A` = последняя клетка (для новых входящих).
5. **Уход.** При `chWorld`, `/goto`, разрыве: всем B —
   `lch;lostUser=<id_A>;`.
6. **Чат.** На `userMsg;entry;group=0` от A: `cmdAck;res=0` → A (без
   эха); всем B в комнате — `userMsg;group=0;from=<id_A>;nick=@НикA@;entry=@..@;`.
   На `userMsg;entry;to=@НикB@` (без `group`): найти сессию по нику; есть —
   `cmdAck;res=0` → A и `userMsg;from=<id_A>;nick=@НикA@;entry=@..@;` → B;
   нет — `cmdAck;res=9`.
7. **Карта** (если оба вышли на неё): при `gmap` для A — по каждому B в
   радиусе `newUser;id=<id_B>;dx=<gxA-gxB>;dy=<gyA-gyB>;` +
   `userMove;id=<id_B>;dx=<gxB>;dy=<gyB>;vx=0;vy=0;t=0;`, симметрично для B;
   раз в 2 с всем видимым `userMove` с текущей позицией и скоростью;
   `userLost;id=` при уходе с карты. И `marks;dxdy=|;title=|;info=|;` после `gmap`.

Проверка: у обоих над фигурой «[1] Ник», в списке игроков карты — ник и
портрет, сообщения в канале «Локация» видны один раз у каждого.
