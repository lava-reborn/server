# LAVA Online — протокол клиент/сервер

Восстановлено из `res/main.swf` (ActionScript 2, SWF v9) декомпиляцией JPEXS FFDec.
Исходник классов: `recon/as-src/lol/`. Ключевые файлы:
`lol/server/XMLConnection.as`, `lol/server/SCDataParser.as`,
`lol/server/mess/CSMessage.as`, `lol/core/Session.as`.

## 1. Транспорт

Flash `XMLSocket` поверх сырого TCP. Кадр = строка, завершённая байтом `0x00`.
Несмотря на имя, XML **не используется**: клиент оборачивает строку в `new XML(str)`,
получая текстовый узел, а на приёме делает `xml.childNodes.join("")`.
То есть на проводе — plain text.

Кодировка: **UTF-8**. Flash разбирает трафик `XMLSocket` как UTF-8, если не
включён `System.useCodepage`, а клиент выставляет его лишь в одной редко
достижимой ветке экрана входа. Функция `convertToCP1251` относится к
`MD5rus` и описывает только то, что подаётся на вход хешу пароля, а не то,
что едет по проводу.

Ошибка здесь не даёт внятного сбоя: разборщик клиента после каждой строки
двигает курсор на её длину **в символах**, поэтому значение, раскодированное
в другую длину, сдвигает все последующие поля кадра.

Адрес по умолчанию из `settings.db`:

    host = game.lava-online.ru
    port = 9775

## 2. Формат кадра

    <имя_команды>;<ключ>=<значение>;<ключ>=<значение>;

Генерация — `CSMessage.toString()`. Разбор — `SCDataParser.parse()`.
Имя команды = всё до первой `;`.

## 3. Типы значений

Тип определяется **первым символом** значения (`SCDataParser.getData`):

| Префикс      | Тип              | Формат                        | Пример                |
|--------------|------------------|-------------------------------|-----------------------|
| цифра, `+`, `-` | число         | `key=123;`                    | `res=0;`              |
| `@`          | строка           | `key=@текст@;`                | `name=@Вася@;`        |
| `H` / `h`    | hex-число        | `key=Hxxxx;`                  | `color=HFF00AA;`      |
| `x`          | big unsigned int | `key=xNNNN;` (хранится строкой) | `id=x4294967296;`   |
| `\|`         | список           | см. ниже                      |                       |

Списки (`getListData`):

- пустой: `key=\|;`
- числовой: `key=\|1\|2\|3\|;`
- строковый: `key=\|@a@\|@b@\|;`  (разделитель `@\|@`, терминатор `@\|;`)
- big-uint: `key=\|xN\|xM\|;`

Строки проходят через `XMLString.unescape()` — см. `recon/as-src/lol/server/XMLString.as`.

## 4. Рукопожатие

Полная последовательность из `lol/core/Session.as`:

1. **HTTP**, вне сокета: `GET http://www.lava-online.ru/client/game_session.php?session=<S>`
   Ответ — строка-хеш. Ответ `0` или пусто = отказ.
   Сессия `S` берётся из `_root.session` (flashvars от лаунчера).
2. TCP connect на `host:port`.
3. Клиент → `hello;minor=2;major=0;`
4. Сервер → кадр с именем `hello` (параметры клиент игнорирует).
   Таймаут 20 с, иначе клиент рвёт соединение (`closeWithoutHelloResponse`).
5. Клиент → `login;hash=@<хеш>@;`
6. Сервер → `cmdAck;res=0;`
   `res=0` — успех, клиент вызывает `persGen.loadDescription()` и идёт дальше.
   Любое другое значение — отказ.

Прочие служебные команды сервера: `kickban;admin=@..@;seconds=N;reason=@..@;`,
`shutdown;seconds=N;`.

## 7. Правила очередей (обязательны)

`lol/server/XMLCCallStack.as`: клиент регистрирует обработчик в момент отправки
команды и снимает **первый пришедший** `cmdAck`. Очередь строго FIFO.
Лишний или пропущенный ответ сдвигает её целиком, и дальнейшие ответы
достаются чужим обработчикам.

- Ровно один `cmdAck` на каждую команду, которая его ждёт, в порядке получения.
- `selPers` подтверждения **не ждёт** — отвечать на неё нельзя.
- Для `bg_op` с `op` 3..7 подтверждение тоже не регистрируется.
- Отдельные независимые очереди: `ctml` (почта), `ah_sresult` (аукцион).
- `ctml` шлётся **только** при `res == 0`; иначе клиент снимает ожидание сам.

Окна конвейера (сервер обязан отвечать на каждый запрос, иначе клиент встаёт):

| Запросы                          | Окно |
|----------------------------------|------|
| `q_si`, `q_di`, `q_status`       | 1    |
| `ss_get_si`, `ss_get_di`         | 5    |
| `ts_get_si`                      | 5    |

## 8. Поправки к разделу 5

Файл `recon/notes/sc_commands.txt` собран из всех вызовов `addEventListener`
и потому содержит внутренние события клиента наравне с сетевыми командами.
Сервер **не должен** слать: `questLoaded`, `questUpdate`, `completed`,
`closedQuest`, `repAck`, `chatRes`, `uiUpd`, `userUpdate`, `actionPoints`,
`regAck`, `addItem`, `removeItem`, `itemUpdate`, `addBag`, `removeBag`,
`transferAll`, `onLoot`, `openPartyPlayerMenu`, `ADD_LOT`, `proposeJoinBG`,
`dead`, `aim`, `fire`, `enemy`.

Отдельно: `fireAck` клиент подписывает, но обработчика не существует —
команда мёртвая, слать её бессмысленно.

Наоборот, в списке **отсутствуют** три реальные команды сервера, потому что
подписка на них динамическая: `ss_ack` (ответ на `ss_get`), `ctml`
(контрольный пакет почты), `ah_sresult` (шапка результата поиска аукциона).

Уточнения семантики:

- `rp_get_info` / `rp_info` — это атрибуты, навыки и специализации, а не репутация.
- `c_ga` — банковская конвертация валют, а не клановая команда.
- Смерть приходит как `lch;dead=<id>;`, отдельной команды нет; при входе —
  флагом `persInfo;death=1`. Подробно: §12.
- `updWeight` — вес банковского хранилища, а не переносимый вес персонажа.

## 9. Отсутствующий файл текстов

`res/database/texts.xml` (20.8 МБ по манифесту) в клиенте **отсутствует** —
это один из двух недостающих файлов из 25 918. Имена и описания предметов,
названия и тексты квестов, имена NPC и их реплики передаются по сокету
**числовыми идентификаторами строк**, а сам текст клиент тянет отдельным
HTTP-запросом.

Формат восстановлен из `lol/utils/StringCollector.as`:

    запрос:  POST <base>/database/texts.xml   телом <data>12,34,56</data>
    ответ:   <любой корень><s id="12">текст</s><s id="34">...</s></любой корень>
    также:   GET <base>/database/texts.xml?all=1  отдаёт всё разом

Имя корня и тегов не проверяется, читается только атрибут `id`, содержимое
проходит через `unescape`. Поддерживаемые макросы в текстах: `%имя%`,
`%sex?мужская:женская%`, `<hint>...</hint>`, обычный HTML.

**Без этого эндпоинта инвентарь не работает:** предмет не попадает в рюкзак,
пока не придёт строка его имени.

### `?all=1` обязан отдавать всё, иначе игрока выбрасывает на логин

Самая дорогая ловушка во всём клиенте. `StringCollector` — вечный синглтон, и
`SBase.initializeStringCollector` подписывается на его событие `update`,
**никогда не отписываясь**:

    StringCollector.parse()   → dispatchEvent("update")   ← на КАЖДУЮ пачку строк
    SBase.initializeLocationNames → GetLocName.loadXML() → dispatchEnding
    dispatchEnding            → SBase.dispatchEvent("onLoad")
    Session.loadSBase         → SceneShifter.enterScene()  ← экран входа

`Session.loadSBase` снимает слушателя с `SSettings`, но не с `SBase`, поэтому
подписка живёт всю сессию. Итог: **любая строка, догруженная после входа в
мир, перезапускает сцену и поднимает окно авторизации поверх игры.** Со второго
раза вход проходил, потому что строки уже лежали в `stringCollection` и пачка
не запрашивалась. Тот же механизм ронял торговлю: открытие лавки просило имена
товаров.

Оригинальный сервер на это не натыкался, потому что его `?all=1` отдавал все
20.8 МБ сразу и клиент больше ни за чем не обращался. Значит заглушка обязана
делать то же самое. Это выполнимо: все идентификаторы строк приходят от
сервера, в SWF нет ни одного `getString` с литералом — проверено по всем
вызовам (`Item`, `Entity`, `NPC`, `Quest`, `Effect`, `SetObject`,
`TransObject`). У нас таблица закрыта целиком: 35 470 строк, 1.6 МБ.

**Признак поломки:** `database/locations.xml` в HTTP-логе запрошен больше
одного раза. Три запроса = цепочка прокрутилась дважды.

## 9a. Идентификатор локации и глобальная карта

`SSEmulator.getLocDescription` разрешает id локации в файл, и **сервер обязан
разрешать так же**: обе стороны читают из выбранного файла сетку проходимости,
и расхождение означает, что игрок ходит сквозь нарисованные стены.

    locations/static/<id>.xml    если такой файл есть в манифесте
    id >> 28 == 4                locations/deadloc/<(id >> 26) & 3>.xml
    id >> 26 == 0                пустошь: gx = id >> 13, gy = id & 0x1FFF,
                                 тайл ((gx + gy) & 3) + 1 из четырёх

Последнее правило — ключевое: **клетка карты, на которой ничего нет, сама себе
id локации**. Поэтому вся карта проходима без единой таблицы, а `g_id` в `lcall`
и id пустоши — это одно и то же число.

Таблица «клетка → посёлок» была серверной и утрачена. Восстановлено 86 клеток
склейкой подсказок карты (`database/locations.xml`, 414 клеток) с атрибутом
`title` файлов `locations/static` — `data/build_settlements.py`. Одноимённые
места (шесть «Лагерей мастеров») разводятся по региону: кандидат, делящий слово
с уже привязанными соседями. Это правило само воспроизвело клетку 5970x1730 →
102, проверенную игрой.

**Проходимость карты тоже была серверной и утрачена; восстановлена из
тайлов.** Правило выше даёт локацию для любой клетки, но не право туда идти.
На карте клиент не спрашивает ничего: `moveAck` задаёт только скорость, и
дальше фигурка экстраполирует сама (`GlobalMap.moveAck` → `MapObject.startMove`),
поэтому рельеф держит исключительно сервер. Таблица восстановлена из самих
картинок карты — `res/globalmap/full`, 256 тайлов 256×256 на прямоугольник
5833..6305 × 1600..2110, ровно 8×8 пикселей на клетку (`data/build_terrain.py`):
шероховатость фотографии (среднее отклонение яркости внутри клетки, сглаженное
по 3×3) выше 20 — горы; средний синий выше среднего красного — вода;
нарисованные поверх значки посёлков и подписи распознаются по цвету, которого
в спутниковом снимке пустыни не бывает, и такие клетки не меряются, а
достраиваются от соседей; 262 клетки посёлков и 414 клеток подсказок
(`database/locations.xml`) открыты независимо от картинки — там игроки стояли.
Итог в `data/map_terrain.json` (92.47% клеток проходимы, 6.88% горы, 0.65%
вода), проверки и сомнительные места — в `data/map_terrain_report.md`.
Нубийская долина при этом выходит замкнутой, как её и помнит игрок: пешком
из неё не выйти.

Сервер: `world.passable(gx, gy)` (пол, как `location_at`; за прямоугольником
карты — непроходимо), `travel.walk` идёт по лучу клетка за клеткой
(обход сетки Amanatides & Woo) и обрезает ход перед первой непроходимой,
`move_on_map` везёт игрока по остатку и таймером подтверждает прибытие там.
Ход, которому некуда идти, подтверждается **тем же кадром, что и прибытие** —
`userMove;id=0;dx=;dy=;vx=0;vy=0;`: только он и ставит фигурку на место, и
гасит экстраполяцию (`GlobalMap.userMove` → `walker.x/y` → `startMove(0,0,0)`).
Пустой `moveAck` остановил бы её там, куда клиент уже успел дорисовать, а
`cor_pos` — кадр локации, карта его не слушает. Подтверждения (`cmdAck`)
`moveTo` не требует ни в одной из форм, так что отказ очередь не сдвигает.

`outzones` в локации говорит, откуда можно выйти и **в какую сторону**
(пятый символ записи: `1`..`4` = W/N/E/S, `a`/`b` — дверь), но не куда: цель
лежала в `serverdata`, а он вычищен во всех 1381 файлах. Клиент, встав на
клетку зоны, шлёт `chWorld;to=1;` без указания зоны, ждёт `cmdAck;res=0` и
затем `lcall` (`Master.changeWorld(1)` → `changeWorldAck` → `lcall`); любой
другой `res`, кроме 39, молча возвращает его в прежнее состояние. Сервер
(`server/travel.py`) читает сторону по клетке игрока: W/N/E/S → соседняя
клетка карты (`world.location_at`, север = `gy−1`), прибытие на
противоположный край; двери — по `data/exits.json`, восстановленному лишь
частично, иначе отказ. За прямоугольником карты 5833..6305 × 1600..2110 —
`locations/deadloc/<k>.xml` с одной зоной выхода на стороне `k` (0 W, 1 N,
2 E, 3 S), id `(4<<28)|(k<<26)`; ему отдаётся `g_id` с `z≠0`, и клиент
отключает выход на карту (`Location.isSubLocation`).

Клиент **не разбирает слэш-команды** — всё набранное уходит в `userMsg` как
есть, поэтому серверные команды чата свободны.

## 10. Экранирование строк

`lol/server/XMLString.as` — процентное кодирование по собственной таблице,
применяется **в обе стороны**:

| Символ | Код   |
|--------|-------|
| `%`    | `%25` |
| `<`    | `%3C` |
| `>`    | `%3E`  |
| `'`    | `%27` |
| `"`    | `%5C` |
| `&`    | `%26` |
| `@`    | `%40` |

Двойная кавычка кодируется как `%5C`, то есть процентным кодом обратного
слеша, а не `%22`. Это особенность оригинала, и её надо воспроизводить:
клиент декодирует `%5C` обратно в кавычку.

Экранирование `@` обязательно: незакодированный символ в нике оборвёт
значение вида `@строка@` раньше времени и разрушит кадр.

## 11. Мир, координаты, движение

### Сетка локации

Гексагональная. Номер клетки в кадрах `pos` и `path`:

    pos = gy * width + gx

`width` берётся из атрибута XML локации: 64 у 1270 файлов, 32 у 126.
Шаг анимации 200 мс на гекс, стоимость хода 1 очко действия за гекс,
и то и другое захардкожено в клиенте.

### Три формы команды движения

| Форма                     | Где работает | Единицы                       |
|---------------------------|--------------|-------------------------------|
| `moveTo;path=\|12\|13\|;` | локация      | номера гексов, первый текущий |
| `moveTo;dy=-250;dx=140;`  | глобальная   | **сотые доли** клетки, смещение |
| `moveTo;trg=12345;`       | глобальная   | перехват игрока по id         |

Отмена перехвата — это `moveTo;dy=1;dx=0;`.

### Позиция: сервер авторитетен полностью

Клиент **не двигается сам**. Отправив `moveTo`, он только запоминает цель.
Анимация стартует исключительно по серверному `userMove`. Значит путь надо
возвращать эхом, в том числе самому отправителю.

Коррекция: `breakMv;id=;pos=;` телепортирует на клетку,
`cor_pos;id=;pos=;` делает то же и **автоматически перевыдаёт** путь до
ранее выбранной цели, то есть игрок сам допройдёт.

Клиент валидирует свою заявку сам (поиск пути в окне 30×40, препятствия,
занятость клеток в боевых локациях), но это обходится модифицированным
клиентом. Сервер обязан проверять путь заново.

### Обязательный heartbeat на глобальной карте

`lol/core/globmap/MapObject.as`: у каждого чужого игрока крутится секундный
таймер, сбрасываемый только приходом `userMove`.

| Молчание | Что происходит          |
|----------|-------------------------|
| 3 с      | объект гаснет           |
| 6 с      | объект удаляется молча  |

**Сервер обязан слать `userMove` по каждому видимому игроку не реже чем
раз в 3 секунды, даже когда тот стоит** (`vx=0;vy=0;`). Иначе игроки будут
беспричинно исчезать друг у друга.

Единицы в разных кадрах разные, это легко перепутать: `newUser` и `marks`
несут целые клетки относительно игрока, `userMove` — абсолютные координаты
плюс скорость в клетках в секунду, `moveTo` — сотые доли клетки.

### Метки адресуются индексом

`updMark;id=` и `rmMark;id=` передают **индекс в клиентском массиве**,
а не ключ базы. Сервер обязан хранить метки упорядоченным списком на
персонажа, и порядок в кадре `marks` должен совпадать с тем, по которому
потом придут эти индексы.

### geoID

    x = (id & 0x3FFE000) >> 13
    y =  id & 0x1FFF
    z =  id >> 26          # ненулевое = подлокация, выход на глобалку запрещён

Разрешение идентификатора в файл: сначала `locations/static/<id>.xml`, если
он есть в манифесте; иначе мёртвая локация; иначе процедурная пустошь, где
из одиннадцати шаблонов реально используются только четыре.

## 12. Состояние DEAD

Отдельной команды «ты умер» нет: смерть приходит двумя разными путями, и оба
кончаются одним окном.

**По ходу боя** — `lch;dead=<id>;`. Про чужого это «положить фигуру»
(`Location.lch` → `DisplayLocScene.dead`), про себя (`id == 0`, как всегда
про получателя) — `Resurrector.lch` → `resurrectGamer()`: `Master.currentState
= DEAD_STATE` и окно `regeneration`. Сервер шлёт его в комнату обычным
броадкастом, где свой id и так станет нулём.

**При входе** — `persInfo;…;death=<0|1>;`. Это **флаг, а не счётчик смертей**:
`PersGenerator.persInfo` кладёт его как `PersInfo.dead = Boolean(param.death)`
(парсер даёт число, так что `death=0` — это `false`), а окно поднимает уже
`Master.lenter` и `Master.gmap`, каждый по `gamer.playerInfo.dead`, — то есть
**после** того, как персонаж где-то встал. Поэтому вошедший мёртвым обязан
получить обычные `lcall` → `lenter` и попасть в комнату: отказать ему во
входе — значит оставить клиента в пустоте без окна. На сервере флаг живёт в
колонке `characters.death`.

В `DEAD_STATE` фильтр клиента (`FilterManager.createDSFilter`) не выпускает
ничего, кроме `resurrect`, — но переходит клиент в это состояние **после**
`lenter`, а не до, и конвейерные запросы (`ss_get`, `q_si`, `getInfo` и
прочие из §7) успевают уйти раньше. Серверная копия фильтра
(`combat.DEAD_PASSES`) поэтому режет только действия, пропуская вход и
запросы: пропущенный `ss_get` навсегда закрывает окно `ss_ack`.

`resurrect;res_type=<0|1|2>;` ждёт ровно один `cmdAck`. Только `res == 0`
закрывает окно и возвращает `LOCAL_STATE`; любой другой код клиент
показывает **никак** — `RegenerationInterface` просто перезапускает свой
15-секундный отсчёт и по его истечении сам нажимает «бесплатно» ещё раз. Это
и делает отказ пригодным для платы временем. Куда и с каким HP поднять тело —
дело сервера: клиент после `cmdAck;res=0` ничего не меняет, кроме окна, так
что `lcall` домой идёт следом за подтверждением, а HP приезжает обычным
`usrUp` на первый же `getInfo` после `lenter`.
