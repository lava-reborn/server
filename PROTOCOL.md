# LAVA Online — протокол клиент/сервер

Восстановлено из `res/main.swf` (ActionScript 2, SWF v9) декомпиляцией JPEXS FFDec.
Исходник классов: `recon/as-src/lol/`. Ключевые файлы:
`lol/server/XMLConnection.as`, `lol/server/SCDataParser.as`,
`lol/server/mess/CSMessage.as`, `lol/core/Session.as`.

## 1. Транспорт

Flash `XMLSocket` поверх сырого TCP. Кадр = строка, завершённая байтом `0x00`.
Несмотря на имя, XML **не используется**: клиент оборачивает строку в `new XML(str)`,
получая текстовый узел, а на приёме делает `xml.childNodes.join("")`.
То есть на проводе — plain text.

Кодировка: **UTF-8**. Flash разбирает трафик `XMLSocket` как UTF-8, если не
включён `System.useCodepage`, а клиент выставляет его лишь в одной редко
достижимой ветке экрана входа. Функция `convertToCP1251` относится к
`MD5rus` и описывает только то, что подаётся на вход хешу пароля, а не то,
что едет по проводу.

Ошибка здесь не даёт внятного сбоя: разборщик клиента после каждой строки
двигает курсор на её длину **в символах**, поэтому значение, раскодированное
в другую длину, сдвигает все последующие поля кадра.

Адрес по умолчанию из `settings.db`:

    host = game.lava-online.ru
    port = 9775

## 2. Формат кадра

    <имя_команды>;<ключ>=<значение>;<ключ>=<значение>;

Генерация — `CSMessage.toString()`. Разбор — `SCDataParser.parse()`.
Имя команды = всё до первой `;`.

## 3. Типы значений

Тип определяется **первым символом** значения (`SCDataParser.getData`):

| Префикс      | Тип              | Формат                        | Пример                |
|--------------|------------------|-------------------------------|-----------------------|
| цифра, `+`, `-` | число         | `key=123;`                    | `res=0;`              |
| `@`          | строка           | `key=@текст@;`                | `name=@Вася@;`        |
| `H` / `h`    | hex-число        | `key=Hxxxx;`                  | `color=HFF00AA;`      |
| `x`          | big unsigned int | `key=xNNNN;` (хранится строкой) | `id=x4294967296;`   |
| `\|`         | список           | см. ниже                      |                       |

Списки (`getListData`):

- пустой: `key=\|;`
- числовой: `key=\|1\|2\|3\|;`
- строковый: `key=\|@a@\|@b@\|;`  (разделитель `@\|@`, терминатор `@\|;`)
- big-uint: `key=\|xN\|xM\|;`

Строки проходят через `XMLString.unescape()` — см. `recon/as-src/lol/server/XMLString.as`.

## 4. Рукопожатие

Полная последовательность из `lol/core/Session.as`:

1. **HTTP**, вне сокета: `GET http://www.lava-online.ru/client/game_session.php?session=<S>`
   Ответ — строка-хеш. Ответ `0` или пусто = отказ.
   Сессия `S` берётся из `_root.session` (flashvars от лаунчера).
2. TCP connect на `host:port`.
3. Клиент → `hello;minor=2;major=0;`
4. Сервер → кадр с именем `hello` (параметры клиент игнорирует).
   Таймаут 20 с, иначе клиент рвёт соединение (`closeWithoutHelloResponse`).
5. Клиент → `login;hash=@<хеш>@;`
6. Сервер → `cmdAck;res=0;`
   `res=0` — успех, клиент вызывает `persGen.loadDescription()` и идёт дальше.
   Любое другое значение — отказ.

Прочие служебные команды сервера: `kickban;admin=@..@;seconds=N;reason=@..@;`,
`shutdown;seconds=N;`.

Клиент с патчем `tools/widescreen.py` добавляет в `hello` параметр `online`.
Для `online=1` или `online=2` сервер присылает `online;count=N;` при входе персонажа
в игру и при изменении числа игроков. Считаются персонажи из `ONLINE`,
включая самого игрока, игроков на глобальной карте и клиентов без патча.
Экран входа и создание персонажа в счёт не входят. Переход между локациями
не меняет число. Это уведомление без `cmdAck`; клиент хранит последнее
значение между сценами и показывает его на верхней панели обеих сцен.
Без `online` последовательность кадров остаётся прежней.

С `online=2` (так отвечает нынешний патч) в том же кадре идут ники:
`online;count=N;names=|@Ник1@|@Ник2@|;`, все игроки онлайн, по алфавиту без
учёта регистра. Строковый список не экранируется (`protocol.RawList`), поэтому
символы `; = @ |` в нике заменяются похожими (`clans.list_safe`). Клиент
показывает список под счётчиком и по конверту готовит приват в строке чата.
Кадр по-прежнему без `cmdAck`, клиенты с `online=1` получают его без `names`.

## 7. Правила очередей (обязательны)

`lol/server/XMLCCallStack.as`: клиент регистрирует обработчик в момент отправки
команды и снимает **первый пришедший** `cmdAck`. Очередь строго FIFO.
Лишний или пропущенный ответ сдвигает её целиком, и дальнейшие ответы
достаются чужим обработчикам.

- Ровно один `cmdAck` на каждую команду, которая его ждёт, в порядке получения.
- `selPers` подтверждения **не ждёт** — отвечать на неё нельзя.
- Для `bg_op` с `op` 3..7 подтверждение тоже не регистрируется.
- `ss_upd;s_status=0` — закрытие любой сессии (лавка, банк, учитель, лут,
  бартер, трофеи) — подтверждения не ждёт, в том числе от мёртвого.
- Бартер (`s_type=2`, `server/barter.py`): 2 (отказ), 5 (готов), 6 (не готов)
  тоже без подтверждения; 1, 3, 4, 7, 8 — с ним. Объект `Barter` клиента
  умирает только в `close()`, поэтому после **любого** конца бартера (отказ,
  отмена, обмен) сервер шлёт `ss_upd;s_status=0` каждому, у кого он жив, —
  иначе клиент не примет следующего приглашения. `Barter.kill` снимает с
  очередей один `ss_ack` окна и до двух переносов 3/4: пришедшие после
  нашего закрытия такие кадры сервер глотает, остальные — отказ.
- Окно бартера клиент закрывает и сам: `applyBarter` срабатывает, как только
  в **его** окне горят обе лампочки, ещё до отправки своего 5. Поэтому 5 из
  окна, где лампочка другой стороны могла гореть, хотя сервер её уже погасил
  (изменение стола ещё в пути или 5 разминулся с изменением), не отвечается
  6/5, а кончает бартер: `ss_upd 0` обоим и честный рюкзак. Если чужой 5 мог
  разминуться с изменением самого игрока, сервер вслед за `cmdAck` шлёт ему
  6, чтобы погасить лампочку, которую больше ничто не погасит.
- Все окна сессий модальные, поэтому новый `ss_create` значит, что прежнего
  окна уже нет, даже если его `ss_upd 0` не пришёл: сервер забывает лавку,
  банк, учителя, мешок и прочие сессии (`Session.windows_gone`). Если игрок в
  бартере, окна бартера у него на экране быть не может: такой `ss_create`
  получает отказ 31, а бартер кончается (`ss_upd 0` идёт после отказа).
- Отдельные независимые очереди: `ctml` (почта), `ah_sresult` (аукцион).
- `ctml` шлётся **только** при `res == 0`; иначе клиент снимает ожидание сам.

Окна конвейера (сервер обязан отвечать на каждый запрос, иначе клиент встаёт):

| Запросы                          | Окно |
|----------------------------------|------|
| `q_si`, `q_di`, `q_status`       | 1    |
| `ss_get_si`, `ss_get_di`         | 5    |
| `ts_get_si`                      | 5    |

## 8. Поправки к разделу 5

Файл `recon/notes/sc_commands.txt` собран из всех вызовов `addEventListener`
и потому содержит внутренние события клиента наравне с сетевыми командами.
Сервер **не должен** слать: `questLoaded`, `questUpdate`, `completed`,
`closedQuest`, `repAck`, `chatRes`, `uiUpd`, `userUpdate`, `actionPoints`,
`regAck`, `addItem`, `removeItem`, `itemUpdate`, `addBag`, `removeBag`,
`transferAll`, `onLoot`, `openPartyPlayerMenu`, `ADD_LOT`, `proposeJoinBG`,
`dead`, `aim`, `fire`, `enemy`.

Отдельно: `fireAck` клиент подписывает, но обработчика не существует —
команда мёртвая, слать её бессмысленно.

Наоборот, в списке **отсутствуют** три реальные команды сервера, потому что
подписка на них динамическая: `ss_ack` (ответ на `ss_get`), `ctml`
(контрольный пакет почты), `ah_sresult` (шапка результата поиска аукциона).

Уточнения семантики:

- `rp_get_info` / `rp_info` — это атрибуты, навыки и специализации, а не репутация.
- `c_ga` — банковская конвертация валют, а не клановая команда.
- Смерть приходит как `lch;dead=<id>;`, отдельной команды нет; при входе —
  флагом `persInfo;death=1`. Подробно: §12.
- `updWeight` — вес банковского хранилища, а не переносимый вес персонажа.
  По сети его нет: это внутреннее событие окна банка, а сервер шлёт
  `ss_upd;s_status=3;obj=x<граммы hex>` (вместимость) и `s_status=4` (занято).
  Только x-hex: `Bank.ss_upd` читает `Number("0x" + obj)`.
- Банк (`ss_create;s_type=3`): «положить» `ss_upd;s_status=1;obj=x<oid>` и
  «взять» `s_status=2` сами предмет не переносят — после `cmdAck;res=0` сервер
  обязан прислать `ss_obj_status` 0 или 1 с тем же oid. «Расширить» —
  `s_status=6` без obj.

## 9. Отсутствующий файл текстов

`res/database/texts.xml` (20.8 МБ по манифесту) в клиенте **отсутствует** —
это один из двух недостающих файлов из 25 918. Имена и описания предметов,
названия и тексты квестов, имена NPC и их реплики передаются по сокету
**числовыми идентификаторами строк**, а сам текст клиент тянет отдельным
HTTP-запросом.

Формат восстановлен из `lol/utils/StringCollector.as`:

    запрос:  POST <base>/database/texts.xml   телом <data>12,34,56</data>
    ответ:   <любой корень><s id="12">текст</s><s id="34">...</s></любой корень>
    также:   GET <base>/database/texts.xml?all=1  отдаёт всё разом

Имя корня и тегов не проверяется, читается только атрибут `id`, содержимое
проходит через `unescape`. Поддерживаемые макросы в текстах: `%имя%`,
`%sex?мужская:женская%`, `<hint>...</hint>`, обычный HTML.

**Без этого эндпоинта инвентарь не работает:** предмет не попадает в рюкзак,
пока не придёт строка его имени.

### `?all=1` обязан отдавать всё, иначе игрока выбрасывает на логин

Самая дорогая ловушка во всём клиенте. `StringCollector` — вечный синглтон, и
`SBase.initializeStringCollector` подписывается на его событие `update`,
**никогда не отписываясь**:

    StringCollector.parse()   → dispatchEvent("update")   ← на КАЖДУЮ пачку строк
    SBase.initializeLocationNames → GetLocName.loadXML() → dispatchEnding
    dispatchEnding            → SBase.dispatchEvent("onLoad")
    Session.loadSBase         → SceneShifter.enterScene()  ← экран входа

`Session.loadSBase` снимает слушателя с `SSettings`, но не с `SBase`, поэтому
подписка живёт всю сессию. Итог: **любая строка, догруженная после входа в
мир, перезапускает сцену и поднимает окно авторизации поверх игры.** Со второго
раза вход проходил, потому что строки уже лежали в `stringCollection` и пачка
не запрашивалась. Тот же механизм ронял торговлю: открытие лавки просило имена
товаров.

Оригинальный сервер на это не натыкался, потому что его `?all=1` отдавал все
20.8 МБ сразу и клиент больше ни за чем не обращался. Значит заглушка обязана
делать то же самое. Это выполнимо: все идентификаторы строк приходят от
сервера, в SWF нет ни одного `getString` с литералом — проверено по всем
вызовам (`Item`, `Entity`, `NPC`, `Quest`, `Effect`, `SetObject`,
`TransObject`). У нас таблица закрыта целиком: 35 470 строк, 1.6 МБ.

**Признак поломки:** `database/locations.xml` в HTTP-логе запрошен больше
одного раза. Три запроса = цепочка прокрутилась дважды.

## 9a. Идентификатор локации и глобальная карта

`SSEmulator.getLocDescription` разрешает id локации в файл, и **сервер обязан
разрешать так же**: обе стороны читают из выбранного файла сетку проходимости,
и расхождение означает, что игрок ходит сквозь нарисованные стены.

    locations/static/<id>.xml    если такой файл есть в манифесте
    id >> 28 == 4                locations/deadloc/<(id >> 26) & 3>.xml
    id >> 26 == 0                пустошь: gx = id >> 13, gy = id & 0x1FFF,
                                 тайл ((gx + gy) & 3) + 1 из четырёх

Последнее правило — ключевое: **клетка карты, на которой ничего нет, сама себе
id локации**. Поэтому вся карта проходима без единой таблицы, а `g_id` в `lcall`
и id пустоши — это одно и то же число.

Таблица «клетка → посёлок» была серверной и утрачена. Восстановлено 86 клеток
склейкой подсказок карты (`database/locations.xml`, 414 клеток) с атрибутом
`title` файлов `locations/static` — `data/build_settlements.py`. Одноимённые
места (шесть «Лагерей мастеров») разводятся по региону: кандидат, делящий слово
с уже привязанными соседями. Это правило само воспроизвело клетку 5970x1730 →
102, проверенную игрой.

**Отдельного слоя проходимости у карты не было.** Правило выше даёт локацию
для любой клетки, и оно же решает, куда из неё можно: клетка закрыта в ту
сторону, кода которой нет в `outzones` стоящей на ней локации. Все
одиннадцать шаблонов пустоши несут `1234`, поэтому клетка без своего файла
открыта во все четыре стороны, а стена — это всегда чей-то файл
(`recon/analysis/borders.md`). Край мира сделан так же: по периметру
5833..6335 × 1600..2143 стоит кольцо скальных плиток `res/locations/static`
(`data/borders.json`, 2088 клеток), стеной наружу.

На карте клиент не спрашивает ничего: `moveAck` задаёт только скорость, и
дальше фигурка экстраполирует сама (`GlobalMap.moveAck` → `MapObject.startMove`),
поэтому землю держит исключительно сервер. Держать ему осталось две вещи —
прямоугольник мира и воду. Вода снята с самих картинок карты
(`res/globalmap/full`, 8×8 пикселей на клетку, средний синий выше среднего
красного — `data/build_terrain.py` → `data/map_terrain.json`): 1568 клеток,
в основном озеро Насер. Шероховатость той же фотографии какое-то время
считалась горами и оказалась ошибкой — 6130 закрытых клеток, каждая из
которых открылась бы пустошью, и спор с 18 выходами посёлков; сервер эту
колонку больше не читает.

Сервер: `world.passable(gx, gy)` (пол, как `location_at`; за прямоугольником
карты — непроходимо), `travel.walk` идёт по лучу клетка за клеткой
(обход сетки Amanatides & Woo) и обрезает ход перед первой непроходимой,
`move_on_map` везёт игрока по остатку и таймером подтверждает прибытие там.
Ход, которому некуда идти, подтверждается **тем же кадром, что и прибытие** —
`userMove;id=0;dx=;dy=;vx=0;vy=0;`: только он и ставит фигурку на место, и
гасит экстраполяцию (`GlobalMap.userMove` → `walker.x/y` → `startMove(0,0,0)`).
Пустой `moveAck` остановил бы её там, куда клиент уже успел дорисовать, а
`cor_pos` — кадр локации, карта его не слушает. Подтверждения (`cmdAck`)
`moveTo` карты не требует ни в одной из своих форм (`GlobalMap.playerMove`
ничего не ставит в очередь), так что отказ очередь не сдвигает; ход в
локации — требует, см. «Позиция» ниже.

`outzones` в локации говорит, откуда можно выйти и **в какую сторону**
(пятый символ записи: `1`..`4` = W/N/E/S, `a`/`b` — дверь), но не куда: цель
лежала в `serverdata`, а он вычищен во всех 1381 файлах. Клиент, встав на
клетку зоны, шлёт `chWorld;to=1;` без указания зоны, ждёт `cmdAck;res=0` и
затем `lcall` (`Master.changeWorld(1)` → `changeWorldAck` → `lcall`); любой
другой `res`, кроме 39, молча возвращает его в прежнее состояние. Сервер
(`server/travel.py`) читает сторону по клетке игрока: W/N/E/S → соседняя
клетка карты (`world.location_at`, север = `gy−1`), прибытие на
противоположный край; двери — по `data/exits.json`, восстановленному лишь
частично (с поправками из `data/passages.json`), иначе отказ. Проход без
зоны (`walk_in` в `data/passages.json`; сейчас таких мест нет, механизм
живёт для следующего и гоняется `test_walk_in` на своей таблице через
`LAVA_PASSAGES`) окна выхода не даёт вовсе: сервер, приняв `moveTo`,
кончающийся на такой клетке, ждёт 200 мс на шаг, пока фигура дойдёт, и шлёт
один `lcall` — без `cmdAck`, потому что `chWorld` клиент не посылал и
обработчика не ставил (так же, как `/goto` и возрождение). Бой держит и
такой проход (та же проверка, что у `chWorld`): причина уходит строкой в
чат — «Идёт бой: пройдёте через N с», — и
сервер переспрашивает раз в секунду, пока игрок стоит на клетке: путь на
клетку, где фигура уже стоит, клиент не шлёт (`Location.movePlayer`), так
что сам он повторить не может. Ожидание кончается новым `moveTo`, уходом из
комнаты, смертью или разрывом. Вход в игру на такой клетке прохода не
открывает: игрок ставится рядом.

`cmdAck;res=39;` на `chWorld` (клиент показывает «Вы не можете выйти из
локации в режиме боя в течение N сек. после вашего последнего выстрела или
удара ножом», N — `constants;leave_combat_timeout`) сервер отвечает, пока
идёт таймер выхода, и только тогда. Это тот же отсчёт, что клиент ведёт и
показывает сам («Выход возможен через N сек.», `LocationInterface.
startExitTimer`): N секунд от последнего попадания, где игрок на одном из
концов, — `faHit` или `caHit`, которым он попал или по нему попали; промах
отсчёта не запускает. `lch;ws=0` его гасит (`battleMode` →
`deleteTimerLeaveLocation`), новая локация начинается без него. Пока
`ws=1`, клиент гасит кнопку выхода на карту, но кнопки окна выхода на
клетке зоны зажигает по этому отсчёту (`ExitLocationInterface.exitEnabled`),
и сервер пропускает ровно тогда же — даже если за игроком ещё гонится моб:
цель моб не бросает, пока игрок в локации и жив (ни поводка, ни «сдался»),
и бой в локации (`ws=1`) держится, пока он гонится. Тот же таймер держит
`/home`, проход без зоны и путь-квест.

Путь-квест (`quest` в `data/passages.json`): квест жителя, сдача которого
и есть дорога. Так в Нубийскую шахту спускаются и из неё поднимаются — квест
Рудо «Отправка в шахту» (тип 7) у входа, «Скалы: Шахта» (153), и квест
Камала «Выведи меня отсюда» (тип 8) на первом ярусе (612). Так же из
Нубийской долины выезжают и возвращаются: «В Хальфу!» (тип 43) у Демира в
«Караване» (186) везёт на Причал Вади-Хальфы (41), «Назад, в долину»
(тип 44) у Демира на Причале — обратно, пока лучший навык не выше второго
уровня (потолок, ниже). Демир в «Караване» — торговец-регистратор трофеев,
и его списки квестов идут в `userInfo_Trader`. Для клиента это
обычный квест в два шага, который сдают тому же, кто его дал:
`give_quests=|7|;take_quests=|7|;` в `userInfo_Commoner`, `q_status` со
`status=1`, `q_si_del_obj` с `obj=0`, `rew_loc=1` (клиент сам пишет «после
выполнения задания Вас переместят в другое место» — в окне НПС и в журнале)
и `repeatable=1`. «Взять задание» (`q_st;mob=<id НПС>;q_idx=0;`) — как у
любого квеста:

```
cmdAck;res=0;
q_di_del_obj;q_id=<id>;q_type=7;complete=1;obj=1;   доставка без предмета: выполнен сразу
```

Квест в журнале (строка `char_quests`), никто никуда не двигается. Окно
Рудо перестраивает список, и квест стоит в «Завершенных заданиях» — с
текстом финиша («Подмога! Как вовремя!», у Камала «Ну, в дорогу!») и
кнопкой сдачи (`QuestInspector.getTQs`, `QuestInterface.openDescription`);
журнал показывает текст задания и строку о перемещении, статуса у `obj=0`
нет (`DeliverObjQuest.getMissionStatus`). Сдача
(`q_co;obj_idx=0;mob=<id НПС>;q_id=<id>;`) у того же НПС:

```
cmdAck;res=0;                                      ответ на q_co, единственный
lcall;id=612;ws=<бой в 612>;ie=0;g_id=<клетка устья>;  переход, как у /goto, без своего cmdAck
```

(`ws` — настоящее состояние комнаты, куда игрок попадает, как у любого
`lcall`: 1, если там уже идёт бой.)

Строка `char_quests` удаляется, а в историю (`char_quests_done`) сдача не
пишется: история нужна неповторяемым квестам и счёту ежедневных, а путь ни
то ни другое. Значит, ни награды, ни опыта, ни траты дневного лимита, и
путь работает, даже когда лимит на сегодня исчерпан; клиент сдачи сам не
считает, он показывает `daily_available` последнего `q_sys`. На ack клиент
убирает квест из журнала, пишет «Задание <…> завершено» и переспрашивает
`q_status` у жителей (`QuestInspector.takeAck`, `requestAllNPC`) — сервер
отвечает на каждый, где бы игрок уже ни был, — а окно НПС закрывается само
вместе с локацией (`SceneShifter.locationScene`). Прибытие — у места, где
путь нарисован на той стороне (`travel.door_arrival`): под табличкой EXIT
на ярусе, в конце рельсов у входа. Сдать можно только тому, кто квест
берёт, и только стоя с ним в одной комнате, как любой квест: сдача другому
жителю, с карты или кадром, собранным руками, — `cmdAck;res=2;`, никто не
двигается, квест остаётся в журнале. Второй `q_co` того же экземпляра —
`cmdAck;res=1;` (строки уже нет), второго перехода нет.

Бой (идёт таймер выхода — см. `res=39` выше, — свой выстрел или
перевязка в полёте) не отказывает ни во взятии — оно никого не двигает, —
ни в сдаче: любой ненулевой ответ на `q_co` клиент показывает как «Вы сдали
максимальное количество ежедневных квестов» (`QuestInspector.takeAck` →
`ErrorReport` 44). Держится сам переход. Сдача принята (`cmdAck;res=0;`),
в чат один раз уходит причина — «Идёт бой: отправитесь через N с» (выстрел
или перевязка в полёте — молча, переход ждёт, пока они долетят), и сервер
переспрашивает раз в секунду, пока игрок в этой комнате; таймер вышел —
приходит тот же `lcall`, один, без `cmdAck`, даже если моб ещё гонится за
игроком. Ходить по комнате можно.
Ожидание кончается уходом из комнаты (карта, дверь, `/goto`, возрождение),
смертью и разрывом — квест уже сдан, его берут снова; повторная сдача во
время ожидания заменяет его, а не добавляет второй переход.

Отказ во взятии остаётся один: таблица не знает, куда путь ведёт отсюда
(житель стоит не там, где записан путь), — `cmdAck;res=4;` и «Это задание
никуда не ведёт», в журнал ничего не ложится; тот же ответ и на сдаче там.
Сейчас это недостижимо: Рудо стоит только в 153, Камал — только в 612,
Демир (5193) — только в 186, Демир (30) — только в 41.
Мёртвому `q_st` и `q_co` отказывает фильтр мёртвых, с карты — отсутствие
комнаты и жителя (`res≠0`, никто не двигается).

Клиент сам не даст нажать «Взять», если журнал полон (`quest_log_capacity`,
`QuestInterface.getQuest`), а путь теперь в журнал ложится. Сейчас это
недостижимо: в журнале могут оказаться все 16 квестов таблицы, каждый не
больше раза, а мест в нём 20. Когда станет достижимо, в шахте всё равно
никто не заперт: наверх выводит и карта (кнопка карты на ярусе — `chWorld`,
игрок оказывается на клетке устья, оттуда в 153), а место в журнале
освобождает отказ от любого квеста (`q_ca`) (UNDONE, 5.x-журнал).

У Камала квестов два: `give_quests=|8|9|;take_quests=|8|9|;` — путь наверх
первым, так что «Взять задание» на нём по-прежнему `q_idx=0`, а
«Золотоискатель» (тип 9, `q_si_bring_l_obj`: `obj_1=2258`, `obj_num_1=10`,
`rew_gold=100`, то есть 1 унция) — `q_idx=1` и обычный журнальный квест.

Квест «принеси» (`bring_l_obj`) сервер считает по рюкзаку: в `obj_num` —
сколько штук каждой позиции лежит в рюкзаке (кучка — своим размером, не
больше нужного). На `q_st` ответ `cmdAck;res=0;` и сразу
`q_di_bring_l_obj;q_id=;q_type=;complete=;obj_num=|..|;` уже с этим счётом.
После любой команды, изменившей рюкзак, — подобрал мешок, купил, продал,
выбросил, положил в банк, получил по бартеру или `/give` — сервер вслед за
её ответом (и её собственными кадрами) шлёт `q_di_bring_l_obj` без запроса,
если счёт сдвинулся, по одному на квест; клиент печатает «Найдено N …» и
показывает кнопку сдачи только при `complete=1`. Ничего не сдвинулось —
ничего не шлётся. `q_di` по запросу тоже отвечает по рюкзаку. На `q_co`
сервер считает заново: не хватает — `q_di_bring_l_obj` с настоящим счётом
(если он разошёлся с журналом) и `cmdAck;res=3;`; хватает — вещи уходят из
рюкзака, старые первыми, раньше награды и ответа:

```
ss_obj_status;obj=x<oid>;status=0;     каждая исчерпанная вещь или кучка
ss_di_heap;obj=x<oid>;size=<остаток>;  кучка, от которой взяли часть
userInfo_Player;…;gold=<+rew_gold>;…   кошелёк, если квест платит
cmdAck;res=0;
```

Что квест умеет сверх разговора и денег (поля строки `data/quests.json`,
решения владельца 2026-09-26; у клиента для большей части полей нет — это
слово сервера, а тексты говорят сами там, где говорит оригинал):

- **Посылка** (`start_obj`: `[{"obj": тип, "num": штук}]`). На `q_st` вещи
  ложатся в рюкзак до ответа — как покупка, `ss_obj_status;status=1;` и
  `ss_di_*` на каждую, — затем `cmdAck;res=0;` и `q_di_*`. Доставка вещи
  (`q_si_del_obj` с `obj≠0`) «найдена», пока такая вещь в рюкзаке:
  `q_di_del_obj;…;complete=1;obj=1;`, иначе `complete=0;obj=0;` — счёт по
  рюкзаку, как у «принеси», с тем же пушем после любой команды, изменившей
  рюкзак (журнал пишет «предмет … найден, но не доставлен / не найден»;
  клиент на каждый такой пуш печатает «Получен предмет <…> для задания» —
  и на потерю тоже, `LocationInterface.delObject` флаг не смотрит). На
  сдаче одна штука уходит из рюкзака, как вещи «принеси», а с ней и всё
  остальное, что дали при взятии (`quests.START_OBJ_BACK_AT_HAND_IN`), —
  так же, как при отказе. Отказ от квеста (`q_ca`) забирает всё, что дали
  при взятии, сколько осталось: из рюкзака, из рук и с тела —
  `ss_obj_status;status=0;` или новый размер кучки до `cmdAck;res=0;`, а
  после ответа — `rp_info`/`usrUp`, если снятое меняло снаряжение; из
  банка — без кадра. Выдать при взятии можно только то, что вне квеста
  ничего не стоит: торговец не купит, бартер и аукцион не примут (`cost` 0
  и `exchang` 0 или флаг `quest`, `quests.START_OBJ_WORTHLESS_ONLY`), —
  проданное назад не забрать, и «взял, продал, отказался, взял снова»
  печатало бы деньги. Выданное квестом при гибели не падает
  (`quests.kept_on_death`): посылка в мешке на земле — доставка, которую
  не сдать. И выбросить его на землю нельзя (`ss_upd;s_status=2` сессии
  мешка — `cmdAck;res=3;`, мешок не ложится, клиент возвращает вещь в
  рюкзак; `quests.START_OBJ_NOT_ON_GROUND`), и почтой не отправить (`sndml`
  с вложением без `exchang` — `cmdAck;res=3;` без `ctml`, как и окно
  клиента не прикрепит: «Данный предмет нельзя передавать»,
  `mail.postable`): ушедшее к другому отказ от квеста не вернёт, и взятие
  выдало бы его снова — записи Аюба из «Новых вопросов» и есть то, что
  просит «Последний удар», и каждый набор был бы чужим «Последним ударом»
  без босса. Так же не падает и ничего не стоящая вещь, которую один квест
  даёт наградой, а другой просит принести (`quests.STEP_REWARD_KEPT_ON_DEATH`):
  молоко коровы для «Друзей» Зулы, инструменты ящика для «Друзей» Ибрахима —
  дающие их квесты разовые, второй раз не взять.
- **Проверка таблицы на старте.** Каждая вещь строки — `rew_obj`,
  `rew_also`, `start_obj`, `obj`, `objs` — должна быть в игре (`items.params_of`), а
  выдаваемая — ничего не стоить; иначе сервер не открывает сокет
  (`quests.check_items` из `server.main`), как не стартует и с цепочкой,
  которую нельзя пройти. Без этого награда-не-вещь роняла сдачу на
  полпути: квест записан сданным, награды нет, `cmdAck` нет.
- **Награда вещью** (`rew_obj`/`num_rew_obj`; клиент показывает иконки и
  при нескольких даёт выбрать одну, `obj_idx` индексирует `rew_obj`). На `q_co`
  до ответа — `ss_obj_status;status=1;` и `ss_di_*` на каждую новую вещь или
  кучку (кучка не больше `max_count` типа, в кучки рюкзака не доливается):
  из этих кадров клиент и складывает «Вы получили: <…>»
  (`QuestInspector.getRewardItem`). Индекс, не называющий ни одной
  награды, — `cmdAck;res=1;`, ничего не двигается. Вещи квеста — и посылка,
  и награда — ложатся и сверх предела веса (`server.QUEST_ITEMS_PAST_WEIGHT`):
  отказ в `q_co` клиент прочёл бы как дневной лимит, отказ в `q_st` — никак.
- **Награда сверх показанной** (`rew_also`: `[{"obj": тип, "num": штук}]`).
  Окно клиента рисует только `rew_obj`, и больше одной иконки там — выбор
  одной; чтобы дать, как оригинал, «Наган и к нему 50 патронов» (вики
  «Стреляем»: в окне «Вы получите: Наган 1895(G)», в награде — Наган,
  «7.62х25 (OLD) КС 50 штук» и опыт), остальное идёт отдельным полем. На
  `q_co` сразу после выбранной вещи — те же `ss_obj_status;status=1;` и
  `ss_di_*`, и клиент называет их в том же «Вы получили: <…>»; в окне их не
  видно. Порядок сдачи «Стреляем»:

  ```
  ss_obj_status;obj=x<oid Нагана>;status=1;
  ss_di_firearm;obj=x<oid>;…
  ss_obj_status;obj=x<oid патронов>;status=1;
  ss_di_heap;obj=x<oid>;size=50;
  rp_info;…                     +50 к Стрельбе
  usrUp;…                       если навык перешёл уровень
  cmdAck;res=0;
  ```
- **Опыт** (`rew_xp`: `{"medicine": 20}`, ключи `quests.SKILL_KEYS`: melee,
  shooting, medicine, industry). На `q_co` до ответа — `rp_info` по
  сдвинувшимся навыкам, и клиент сам пишет «Медицина: +20 опыта»
  (`SpecSkillMessages`); новый уровень — ещё `usrUp`. Весь опыт — навыку,
  специализациям квест ничего не даёт; премиум сверху, как за любое
  действие. В окне квеста опыта не видно: такого поля у клиента нет.
- **Цепочка** (`need_quest` — тип или список, сданы все; `need_any` —
  список, сдан хоть один). До того `q_status;…;status=0;` (НПС квест не
  предлагает) и `q_st` — `cmdAck;res=4;`. После сдачи клиент сам
  переспрашивает `q_status` у жителей (`requestAllNPC`) и получает
  `status=1`. В `q_si` уходит `need_quest` — первый из списка; клиент его
  хранит и нигде не показывает. Неповторяемый сданный квест — `status=0`
  навсегда.
- **Потолок** (`max_level`: «недоступен после третьего уровня любого
  навыка» — это 2). При лучшем навыке выше — `status=0`, даже если квест в
  журнале: окно НПС его не покажет, журнал может от него отказаться;
  `q_st` и `q_co` (и путь-квест) — `cmdAck;res=4;`.
- **Раз в сутки** (`per_day` у повторяемого: «не чаще 1 раза в сутки» —
  1). Сданный столько раз с начала суток дневного лимита — `status=0` до
  следующих суток, и `q_st` — `cmdAck;res=4;` (у клиента это ложное
  «Получено новое задание», как у любого отказа во взятии). Взятый раньше
  остаётся доступным до сдачи; отдельного отказа на сдаче нет — квест в
  журнале один, а взять его в день сдачи нельзя. Сдача тратит и дневной
  лимит, `q_sys` перед ответом — как у любого повторяемого.
- **Выбор награды** (`rew_obj` из двух и больше: «Сгоревшая микросхема»:
  Салюс МК I или Анестетик МК I). Клиент рисует иконки и шлёт в `q_co`
  `obj_idx` выбранной. `Quest.createRewardItems` разворачивает `rew_obj`
  через AS2 `for..in` и `push`, затем `QuestInterface.buildRewardItems`
  присваивает иконкам `id = n - 1 - i` уже в развёрнутом массиве.
  Поэтому `obj_idx` совпадает с индексом исходного `rew_obj`: 0 для Салюса,
  1 для Анестетика. На сдаче в рюкзак ложится одна
  выбранная, её `ss_obj_status;status=1;` и `ss_di_heal` до ответа.
- **Дневной лимит** (`DAILY_MAX`) считает только повторяемые квесты: сдача
  разового лимит не тратит и при исчерпанном не отказывает, а сдача
  повторяемого шлёт перед `cmdAck` новый `q_sys;daily_available=<N>;` — по
  нему журнал пишет «Сейчас вам доступно N ежедневных квестов». (Каждый
  `q_sys` заводит у клиента свой таймер суточного сброса и старые не гасит —
  так и было на каждом входе в локацию; число в подписи от этого может
  раньше времени вернуться к `daily_max`.)

Порядок кадров на сдаче: вещи квеста из рюкзака, остальное выданное при
взятии (из рюкзака, рук, с тела), награда-вещь, `rp_info` (и `usrUp`),
`userInfo_Player`, `q_sys` (у повторяемого), `cmdAck;res=0;` — и после
ответа пересчёт снаряжения, если с тела что-то ушло.

Вещь, за которой квест шлёт к мобу (тир «Квестовый» в
`data/loot_manual.json`), приходит обычным мешком трупа: `ss_loot;s_status=1;`
и её строка в `ss_ack` слота 24 — нового кадра нет. Разница только в том,
кому она выпадает: строка бросается, пока у кого-то из тех, кто завалил моба
(ранил и ещё в комнате, или добил), открыт квест, который вещь просит, и её
в рюкзаке меньше, чем нужно (`mobs.QUEST_TIER`). Подобрал — счёт «принеси»
сдвигается как всегда, `q_di_bring_l_obj` после ответа на `ss_upd`. Мешок
общий: поднять вещь может и другой. Второй труп на той же клетке, пока
лежит первый мешок, кладёт свои вещи в него, и `ss_loot` не повторяется.

Мешок лежит 15 минут, есть кто в локации или нет (`combat.LOOT_LIFETIME`),
поэтому вошедшему в локацию, где лежат мешки, сразу после входа (за
`e_list` и телами, `lch;dead`) уходит один `ss_loot;s_status=1;hex=|…|;` со
всеми их клетками: `Location.ss_loot` берёт список, а `DisplayLocScene` при
постройке сама читает `lootBagList` локации, так что кадр ложится, построена
сцена или ещё нет. Истёк последний предмет мешка — `ss_loot;s_status=0;`
тем, кто в комнате, как при опустошении.

Истёк предмет, пока окно мешка открыто, — окну об этом не сказать: `Loot`
не слушает ничего, кроме ответов на свои запросы. На «взять всё»
(`ss_upd;s_status=3`) `Loot.allTranferAck` по `cmdAck;res=0` переносит в
рюкзак всё, что показывает окно, истёкшее тоже, поэтому сразу за этим
подтверждением сервер шлёт `ss_obj_status;status=0;obj=x<oid>;` на каждый
такой предмет (`combat.Fighter.ran_out`): `PersEquip.ss_obj_status` находит
его в рюкзаке и убирает. Порядок — `cmdAck`, `ss_obj_status`, затем
`ss_loot;s_status=0`, если мешок опустел.

Житель, поставленный руками (`data/placements.json`), для клиента ничем не
отличается от своих жителей файла: `lch;newUser;pos;rtype` и `userInfo_*`
в том же порядке (`rooms.Room.snapshot_for`), id из того же счётчика. У
вещи-жителя (ящик с инструментами в 184: Commoner, которого `data/npcs.json`
не прописывает, `world.offers_home`) в
`userInfo_Commoner` `can_set_home=0` и `can_banking=0`: клиент рисует только
вкладку квестов, а без квестов щелчок по нему не открывает ничего
(`NPCService.openService`).
Спорить с файлом локации сервер не пытается: сторона объявлена — игрок идёт. Если идти всё-таки некуда (озеро), открывается
карман скал — тупиковая сцена с единственным выходом назад, и клетка карты
не меняется. За прямоугольником карты 5833..6335 × 1600..2143 —
`locations/deadloc/<k>.xml` с одной зоной выхода на стороне `k` (0 W, 1 N,
2 E, 3 S), id `(4<<28)|(k<<26)`; ему отдаётся `g_id` с `z≠0`, и клиент
отключает выход на карту (`Location.isSubLocation`). Дойти туда нельзя —
мешает кольцо скал, — но персонаж, сохранённый вне прямоугольника, войдёт
в мир именно так.

Чат `userMsg`: `group=0` внутри сцены слышат остальные игроки той же комнаты.
На глобальной карте его слышат только другие игроки на карте в радиусе
видимости (8 клеток, расстояние по текущим координатам с учётом движения).
Это выбранная серверная область доставки по списку собеседников карты в
`ChatPan.initialize`, а не восстановленное правило оригинального сервера.
Между картой и локальной сценой канал 0 не передаётся.
`group=4` (торговля) и `group=6` (мир) получают все игроки онлайн;
отображение торгового канала зависит от настройки клиента.
Отправитель получает ровно один `cmdAck;res=0`, без эха `userMsg`, поскольку
свою строку клиент печатает по подтверждению. Получателю передаются исходные
`group`, `entry` (включая префиксы частей длинного сообщения), `nick` и `from`.

Клиент **не разбирает слэш-команды** — всё набранное уходит в `userMsg` как
есть, поэтому серверные команды чата свободны.

Строки, которые сервер пишет в чат сам (`userMsg;nick=@Сервер@;from=0;`:
причина отказа, что выпало при гибели, чем кончился
бартер, трофей зарегистрирован, бой держит переход), **по умолчанию не
уходят** — решение владельца 2026-09-25; сервер пишет их в лог
(`..    not said to <ник>: <строка>`), а `LAVA_SERVER_CHAT=1` возвращает их в
чат (`Session.say`). Ответ на набранную команду — `/where`, отказ `/home`
из боя, тестовые `/goto`/`/give`/`/money` — приходит всегда
(`Session.answer`). Везде в этом документе, где сказано «причина в чат»
или «строка в чат», это о включённом выключателе; кадры и коды `cmdAck` от
него не зависят.

## 10. Экранирование строк

`lol/server/XMLString.as` — процентное кодирование по собственной таблице,
применяется **в обе стороны**:

| Символ | Код   |
|--------|-------|
| `%`    | `%25` |
| `<`    | `%3C` |
| `>`    | `%3E`  |
| `'`    | `%27` |
| `"`    | `%5C` |
| `&`    | `%26` |
| `@`    | `%40` |

Двойная кавычка кодируется как `%5C`, то есть процентным кодом обратного
слеша, а не `%22`. Это особенность оригинала, и её надо воспроизводить:
клиент декодирует `%5C` обратно в кавычку.

Экранирование `@` обязательно: незакодированный символ в нике оборвёт
значение вида `@строка@` раньше времени и разрушит кадр.

## 11. Мир, координаты, движение

### Сетка локации

Гексагональная. Номер клетки в кадрах `pos` и `path`:

    pos = gy * width + gx

`width` берётся из атрибута XML локации: 64 у 1270 файлов, 32 у 126.
Шаг анимации 200 мс на гекс, стоимость хода 1 очко действия за гекс,
и то и другое захардкожено в клиенте.

### Три формы команды движения

| Форма                     | Где работает | Единицы                       |
|---------------------------|--------------|-------------------------------|
| `moveTo;path=\|12\|13\|;` | локация      | номера гексов, первый текущий |
| `moveTo;dy=-250;dx=140;`  | глобальная   | **сотые доли** клетки, смещение |
| `moveTo;trg=12345;`       | глобальная   | перехват игрока по id         |

Отмена перехвата — это `moveTo;dy=1;dx=0;`.

### Позиция: сервер авторитетен полностью

Клиент **не двигается сам**. Отправив `moveTo`, он только запоминает цель.
Анимация стартует исключительно по серверному `userMove`. Значит путь надо
возвращать эхом, в том числе самому отправителю.

Коррекция: `breakMv;id=;pos=;` телепортирует на клетку,
`cor_pos;id=;pos=;` делает то же и **автоматически перевыдаёт** путь до
ранее выбранной цели, то есть игрок сам допройдёт.

Между комнатами — после `lcall` и до `lenter` — `loc` и `pos` сервера уже
новые, а `moveTo;path=` в этом окне — клик, посланный из покидаемой
локации, пока `lcall` до неё шёл (клиент перестаёт слать `moveTo` только в
`CW_STATE`, `FilterManager.createCWFilter`): номера его клеток — сетка
старого файла, на новой они где угодно, в скале тоже. Такой ход не
применяется и не эхается; ответ — один `cmdAck;res=3;`: `moveCmdAck`
покидаемой локации ещё в очереди (`Location.kill` снимает его только на
`lenter`) и в ответ не смотрит. Не `breakMv`: его слушают и покидаемая, и
строящаяся локация, и обе двигают одного ходока (`master.gamer`) на клетку
с номером новой сетки в старой (`LocWalker.breakMove`), а `finishMove` там
откроет окно выхода, если клетка окажется зоной. `lenter` ставит игрока
туда, куда его перенёс сервер. Кадр без `path` (ход карты, `cmdAck` не
ждущий) так не отвечается.

Клиент валидирует свою заявку сам (поиск пути в окне 30×40, препятствия,
занятость клеток в боевых локациях), но это обходится модифицированным
клиентом. Сервер обязан проверять путь заново.

### Обязательный heartbeat на глобальной карте

`lol/core/globmap/MapObject.as`: у каждого чужого игрока крутится секундный
таймер, сбрасываемый только приходом `userMove`.

| Молчание | Что происходит          |
|----------|-------------------------|
| 3 с      | объект гаснет           |
| 6 с      | объект удаляется молча  |

**Сервер обязан слать `userMove` по каждому видимому игроку не реже чем
раз в 3 секунды, даже когда тот стоит** (`vx=0;vy=0;`). Иначе игроки будут
беспричинно исчезать друг у друга.

Это же молчание — **единственное прощание**: `userLost` не шлётся.
`GlobalMap.userLost` убирает игрока из своего списка и глушит таймер фигуры,
но фигуру на карте (`DisplayGlobalMap`) и имя в списке справа
(`GlobalMapInterface`) снимает только событие таймера `lost` — на
`removePlayer` не подписан никто из них. После `userLost` фигура застывала
навсегда (до своего `gmap` у смотрящего), а следующий `newUser` того же
игрока рисовал вторую рядом — «дубли» на карте. Поэтому уходящему с карты или
из радиуса просто перестают слать `userMove` (уходящему на ходу — один
`userMove` с нулевой скоростью, чтобы встал), `newUser` по одному id — один
раз за `gmap` смотрящего, дальше только `userMove`: он сам добавляет игрока,
которого у клиента нет, и двигает того, кто есть (`rooms.GlobalMapRoom`,
`server/test_gmap_presence.py`).

Единицы в разных кадрах разные, это легко перепутать: `newUser` и `marks`
несут целые клетки относительно игрока, `userMove` — абсолютные координаты
плюс скорость в клетках в секунду, `moveTo` — сотые доли клетки.

### Метки адресуются индексом

`updMark;id=` и `rmMark;id=` передают **индекс в клиентском массиве**,
а не ключ базы. Сервер обязан хранить метки упорядоченным списком на
персонажа, и порядок в кадре `marks` должен совпадать с тем, по которому
потом придут эти индексы.

### geoID

    x = (id & 0x3FFE000) >> 13
    y =  id & 0x1FFF
    z =  id >> 26          # ненулевое = подлокация, выход на глобалку запрещён

Разрешение идентификатора в файл: сначала `locations/static/<id>.xml`, если
он есть в манифесте; иначе мёртвая локация; иначе процедурная пустошь, где
из одиннадцати шаблонов реально используются только четыре.

## 12. Состояние DEAD

Отдельной команды «ты умер» нет: смерть приходит двумя разными путями, и оба
кончаются одним окном.

**По ходу боя** — `lch;dead=<id>;`. Про чужого это «положить фигуру»
(`Location.lch` → `DisplayLocScene.dead`), про себя (`id == 0`, как всегда
про получателя) — `Resurrector.lch` → `resurrectGamer()`: `Master.currentState
= DEAD_STATE` и окно `regeneration`. Сервер шлёт его в комнату обычным
броадкастом, где свой id и так станет нулём.

**При входе** — `persInfo;…;death=<0|1>;`. Это **флаг, а не счётчик смертей**:
`PersGenerator.persInfo` кладёт его как `PersInfo.dead = Boolean(param.death)`
(парсер даёт число, так что `death=0` — это `false`), а окно поднимает уже
`Master.lenter` и `Master.gmap`, каждый по `gamer.playerInfo.dead`, — то есть
**после** того, как персонаж где-то встал. Поэтому вошедший мёртвым обязан
получить обычные `lcall` → `lenter` и попасть в комнату: отказать ему во
входе — значит оставить клиента в пустоте без окна. На сервере флаг живёт в
колонке `characters.death`.

В `DEAD_STATE` фильтр клиента (`FilterManager.createDSFilter`) не выпускает
ничего, кроме `resurrect`, — но переходит клиент в это состояние **после**
`lenter`, а не до, и конвейерные запросы (`ss_get`, `q_si`, `getInfo` и
прочие из §7) успевают уйти раньше. Серверная копия фильтра
(`combat.DEAD_PASSES`) поэтому режет только действия, пропуская вход и
запросы: пропущенный `ss_get` навсегда закрывает окно `ss_ack`. Пропускает
она и `gg_info` — клановые вопросы, которые клиент члена клана задаёт сам в
тот самый миг, когда `Master.lenter` переводит его в `LOCAL_STATE`, до окна
воскрешения (§16). Отказ мёртвому — `cmdAck;res=3`, но для `head`, `admit` и
`apply` — клановый немой 20 (`combat.DEAD_REFUSAL`): 3 — это «Сервер не
отвечает» на весь экран.

`resurrect;res_type=<0|1|2>;` ждёт ровно один `cmdAck`. Только `res == 0`
закрывает окно и возвращает `LOCAL_STATE`; на любой другой код
`RegenerationInterface` перезапускает свой 15-секундный отсчёт, а
`ErrorReport`, который слушает **каждый** `cmdAck`, показывает текст кода,
если он у него есть: `17` — «Объект не готов», `3` — «Сервер не отвечает»
(`21` у него текста нет). Поэтому бесплатную кнопку — в окне она подписана
«Частичное восстановление», `freeOfCharge_btn`, доступна с первой секунды —
сервер принимает сразу, а не после отсчёта, и поднимает тело на 10 % HP и
10 % выносливости, как написано под ней. Куда и с каким HP поднять тело —
дело сервера: клиент после `cmdAck;res=0` ничего не меняет, кроме окна, так
что `lcall` домой идёт следом за подтверждением, а HP приезжает обычным
`usrUp` на первый же `getInfo` после `lenter`.

## 13. Облик полного комплекта

Пять предметов одного сэта в слотах голова, рубашка, броня, штаны, ботинки
(пояс не считается, износ не важен) рисуют персонажа папкой
`res/personages/<res>` вместо тела по полу: `PersInfo.persType` отдаёт
`setResID`, если тот задан, иначе `sex`. Свой облик клиент считает сам
(`PersEquip.getFullSetID` / `checkFullSet` на каждом `addItem`/`removeItem`),
`res` берёт из `ss_si_set`. Чужой не может: `ss_ack` про другого игрока только
запоминает список одежды (`wear_arr`), слоты не заполняет. Поэтому сервер
сообщает облик сам, двумя кадрами:

- `ss_ack;…;set_res=<res>` — в ответ на `ss_get` со слотом одежды (клиент шлёт
  его сам, когда ставит игрока по `lch;newUser;rtype=-1`), и в своём `ss_ack`
  тоже. Только ставит облик: `0` клиент игнорирует (`if(set_res)`), снять
  облик этим кадром нельзя. Непрошеный `ss_ack` слать нельзя — его съест
  чужой ожидающий обработчик.
- `ss_obj_move;id=<игрок>;obj=x<oid|0>;from=<слот>;to=<слот>` — пять штук,
  голова → ботинки, `from == to`: каждый опустошает слот и кладёт в него то,
  что там сейчас, после чего клиент сам прогоняет `checkFullSet`. Шлётся всем в
  комнате, когда облик игрока меняется, и одному зрителю следом за его
  `ss_ack` без облика, если у зрителя облик мог остаться: ему его показывали
  кадрами, или прошлый `ss_ack` про этого игрока нёс список одежды с полным
  сэтом. Подтверждений не ждёт.

Окно осмотра (`InspectInterface.setPlayer`) ничего у сервера не спрашивает:
`parseWear()` без аргумента кладёт в слоты `wear_arr` из последнего `ss_ack`
(пустые позиции слот не трогают) и прогоняет `checkFullSet`. Если игрок с тех
пор переоделся, зритель видит старую одежду и старый облик до следующих
кадров о нём. Поэтому сервер помнит облик списка, отправленного в последнем
`ss_ack` про каждого игрока, и при следующей постановке игрока шлёт пять
`ss_obj_move`, если тот список давал облик, а нынешний не даёт.

Пол не участвует: женский персонаж в полном сэте рисуется той же папкой.
Вне военных локаций стоящую фигуру клиент не перерисовывает: `stand` за
`stand` взводит `one_pass_left`, и `playAnimation` останавливается. Новый
облик там виден со следующей анимации (шаг, выстрел, удар), и своя фигура
тоже. В военной локации фигура не замирает — `extendedStand` чередует
`stand_mili` и `stand`, — и облик меняется сразу. Код: `sets.look`,
`inventory.py` («the figure»), тест `server/test_set_look.py`.

## 14. Уровень вещи и покупка патронов

**Надеть можно только по уровню.** `ss_move` на слот одежды (256..261) или
руки (512, 513) проверяет уровень: у вещи это наибольшее число из
`need_skills` её `ss_si_*`, у персонажа — лучший навык (`lvl` в
`userInfo_Player`/`rp_info`). Проверяется и вещь, идущая в `to`, и та, что
при обмене вытесняется в `from`, если `from` — тоже слот тела. Отказ:

    cmdAck;res=45;                       — «У вас не хватает навыков для использования этого предмета.»
    userMsg;entry=@«Наган 1895»: взять в руки можно с 1-го уровня, у вас 0-й@;…

`ss_obj_move` после отказа не идёт; клиент по `res≠0` сам возвращает вещь
(`StuffManager.transferAck` → `applyTransfer(false)`). Лекарства (корень 2) и
патроны под правило не попадают. Что надето выше уровня, сервер при входе в
игру молча перекладывает в рюкзак (в `ss_ack` оно уже в рюкзаке), а после
`lenter` шлёт по строке `userMsg` на вещь: `Перенесено в рюкзак — …`.

**Патроны до 5000 за покупку.** `ss_si_ammo` несёт `max_count=5000` (было
200): это и стопка прилавка, до которой клиент открывает «Сколько штук
купить?», и предел стопки в рюкзаке. `ss_upd;s_status=1|4;obj=x<индекс>;param=<n>;`
принимает `1 ≤ n ≤ max_count` для корня 3 (патроны); для остальных корней
`param` не читается, покупается одна штука — так шлёт и `Trade.buy`. Цена —
арифметика окна: `ceil(round(cost·1000/sell_num)/1000 · n · pmod)` афро или
`ceil(round(g_cost/sell_num) · n · pmod)` сотых золота (`round` — `Math.round`
AS2). Покупка — одна новая стопка: `cmdAck;res=0;`, `ss_obj_status;status=1;`,
`ss_di_heap;size=n;`, `userInfo_Player`. Отказы: 3 — `n` вне окна, 21 — не
хватает денег («У вас недостаточно средств» окна торговли), 27 — вес всех `n`
сверх 50 кг («Вы перегружены»). Код: `inventory.py` («the level», `buy`,
`buy_price`), `items.AMMO_STACK`, тест `server/test_gear_level.py`.

## 15. Трофеи

Трофей — обычный предмет корня 6 (`tr_Skull` 1492 … `tr_Hand` 1496): лежит в
рюкзаке, в мешке, в письме, на аукционе и в бартере, как всё прочее, не
стопка (`Trophy extends Item`). То, что он «говорит», приходит только
динамической информацией:

- `ss_di_trophy;obj=x<oid>;count=<убийств>;k_id=<id игрока>;k_lvl=<ур.>;`
  `v_id=<id игрока>;v_lvl=<ур.>;time=@ГГГГ-ММ-ДД ЧЧ:ММ:СС@;v_clan=@…@;`
  `k_name=@…@;v_name=@…@;` — `updateItemDI` копирует ключи на предмет,
  аннотация печатает «Количество», «Имя/Уровень убийцы», «Имя/Уровень/Клан
  жертвы» и «Последнее убийство»; время — UTC, клиент сам прибавляет свой
  пояс (`Annotation.parseDate`). Строки последними, имена в самом конце.
  `k_id`/`v_id` клиент нигде не читает; сервер шлёт id игроков. `v_clan` —
  название клана жертвы **на момент убийства** (`trophies.clan_of`, из
  базы), пустое — вне клана; запись не меняется, что бы ни стало потом с
  кланом или с жертвой. По нему же ищет окно коллекции
  (`TrophyInterface.setTrophyList`).

Регистрация — часть торговой сессии (`RegTrophyInterface`, «Сохранить
трофеи»): НПС-торговец с `can_trophy=1` в `userInfo_Trader`, клиент
открывает `ss_create;s_type=1` и шлёт
`ss_upd;s_status=6;obj=x<oid трофея>` — ровно один `cmdAck`. Цена —
`cost` трофея в афро (0 окно рисует как 1). На `res=0` окно само гасит
трофей в своём слоте, а из рюкзака его убирает `ss_obj_status;status=0`
(так же кнопка «Сохранить все» полагается на этот кадр для остальных).
Если трофей влился в запись коллекции (тот же вид, та же жертва), следом
идёт `ss_di_trophy` этой записи с новыми `count` и `time`: клиент знает её
предмет и сам его не перезапрашивает. Деньги и «Навык бойца» — целым
`userInfo_Player`. Отказы: 3 — не регистратор, 12 — нет такого трофея в
рюкзаке, 21 — не хватает афро (цена в чате: окно на 21 молчит), 31 —
чужой или безымянный трофей либо лавка, открытая в другой локации
(объяснение в чате).

Коллекция — `s_type=6` (`TrophyInterface`, кнопка трофеев в окне локации):
`ss_create;s_type=6;target=0` → `cmdAck`; `ss_get;target=0;slot=16` →
`ss_ack` со списком зарегистрированных трофеев **без** разделителя «0»
(`TrophyManager.requestTrophyAck` делает предмет из каждой позиции);
`ss_get_di` на них отвечает `ss_di_trophy`, хотя строки в `items` у них уже
нет. `ss_upd` 4 — удалить (`cmdAck` 0/12; строка остаётся ничьей ради
отметки оплаты, так что час на пару удалением не сбрасывается; с витрины
запись уходит тоже); 0 — закрытие без ответа.

Регистраторы — `world.TROPHY_REGISTRARS`: шесть живодеров Мясников (164) и
Демир в «Караване» (5193, локация 186, внутри долины). По `mobs.xml` Демир —
Commoner, сервер строит его торговцем (`lch` `rtype=1`, `userInfo_Trader`
с `can_trophy=1`, `can_trade=0`, `can_repair=0`, пустым `type_list`):
окно «Сохранить трофеи» живёт только в торговой сессии, а её клиент
открывает лишь у `Trader`. Вкладки «Прописка» у торговца клиент не рисует
(`NPCService.openService`), её в «Караване» дают жители Крысолов (5194) и
Точильный камень (5192); `on_conv;op=0` сервер принимает и от Демира.
Адам (5216) — обычный торговец, `ss_upd 6` у него — 3.

Витрина («демонстрируемые трофеи»):

- `ss_get;target=<чья>;slot=32` → **один** `ss_ack;o_list=|…|` — по элементу на
  место: `x<oid>` выставленной записи или `x0` для пустого; длина списка и
  есть число мест («ЗАНЯТО МЕСТ n ИЗ m» в окне коллекции). `target=0` — свой
  (`Gamer.ID`), id игрока — его витрина (окно осмотра, вкладка трофеев,
  рисует не меньше 12 клеток), что угодно другое — пустой список. Отвечается
  и вне сессии `s_type=6`. `PersEquip.requestPublicTrophy` ждёт `ss_ack` или
  `cmdAck` и первым снимает второе — отвечать строго одним.
- Чужие трофеи клиент описывает `ss_get_di;target=<id игрока>;obj=x<oid>` →
  `ss_di_trophy` со словами записи.
- `ss_upd;s_status=1;obj=x<oid>|x0;param=<место>` (в `s_type=6`) — поставить
  запись коллекции на место или освободить его; запись стоит не больше чем
  на одном месте (поставленная на другое уходит с прежнего), бывшая на месте
  остаётся только в коллекции. Клиент шлёт одну-две такие команды на жест
  (новое место, затем «x0» на старое) и на каждый `res=0` сам заново
  спрашивает `slot=32`. `cmdAck`: 0; 12 — не своя зарегистрированная запись
  (общая надпись клиента «Объект не найден»); 31 — такого места нет (без
  надписи). На отказ окно витрину не перезапрашивает.
- `ss_upd;s_status=3` (без `obj`) — купить место после вопроса клиента
  «Купить новое место под демонстрируемый трофей?». `cmdAck` 0 и следом
  `userInfo_Player` с новым кошельком; 21 — мало денег, 31 — мест уже
  `MAX_PLACES`: на любой не-0 клиент пишет «У вас недостаточно денег».
- `ss_upd;s_status=2;obj=<число>` от сервера (число мест) клиент слушает,
  но ничем не рисует, а `ss_upd` слушает всякое открытое окно — не шлётся.

Числа СПРОЕКТИРОВАНЫ (оригинал их не сохранил): `trophies.START_PLACES = 3`,
`MAX_PLACES = 12`, `PLACE_PRICE = 500` афро. Хранение — `trophies.shown`
(место, NULL — только в коллекции) и `characters.trophy_places` (куплено
сверх `START_PLACES`).

Код: `server/trophies.py`, таблица `trophies` (`accounts.SCHEMA`,
`accounts.TROPHY_COLUMNS`), тест `server/test_trophies.py`.

### Команды клиента

Каждая из четырёх **всегда** регистрирует ровно один `cmdAck` (все пути
`ClanInspector`), в том числе отказанная.

- `head;reg=@<описание>@;soc=@<название>@;` — основать. `reg` здесь —
  описание, а не id; поля окна — 40 и 127 символов, оба непустые.
- `admit;char=@<ник>@;perm=<права>;post=@<должность>@;` — пригласить.
- `admit;char=<id персонажа>;perm=<права>;post=@<должность>@;` — сменить
  члену клана права и должность. Две формы одной команды различаются **типом**
  значения `char` (строка или число), а не цифрами: ник «123» придёт как
  `@123@`. Без `char` вовсе (строка списка без id: `CSMessage` выбрасывает
  undefined) — 12, ничего не угадывается.
- `apply;number=<n>;action=<a>;`:

| action | number | смысл |
|---|---|---|
| 0 | 0 | переключить «Запретить другим игрокам приглашать меня в клан» |
| 1 | 0 | у свободного — отказ от приглашения, у члена клана — выход |
| 1 | id члена | исключить |
| 2 | 0 | принять приглашение |
| 3 | ±афро | в казну / из казны: направление по **знаку** (ниже «Казна») |
| 4 | ±золото×100 | золотая казна: выключена, всегда 21 (окна для неё в клиенте нет) |
| 5 / 6 | id клана | улучшить / ухудшить наше отношение (ниже «Дипломатия») |
| 7 | id клана | «Спросить» их отношение к нам |

  `number` обязан прийти и быть целым для всего, кроме казны: исключение по
  строке без id приходит **без** `number`, и прочитанное как 0 оно стало бы
  выходом, а у одинокого главы — роспуском. Нет `number` у 1/2 — 12, у 0 — 20.
- `gg_info;det=<d>;` — вопросы: 1 состав, 3 казна афро, 4 казна золота,
  5 отношения, 6 цены. `gg_info` пропускают и фильтры ENTER и CW
  (`FilterManager`), остальные три — только LOCAL и GLOBAL.

### Кадры сервера

- `fellow` — кто в каком клане (`ClanInspector.fellow`, четыре случая):
  - `fellow;id=0;reg=<клан>;soc=@<название>@;post=@<должность>@;char=<свой id>;perm=<права>;stand=0;`
    — я в клане. Единственный способ сообщить клиенту его **собственные**
    права: после каждой их перемены он получает этот кадр снова. На нём
    клиент сам спрашивает `det=1` (и `det=5` при праве 0x2) — один раз за
    соединение, в LOCAL или GLOBAL (`firstRequest`).
  - `fellow;id=0;reg=0;` при `clanInfo.reg ≠ 0` — меня исключили (или я
    вышел): права сброшены, канал 2 закрыт, «Вас исключили из клана» / «Вы
    больше не состоите в клане». `clanInfo` при этом **не** сбрасывается.
  - `fellow;id=0;reg=0|16777215;` у свободного — приглашения принимаю /
    запрещены (16777215 ставит галочку запрета; `world.md` это путал).
  - `fellow;id=<id сущности>;reg=<клан>;soc=@<название>@;` — про другого
    игрока: «<Клан>» под ником и цвет ника. Теряется, если фигуры ещё нет,
    поэтому едет и в ответе на `getInfo` о нём (после `userInfo_Player` и
    `usrUp`). `reg=0;soc=@@` снимает метку. Для «Солдат СА» клиент кадр
    игнорирует.
- `invite;rec=@<ник пригласившего>@;soc=@<клан>@;pos=@<должность>@;` — окно
  «Персонаж X приглашает вас в клан Y» (модальное `query`). `pos` не
  показывается. Если окно `query` уже открыто, новое не создаётся и
  приглашение теряется молча.
- `gg_list;res=<r>;…` — по `res`:
  - 6 — цены: `data=|<основание, золото×100>|<ухудшить, афро>|<улучшить, афро>|`;
  - 0 — все **другие** кланы с нашим отношением: `data=|id|;names=|@..@|;stats=|-1/0/1|`
    (пустой — `data=|;names=|;stats=|;`). Никогда нашего клана (фильтр окна
    читает несуществующее поле `.names`), id 0 и пустых имён (цикл клиента
    ключует список счётчиком, который их пропускает);
  - 1 (и любой другой, кроме 0, 3, 4, 5, 6, 8, 9) — состав:
    `data=|id|;names=|@..@|;posts=|@..@|;dates=|@ГГГГ-ММ-ДД ЧЧ:ММ:СС@|;perms=|..|;stats=|1/0|`
    (дата — UTC, клиент сдвигает только часы и минуты; пустая строка — «никогда»);
  - 3 / 4 — казна: `data=|N|` (4 сервер не шлёт: золотой казны нет);
  - 5 — их отношение к нам: `data=|X|;stats=|s|`;
  - 8 / 9 — мы / они изменили отношение: `data=|X|;names=|@X@|;stats=|s|` —
    всплывает окно «Ваш клан изменил…» / «Клан X изменил…».
- `gg_struct;id=<id персонажа>;act=<a>;…` — одна строка состава: 0 вошёл в
  игру (`date`, `perm`), 1 добавлен (`name`, `post`, `date`, `perm`), 2
  удалён (только id), 3 изменён (`post`, `perm`), 4 вышел из игры.
- `gg_code;res=20;` — «Вам нельзя этого делать» (слушатель есть, когда
  страница прав была хоть раз открыта).
- `userMsg;group=2;player=<id персонажа>;nick=@..@;entry=@..@;` — клановый
  чат; для канала 2 отправитель берётся из `player`, а не из `from`.

Числа: «char» на клановом проводе — везде `characters.id` (`gg_list data`,
`fellow char`, `gg_struct id`, `number` исключения, `admit char`, `player`);
id сущности (1 000 000 + id) — только `fellow id` о другом игроке. «reg» —
id клана, всегда в 1..16777214 (`clans.id` AUTOINCREMENT: клиент держит
`ClanInfo` по reg до перезагрузки страницы, повторно выданный id показал бы
старое название).

### Коды cmdAck

`ErrorReport` показывает окно на **любой** `cmdAck` с кодом 1–8, 11–19, 27,
44, 45, 1001–1003, а 9 у `det=1/5` включает вечный перезапрос раз в 5 с.
Поэтому клановые отказы — только немые или те, чьи слова нужны:

- 0 — да;
- 5 — плохое название (глобально «Имя содержит некорректные символы»);
- 6 — название занято или зарезервировано («Имя уже используется…»);
- 12 — то, на что нажали, исчезло: приглашение истекло или отозвано, член
  клана ушёл, клан распущен (глобально «Объект не найден»);
- 20 — нельзя, немо; если дело в правах — сначала `gg_code;res=20;`;
- 21 — денег нет («Недостаточно средств» у основания, «Не хватает денег на
  клановом счете» у 5/6, у 3/4 — ничего);
- 22 / 30 — у приглашения: «Персонаж находится в офлайне» / «Персонажа с
  таким именем не существует» (тексты этих двух кодов в `ClanInterface`
  **переставлены**, код выбран по нужному тексту); мёртвый — тоже 22;
- 28 — «Персонаж уже состоит в другом клане»;
- 29 — немо: цель запретила приглашения или уже ждёт приглашения другого
  клана; причина — строкой в чат пригласившему (`Session.answer`: это ответ
  на его действие, а не «сервер сам по себе»).

Никогда: 1–4, 7–9, 11, 13–19, 27, 44, 45, 1001–1003 (`clans.NEVER`). Даже
от мёртвого (§12) и даже на кадр, который не удалось разобрать
(`server.bad_frame_res`): там 20, а не 3. Обработчик, упавший или
вернувшийся без ответа, отвечается 20 (`Clans.command`), второй ответ не
уходит никогда.

### Порядок кадров (обязателен)

- **Основание**: `userInfo_Player` (кошелёк) → свой `fellow` → `gg_list res=0`
  → `cmdAck 0`; затем метка основателя всем, кто его видит, и новый
  `res=0` всем членам других кланов онлайн. Вопросы `det=1/5`, которые
  клиент шлёт на `fellow`, встают в очередь **за** обработчиком `head`.
- **Приглашение**: `invite` цели → `cmdAck 0` пригласившему («Приглашение
  отправлено»).
- **Согласие**: свой `fellow` → `gg_list res=0` → `cmdAck 0`; затем
  `gg_struct act=1` **остальным** держателям состава (новичку — никогда: его
  клиент принял бы строку за себя) и метка новичка его наблюдателям.
- **Выход**: `cmdAck 0` **раньше** `fellow reg=0`: ответ закрывает окно
  (`leaveClanAck`), а `fellow` первым заставил бы `kickedFromClan` открыть
  его снова. Дальше — пустой `res=0` (иначе старые враги так и останутся
  красными: `clanInfo` у клиента старый), `act=2` держателям состава, снятие
  метки у наблюдателей. Если уходит глава и в клане кто-то остался, клан
  сначала переходит к преемнику (`act=3` о нём и его новый `fellow`); если
  глава последний — клан распущен, и остаток казны пришёл ему в кошелёк:
  тогда `userInfo_Player` идёт **до** `cmdAck`.
- **Исключение**: `gg_struct act=2` держателям состава, **включая**
  исключающего, → его `cmdAck 0` (на него клиент сам перезапрашивает
  `det=1`) → исключённому `fellow reg=0` и пустой `res=0` → снятие метки.
- **Права**: `gg_struct act=3` держателям состава → `fellow` самому члену →
  `cmdAck 0`.
- **Запрет приглашений**: `cmdAck 0` → `fellow;id=0;reg=16777215|0;`.
- **Казна** (action 3): `userInfo_Player` → `cmdAck 0` → `gg_list res=3`
  остальным держателям 0x400 онлайн.
- **Отношение** (`apply` 5/6, подраздел «Дипломатия»): инициатору `cmdAck 0`
  **раньше** его `res=8` → каждому нашему члену онлайн (инициатору первым)
  `res=8` и **после** него `fellow` о каждом видимом ему члене того клана →
  каждому их члену онлайн `res=9`. Перед каждым `res=8/9` — проверка I2.
  Последним — `gg_list res=3` с новым остатком казны нашим держателям 0x400
  онлайн (`clan_treasury.tell_balance`).
- **Вход в игру** (первый `enter_location` соединения): члену — свой
  `fellow`, `res=0` (всем членам, не только с правом 0x2: цвета ников
  считаются по нему — решение владельца 6), `act=0` держателям состава;
  свободному с запретом — `fellow reg=16777215`; свободному без запрета —
  ничего. **Выход**: `act=4`.

### Строки в списках

Строковые списки клиент **не** разэкранирует (`SCDataParser.getStringListData`,
в отличие от скаляров), а цикл разбора кадра ищет `;` и `=` прямо сквозь
список. Поэтому элементы идут **сырыми** (`protocol.RawList`): «O'Neil&50%»
приходит как есть, а не «O%27Neil%2650%25», и проверки клиента «это моя
строка» (сравнение с ником) работают. В сыром элементе нельзя `;`, `=`, `@`
и `|`:

- название клана — 3–40 символов из кириллицы, латиницы, цифр, пробела и
  `- _ . , ! ? ( ) [ ] # * + : ~`, минимум две буквы или цифры; уникально по
  «скелету» (`mail._skeleton`: регистр, похожие буквы, пробелы);
  «Аукцион» и «Сервер» заняты (СПРОЕКТИРОВАНО);
- должность — без `@ | ; = % < > & ' " \` и управляющих, до 20 символов
  (длиннее — обрезается молча: у кода 23 на странице прав нет слушателя);
- ник персонажа не ограничен ничем, поэтому **в списках** (и в `name`
  `gg_struct act=1`, чтобы они совпадали) четыре опасных символа заменяются
  похожими: `@`→`©`, `|`→`¦`, `;`→`,`, `=`→`═` (все есть в шрифтах окна).
  `RawList` с опасным элементом не отправляется вовсе.

### Права и ранги

Одиннадцать битов (`Rights.as`): 0x1 без смысла (ставится всегда), 0x2 чат и
отношения, 0x4 / 0x20 положить / взять со склада (окна нет), 0x40 принимать,
0x100 исключать, 0x200 назначать права, 0x400 снимать афро, 0x800 снимать
золото (выключено), 0x2000 дипломатия, 0x8000 всё прочее (глава, код 65535).
Ранг (`rankDetection`): 4 глава; 2 — есть 0x100/0x200/0x400/0x800/0x2000;
1 — есть 0x40/0x20; иначе 0. Выдать может: глава — всё, кроме 0x8000;
ранг 2 — 0x2, 0x4, 0x20, 0x40; ранги 0–1 — ничего. Действовать можно только
на младшего по рангу, не на себя и не на главу. При смене прав проверяются
**изменившиеся** биты: редактор ранга 1 шлёт права цели из выключенных
галочек неизменными, и «новые права внутри выдаваемого» ему бы отказало.
Правку себя делает только глава и только должности: страница шлёт
`perm=65535` из-за ошибки `Rights` (любой ненулевой код разбирается как
«глава»). Приглашённый членом клана, которому нечего выдавать, получает
право чата, иначе он «немой» (решение владельца 5).

### Инварианты сервера

- I1: `gg_struct` уходит только клиенту, который держит состав этого клана
  (получил `res=1` на этом соединении), и каждое изменение — всем таким, по
  порядку. Иначе `act=2` про незнакомый id делает `splice(null, 1)` и
  удаляет **первую** строку.
- I2: перед `res=8/9` о клане X клиент уже знает X по последнему `res=0`,
  иначе сначала полный `res=0` (`createNewClanStanding` путает аргументы).
- I3: у персонажа с открытым приглашением нет клана; основание клана поверх
  приглашения моложе 5 с — 20, старше — приглашение снимается (окно явно не
  показалось: оно модальное). Приглашение живёт 5 минут, одно на персонажа;
  тот же клан может пригласить снова — окно покажется ещё раз.
- I4: 0x8000 — ровно у одного, `clans.head`.

База — единственный источник правды: сервер **ничего** о кланах в памяти не
кэширует (читает строку по ключу на каждую команду), потому что
`tools/admin_account.py`, отдельный процесс, меняет кланы на ходу. В памяти
лишь то, что сказано каждому клиенту (`clans.View`), и открытые приглашения.

### Дипломатия

`server/clan_diplomacy.py`. Страница «Дипломатия» окна клана (кадр 7:
«Клан / Наше отношение к ним / Их отношение к нам»), три команды:
`apply;number=<клан>;action=5;` «Улучшить», `action=6;` «Ухудшить»,
`action=7;` «Спросить». Отношение — -1 война, 0 нейтралитет, 1 мир
(`clan_relations.stat`, `stats` на проводе), **одностороннее**: каждый клан
ставит своё к каждому другому, и чужое от этого не меняется (вики
«Дипломатия»). Строки нет — значит 0.

- **Шаг** — ровно на одну ступень, в пределах [-1, 1]; платит **казна** клана:
  улучшить 1 000 афро (`clans.STANCE_UP`), ухудшить 100 (`STANCE_DOWN`) —
  те же числа, что `gg_info;det=6` показывает у кнопок (`data[1]` вниз,
  `data[2]` вверх). Нужно право 0x2000; у главы (65535) оно есть. Кошелёк не
  трогается: в `clan_ledger` строка `diplomacy` (сток, ref — другой клан,
  char — кто нажал), в `money_ledger` ничего. Списание, новое отношение и
  строка журнала — одна транзакция (`Store.clan_stance_step`): её `UPDATE`
  казны называет всё, на чём решение стояло (казна не меньше цены, другой
  клан на месте, отношение всё ещё прежнее, нажавший всё ещё в клане и с
  правом), и если не задел строку — не пишется ничего.
- **Отказы**: нет права (или клана — страница осталась открытой после
  исключения) — `gg_code;res=20;` и 20; `number` нет, не целое, вне
  1..16777214, наш собственный клан или клана больше нет — 12 («Объект не
  найден»: то, на что нажали, исчезло); шаг за войну или за мир — 20 немо
  (страница гасит кнопку на краю, сюда попадает только устаревшая); в казне
  меньше цены — 21, «Не хватает денег на клановом счете». Мёртвому — 20
  фильтра (§12).
- **Кадры** (порядок — в «Порядок кадров»): инициатору `cmdAck 0` **раньше**
  его `res=8`: окно алерта у клиента одно (`SceneShifter.openNewWindow`
  второе не создаёт), и кто первым — того и читают; так инициатор видит свои
  слова «Вы улучшили / ухудшили отношения с кланом <X>», а не общее «Ваш клан
  изменил…». `gg_list;res=8;data=|X|;names=|@X@|;stats=|s|;` — **каждому**
  нашему члену онлайн, не только с правом 0x2 (цвета считаются по списку
  отношений — решение 6); `gg_list;res=9;data=|мы|;names=|@мы@|;stats=|s|;` —
  каждому члену X онлайн («Клан <мы> изменил отношения к вашему клану на …»
  и колонка «Их отношение к нам»). Перед каждым — I2.
- **Цвета.** `CharInfo.checkColor` красит чужой ник по **нашему** отношению к
  его клану (`standingArray[..].stat`: война — красный, мир и свой клан —
  зелёный, остальное — жёлтый), но на смену отношений не подписан и
  перекрашивает только на клановом событии. `fellow` о другом игроке — такое
  событие (`OTHER_CLAN_MEMBER_ARRIVED` перекрашивает все ники экрана),
  поэтому каждому нашему члену онлайн **после** его `res=8` заново уходят
  метки членов X, которых он видит (`Clans.visible_to`). Их стороне — ничего:
  их цвета нас считаются по **их** отношению, а оно не менялось. Имена на
  глобальной карте под Ctrl (`DisplayMapObject.showInfo`) красятся по списку
  отношений в момент показа — им хватает `res=8`; красная точка мини-карты —
  это нападавший (`Location.setEnemy`), а не война кланов.
- **Спросить** (7) — бесплатно, любому члену: `gg_list;res=5;data=|X|;stats=|их к нам|;`
  → `cmdAck 0`; клана нет — 12; не член — 20.
- **Роспуск** клана удаляет его отношения в обе стороны (`accounts.clan_drop`),
  остальные кланы получают новый `res=0` уже без него; шаг к нему со старой
  страницы — 12.
- Война — только цвета и уведомления (решение владельца 7): ни ПвП, ни лут,
  ни захваты отношения не читают.

### Недостатки клиента

- **Глухой клиент.** После любого закрытия сокета (выход, смена персонажа,
  обрыв) `ClanInspector` снимает все свои подписки и больше их не ставит
  (`kill()` без сброса `sInstance`) — до перезагрузки страницы. `fellow`,
  `invite`, `gg_*` он игнорирует, `cmdAck` — нет, поэтому ответы 1:1 всё
  равно. Сервер замечает это так: членский `fellow` ушёл при входе, `lenter`
  отвечен, а `det=1` за `LAVA_CLAN_DEAF_CHECK` секунд (8) не пришёл, — и один
  раз пишет в чат «Клан: окно клана не получает данных … — обновите страницу
  (F5)». Лечится только лаунчером или правкой SWF (решение владельца 13).
- `inClan` не сбрасывается после исключения: такой клиент снова спрашивает
  `det=1` — ответ `cmdAck 0` без кадра, никогда 9.
- `SettingsInterface.clanInvite` ставит `clanInviteParam=false`, и следующее
  «Вас исключили из клана» может быть проглочено (не исправлено).
- `CharInfo` не слушает обновление отношений: цвета ников меняются только на
  клановом событии — поэтому после смены отношения сервер заново шлёт метки
  (подраздел «Дипломатия»).
- Страница отношений снимает после ответа только сработавший слушатель
  (`upStandingAck` / `downStandingAck` / `setStandingNoMoney`), остальные
  остаются: после отказанного «Ухудшить» следующее удачное «Улучшить» может
  показать «Вы ухудшили…». Так было и у оригинала; снять чужой слушатель
  сервер ничем не может.

### Казна (`server/clan_treasury.py`)

Страница «Деньги» окна клана (`ClanInterface.initMoneyPage`, кадр 5): поля
«положить» и «снять» — только цифры, до 6 знаков; клиент шлёт
`apply;number=N;action=3;` на «положить» и тот же кадр с `-N` на «снять»
(`ClanInspector.addMoneyToClanAccount` / `withdrawMoneyFromClanAccount`).
Остаток спрашивает (`gg_info;det=3;`) только страница с правом 0x400 — без
него она пишет «у вас недостаточно прав для просмотра счета»; золото
(`det=4`, action 4, сумма ×100 дробью вроде `28.999999999999996`) — только
при 0x800, а золотых полей на этой странице нет вовсе
(`goldOperation_bool=false`).

- `gg_info;det=3;` — члену с 0x400: `gg_list;res=3;data=|<афро>|;` → `cmdAck 0`.
  Остальным (без права, не в клане) — немое 20, без `gg_code`: настоящая
  страница без права не спрашивает, а всплывающее «Вам нельзя…» при
  открытии страницы было бы лишним.
- `gg_info;det=4;` — 20 всегда и молча: золотой казны нет (решение
  владельца 8), а обработчик ответа знает только 0 и 2.
- `apply;number=N;action=3;` — **знак** решает, вклад это или снятие, а не
  кнопка: `putAfro`/`takeAfro` не проверяют знак перед тем, как его
  сменить, поэтому «вклад» −500 — это снятие, и право на него проверяется
  как на снятие. Отказы по порядку:
  - не член клана (в том числе исключённый со страницей, открытой по
    старому) — 20;
  - `N` не целое 1..999 999 по модулю — 21. Целое — это `int`, либо `float`,
    равный целому с точностью 10⁻⁶ (`1e2`, `100.0`, артефакт Number×100);
    настоящая дробь (`2.5`), 0, `1e999`, строка, список, ключ дважды —
    21, без округления: деньги двигаются ровно на то число, что решено;
  - снятие без 0x400 — `gg_code;res=20;` → `cmdAck 20`;
  - вклад больше кошелька — 21;
  - запись не прошла: он уже не в этом клане — 20; казна меньше
    снимаемого (две одновременные попытки, или страница показывала
    устаревший остаток) — 21, и строка в чат «На клановом счёте N афро —
    снять M нельзя» (`Session.answer`: страница на 21 не говорит ничего).
- Успех: `userInfo_Player` (кошелёк) → `cmdAck 0` (на 0 страница сразу
  перечитывает кошелёк — `refreshMoney` — и сама спрашивает `det=3`, если
  есть 0x400); затем `gg_list;res=3;data=|<остаток>|;` **остальным** членам
  онлайн с 0x400 (СПРОЕКТИРОВАНО: открытая страница показывает новый
  остаток сразу, закрытая кадр просто не слушает). Тем, у кого права нет,
  остаток не уходит никогда.
- Одна транзакция на три записи (`Store.clan_treasury_move`): казна —
  `UPDATE`, который называет члена всё ещё в этом клане и, для снятия,
  `afro >= N` (две попытки снять всё разом — из игры или из
  `tools/` в другом процессе — не получат обе: вторая ждёт блокировку строки
  и не находит её); кошелёк со строкой `money_ledger` `clan` (ref — клан);
  строка `clan_ledger` `deposit`/`withdraw`. Кошелёк в памяти (`Character`)
  меняется только после записи.
- action 4 (золото) — 21 всегда, при любом `number`.

Для других писателей казны (дипломатия, админка) — `clan_treasury.
tell_balance(CLANS, клан)`: тот же `res=3` держателям 0x400 онлайн.

сотые золота). Поле адресата окно прячет, вложения обнуляет, но `to` и

- Адресаты — все члены клана отправителя, кроме него самого, **и офлайн**
  (решение владельца 10); `to` не читается. Членство — по базе, не по
  клиенту: исключённый до F5 держит старый `reg` и живые кнопки.
- Плата — одна на всю рассылку, по тарифу без веса (`mail.tariff`, как
  `updateLetterPrise`): 10 афро или 0,20 G; в журнале денег — одна строка
  `mail`, ref — первое письмо.
- Письма и плата — одна транзакция (`Store.mail_send_each`). В исходящих у
  отправителя — одна копия (первое письмо), остальные строки с его стороны
  сразу удалены; адресат, выбросивший свою, удаляет строку совсем.
- Порядок: `cmdAck 0` → `ctml;id=<первое письмо>;item=|;code=|;` (его ждёт
  очередь окна) → `userInfo_Player` → каждому адресату в игре `lsml` с
  письмом (если он уже листал входящие).
- Отказ — всегда 37: у `sendLetterAck` это «не в клане», и слушателя у
  этого события нет — окно молчит. Никогда 3 («Сервер не отвечает»), 2
  («Аккаунт забанен») и 34 (окно назвало бы спрятанного адресата). Вне
  клана (в том числе исключённый ранее) — голый 37. Деньги или вещь в
  письме, клан из одного отправителя, мало денег на тариф — 37 и причина
  строкой в чат (`Session.answer`: ответ на нажатую кнопку, как 29 у
  приглашения). Ничего не списывается.

### Админка кланов (`admin_actions.kind='clan'`)

Кнопок роспуска, передачи главенства и переименования у клиента нет
(решение владельца 4). Приказы пишут панель (`/admin`, раздел «Кланы» и
страница `/admin/clan?id=N`) и `tools/admin_account.py` (`clans`, `clan`,
`clan-rename`, `clan-disband`, `clan-head`, `clan-treasury`, `clan-kick`) —
только в очередь; выполняет игровой сервер (`server/clan_admin.py`,
`apply_admin_action` отдаёт `clan` раньше проверки персонажа), итог — строкой
в журнале очереди. `args_json`: `{"op": …, "clan": <id или название>, …}`.

| op | аргументы | что делает |
|---|---|---|
| `rename` | `name` | правила и уникальность — как у основания; всем членам **других** кланов онлайн — новый `res=0` (название в их списке отношений сразу); свои и наблюдатели меток видят новое название только после F5 (`clanArray` держит `ClanInfo` по reg) |
| `disband` | `payout` — кому казну (по умолчанию глава; любой персонаж) | `Clans.disband`: выплата в живой кошелёк с `userInfo_Player` или в строку базы, `clan_disband` в журнале денег и `disband` в журнале казны одной транзакцией; каждому члену онлайн — `fellow reg=0` и пустой `res=0`, снятие меток, приглашения в клан аннулированы, другие кланы получают `res=0` без него; название свободно, id — никогда |
| `head` | `char` — член клана | 65535 переходит к нему, старый глава получает 0x2F67; `act=3` о обоих держателям состава и каждому свой `fellow` |
| `treasury` | `afro` — ±целое, не 0 | `clan_treasury_adjust`: снятие — только пока хватает; строка `admin` в `clan_ledger` с ref = id приказа; членам онлайн с правом 0x400 — `gg_list;res=3` с новым остатком (другим клиент баланс не показывает) |
| `kick` | `char` — член клана, не глава | как исключение, без исключающего: `act=2` держателям состава, исключённому онлайн — `fellow reg=0` и пустой `res=0`, снятие метки; офлайн узнает при входе |

Кэша нет: игра читает кланы из базы на каждой команде, поэтому приказ
безопасен на ходу, а член клана вне игры застаёт всё как есть при входе.
Инструмент не импортирует игру (модули читают файлы клиента при импорте) и
проверок у него нет — только поиск клана по названию/id и персонажа по
нику/id; ответ игры он ждёт (`--wait`, 15 с) и печатает. Если игра не
запущена (её `heartbeat` старше 15 с), приказ остаётся в очереди до старта
игры — инструмент говорит это и выходит с кодом 2.
